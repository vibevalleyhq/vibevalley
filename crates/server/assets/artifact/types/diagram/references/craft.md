# 工程图示清晰度与审校清单（diagram / craft）

## 1. 可读性与抽象纪律

- **控制节点预算**：单张图控制在 8–18 个核心节点、2–4 个主要边界分组；超过 20 个节点时拆为「全景总览 + 子系统详图」两份作品或分层视图。
- **主轴一致，杜绝蜘蛛网**：全图统一从左到右（`LR`）或从上到下（`TB`）的阅读流向；同步调用用实线（`solid`），异步事件/物化落盘/可选回调统一用虚线（`dashed`）。
- **每条边必须有语义标签**：绝不画无文字的裸箭头；架构图标明协议或载荷，时序图标明动作与返回值，状态机标明触发事件与守卫条件，ER 图标明基数（`1:N` / `0..1`）。
- **节点命名对齐代码真实概念**：使用仓库与协议中的真实模块名/表名/接口名，不发明脱节的抽象代号。

## 2. 交付前核对清单

- [ ] `manifest.json` 指定唯一 `entry`（`diagram.json` 或 `diagram.mmd`），不维护相互漂移的双份源。
- [ ] 所有边的 `from`/`to` 与分组 `group` 均引用有效 ID，无悬空节点或未标注的裸连线。
- [ ] 状态机显式标出初始态、终态与异常回退边；时序图明确区分同步请求与异步通知。
- [ ] 对用户已确认架构边界或核心流向的修改均通过 `artifact_suggestion` 提议，未静默覆写。
