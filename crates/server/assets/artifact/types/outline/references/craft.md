# 树状大纲设计工艺与审校清单（outline / craft）

## 1. 信息密度与树形纪律

- **MECE 同级平行**：同一父节点下的兄弟节点保持相同抽象层级与词性结构（例如同为动宾短语或同为模块名），不把顶层目标与实现细节混在同一层。
- **宽度与深度平衡**：单层子节点建议控制在 3–7 个；超过 9 个同级节点时引入中间分组节点，降低折叠/展开时的认知负荷。
- **叶子承载证据**：上层节点写判断与结论，叶子节点放指标、代码路径、风险条件或 `asset/` 截图链接。

## 2. 常见大纲模板

- **问题拆解树**：现象与影响 → 假设分支（各带验证方法与证伪条件）→ 根因确认 → 修复 `todo` 子树。
- **会议实时纪要**：议题分支 → 讨论要点（`bullet`）→ 明确决议（`quote` + `props.decision: true`）→ 行动项（`todo` + `props.owner` / `props.due`）。
- **知识地图 / 脑暴**：顶层主题不超过 5 个 → 二层视角（用户、技术、成本、风险）→ 三层具体点子与权衡。

## 3. 交付前核对清单

- [ ] 无孤儿节点、无循环引用，`rootIds` 与所有 `children` 均能在 `nodes` 中查到。
- [ ] 每个节点不超过 1–2 句，没有整段大块散文（需要成段论述时改用 `docs`）。
- [ ] 可执行事项均标记 `kind: "todo"`，重要元信息放入 `props` 而非堆进长标题。
- [ ] 未静默覆盖或删除用户刚刚编辑过的分支，必要改动已发起 `artifact_suggestion`。
