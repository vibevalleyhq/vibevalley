# 写作

文档、Note、README、skill、提交说明、PR 描述、代码注释、界面上的帮助文字和给主人的回复，都照这一篇写。第一部分管写什么、删什么，第二部分管词和格式怎么写。文档放在哪、写什么，见 [docs/AGENTS.md](../AGENTS.md)；代码注释写什么，见 [code.md](code.md)。官网的宣传文案和首页的诗句不用它，那些靠节奏和修辞（[为什么换成这一篇](../../.agents/notes/implemented/process/2026-10-17-one-writing-standard.md)）。

## 写什么，删什么

信息密度高，证据在前，讲清机制。知道的事实直接写，有依据的结论直接说，不用「值得注意的是」「一定程度上说明」「需要特别强调」铺垫。

**开头**直接给主要结论、核心数字或关键机制，不介绍接下来要怎么写。

**事实**尽量一句话交代时间、主体、行为、规模和来源（文件和行号、提交、命令的输出）。

**解释**只留三种：讲因果机制的，澄清容易混淆的因果的，建立新分类的。其余的解释删掉。

**推论**要带来前文没有明说的东西：可检验的预测、约束条件、因果关系、对产品或成本的影响。只是把前面的事实换个说法概括一遍的，删掉。

**证据的强弱**用措辞表达（「测过」「代码里是」「推测」），不另写段落强调。限定条件只留影响事实判断或推论成立的。

**比较**多个对象、多个指标用表格，表格后不逐行复述。

**章节**按要回答的问题分，不为了完整加引言、过渡和小结。总结只留前文还没概括过的重要结论。

**删掉的东西**：

- 写作者对自己工作的评价和过程（「我仔细查了」「这是最关键的一步」）。
- 对已经清楚的事实的第二遍解释，包括用否定句告诉读者不要怎么理解。
- 重复的免责声明和谨慎的表态。
- 每条证据都包成一个小论证：背景、材料、含义、限制、意义。让事实和机制直接进文章。
- 教程式的举例，以及用假设的例子证明一条本来就好懂的规则。例子用实际的东西：这个仓库里的文件、命令、真实的输出。
- 同一件事在第二处展开：一件事只写在它的家里，别处链接过去。Note 不复制文档里的清单；skill 不复制 `AGENTS.md`。

**删除测试**：删掉一段，读者对事实、数字、机制、因果、适用条件和结论的理解完全不变，就删掉。以「这说明」「值得注意的是」「因此」「不过」「需要强调的是」开头的段落要重点查：有的承载必要的推论，多数只是复述。

步骤类的文字（skill 的步骤、文档里的操作）本来就是一步一步的，「删除教程式讲解」不管步骤本身，只管步骤之间解释「为什么」的话。

## 词和格式

给 agent 读的文字（`AGENTS.md`、规矩、skill、Note）读错的代价比啰嗦大，下面几条是硬规则。规则来自 [hai-simplified-technical](https://github.com/hylarucoder/hai-stack/blob/main/skills/hai-simplified-technical/SKILL.zh_CN.md)（ASD-STE100）。

- **词**：一词一义，一义一词，用[用语表](../README.md#用语)里的词，同一个东西不换说法。不用「适当」「有关的」「较为」「基本上」「若干」「显著」「大幅」这类程度词，不用「处理」「操作」「优化」这类空动词，不用「开箱即用」「无缝」「赋能」这类套话。
- **要求**：只用「应」「不应」「宜」「不宜」「可」「不必」，强弱按这个顺序。用主动句，写明谁做。
- **步骤**：编号列表，一步一条指令，动词开头，条件写在前，结果单独写。
- **警告**：放在步骤前，先写指令再写后果；分「警告」和「注意」两级。
- **标点**：全角标点，全文一种引号（「」），中文和英文、数字之间空一格，范围用「–」，代码名放在反引号里。

引文、代码、命令输出、专有名词和原话照原样保留。改别人的文字时，原来的要求按原来的强弱保留，只删空的程度词。影响判断的风险和回退办法要写，写一次。
