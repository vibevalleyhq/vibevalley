# 架构、模块边界与测试设计

**先明确业务语义与不变量，再决定架构和模块边界；模块内部设计与测试策略共同落地，测试结果反过来检验设计。** 测试是模块的使用者，不是实现完成后附加的一层脚本。

本文规定设计和评审的方法，不表示仓库每个模块都已满足这些准则。现行结构见 [架构](docs/architecture.md)，测试分层与预算见 [地基](docs/subsystems/foundation.md#测试金字塔)，具体改造留在 Agent Notes。

| 层次 | 回答什么 | 产出 |
|---|---|---|
| 道：设计原则 | 什么应保持不变，为什么这样划分责任 | 不变量、状态与资源的所有者、取舍依据 |
| 术：设计方法 | 怎样把原则落到模块边界、实现和证据上 | 契约、依赖关系、同步与故障场景、测试分层 |
| 器：实现与检查工具 | 用什么表达、执行和守住这些决定 | 类型、Effect 原语、脚本替身、测试运行器、门禁 |

道约束术，术选择器。换成 Clock 是器的变化；显式表达时间依赖是术；不让业务依赖隐藏的外部输入是道。不能用更复杂的测试工具代替缺失的模块契约。

## 道：先明确责任，再追求可测试

### 业务语义先于代码组织

模块设计从系统应保证的行为出发，不从文件大小、技术类型或测试框架出发。

- 谁拥有状态，谁能修改，其他模块读什么？
- 一次操作在什么时刻算成功，哪些步骤应原子完成？
- 重复、并发、取消、外部失败和进程重启分别留下什么？
- 哪些结果允许稍后生效，调用方如何知道它已生效？
- 规模和资源上限是什么，超出时拒绝、排队还是降级？

例如，Session 的执行与工作目录安全约束属于[帮工的契约](docs/subsystems/session.md)，不应由测试替身决定。业务政策不清楚时应先作决定，不用增大超时或放松断言替代决定。

### 架构规定所有权，边界规定合作方式

架构分配状态、业务决定、资源和生命周期的所有权，规定依赖方向。模块边界将这些决定表达成输入、输出、错误、完成条件和关闭契约；模块内部设计再选择数据结构、函数、锁与事务。

边界不只是 TypeScript interface。一个返回 `void` 的异步方法，即使类型完整，也可能没有说清返回时是已接收、已持久化还是已执行。调用方需要猜测的部分仍是隐式契约。

宜隐藏内部机制，不应隐藏调用方正确使用模块所需的语义。跨模块一致性应由明确的事务或恢复流程保证，不能靠两个模块碰巧按同一顺序更新。

### 显式输入降低推理成本

时间、随机数、环境、外部响应和调度顺序都可能影响行为。应在拥有该依赖的边界取得它；纯规则接收值，执行流程使用可替换的外部能力。

这对应三个设计依据：

- **引用透明性**：纯规则在相同输入下给出相同结果，能独立推导和验证。
- **依赖倒置**：业务依赖所需能力的契约，不依赖特定厂商、全局对象或进程实现。
- **信息隐藏**：模块隐藏实现细节，让调用方只依赖稳定的业务语义。

显式不等于每个函数都收一个 Clock、每个对象都配一个接口。纯日期比较收 `now` 即可；只有跨越真实依赖边界时才需要端口。

### 可控制、可观察、可关闭共同决定可测试性

| 能力 | 含义 | 不意味着什么 |
|---|---|---|
| 可控制 | 能在边界给定输入、时间和外部结果，构造必要的交错 | 能随意修改模块私有状态 |
| 可观察 | 能通过结果、状态或事件判断契约是否满足 | 暴露内部字段，记录每次私有函数调用 |
| 可关闭 | 明确谁停止任务、释放资源，关闭何时完成 | 全局清空所有计时器，把未完成工作丢掉 |

测试设施也应满足这三项：等待器有截止和取消，替身拒绝意外调用，观察器不漏订阅窗口，资源随作用域释放。

### 测试是反馈，不是唯一目标

难测是设计的诊断信号，不直接证明架构错误。验证跨模块恢复需要完整流程，验证真实 git 行为需要真实仓库；这些成本有业务理由。一个到期判断却需要整座农场，就应检查职责是否耦合。

判断一次修改是否改善设计，应问：**拿掉测试以后，它是否仍让模块更容易理解、更难误用、更容易正确组合？** 可测试性应与一致性、性能、安全和维护成本共同取舍，不以接口数、纯函数比例或 mock 数为目标。

## 术：把原则落成契约与证据

### 架构与边界审查

每条非平凡业务链路应明确下列内容；写在拥有该行为的子系统或计划中，不另建重复的全仓清单。

| 项目 | 应明确的决定 |
|---|---|
| 不变量 | 哪种结果无论失败或交错都不应出现 |
| 所有权 | 状态、决定、资源分别归谁；是否存在第二份可写真相 |
| 依赖 | 调用方向、外部能力、反向通知方式 |
| 输入与输出 | 参数含义、默认来源、返回值所代表的阶段 |
| 一致性 | 锁和事务保护什么；跨模块如何恢复；事实何时发布 |
| 失败与重复 | 错误类型、重试边界、幂等或去重语义 |
| 时间与顺序 | 哪种时间、哪个时区、同刻事件如何排序 |
| 生命周期 | 构建、订阅就绪、启动、停止接收、取消、释放分别由谁负责 |
| 容量 | 队列、并发、缓冲、记录的上限与满载行为 |
| 证据 | 每项不变量由哪种观察证明，在什么最低有效层验证 |

这是设计依赖顺序，不是先写完全部架构才允许测试的瀑布流程。可先写一个最小测试表达契约，再据此调整边界；不应为了保住原测试写法而扭曲业务语义。

### 模块内部区分决定、执行与驱动

| 部分 | 负责 | 证明什么 |
|---|---|---|
| 决定 | 根据显式状态与输入计算业务结果 | 边界值、组合和不变量 |
| 执行 | 取得状态，在锁和事务内应用决定，调用外部能力、发布事实 | 并发安全、失败残留、持久化与恢复 |
| 驱动 | 从接口、事件或周期触发执行，管理任务生命周期 | 接线、启动次序、取消与关闭 |

三者不必拆成三个服务。只有职责可独立命名且能降低耦合时才提取，保留在原业务模块内；不新建一个收集所有规则的技术层。

以定时任务为例，[到期计算](apps/server/src/cron/when.ts)与[服务执行](apps/server/src/cron/cron.ts)应分别承担日期决定和持久化、投递责任。测试直接调用 tick 能验证一次执行，不能单独证明周期驱动已接好；测试拨钟能验证调度，不能替代事务失败与恢复测试。

提取纯决定时，应保留「读取、判断、提交」的并发边界。把判断挪到锁外可能引入过期快照；函数变纯不代表整个流程变正确。

### 显式状态

一件事沿一条线走（签了、正在接、通话中；等着、就绪、关了），就用一个联合表示它：每个状态一个标签，只有这个状态才有的东西挂在这个状态上（失败的意图才有 `fault`，通话中的授权才有 agent id），存在一个 `let`、信号或 `Ref` 里。例子：[意图](apps/web/src/state/intent.ts)的 `IntentAt`、[语音](apps/server/src/voice/voice.ts)的 `GrantPhase` 与 `MossPhase`、[记性源](apps/server/src/memory/sources.ts)的 `Held`、帮工招人时的 `reached`（[帮工](apps/server/src/session/session.ts)）。

- **各管各的维度分开放。** 在任一状态下都可能为真的，不并进联合：表单的校验、提交、输入法组字（[表单](apps/web/src/infra/form/form.ts)）；MOSS 回答的音频发完、回答结束和被切断（[MOSS](packages/ai/src/realtime/moss.ts)）。硬并只会得到它们的乘积。
- **永远同值的删掉副本。** 读源头：通话的「在结束」就是它 `life` 的 abort。
- **共享对象靠同一性比较时，留着对象、换它的状态。** 通话和实时线路共用一个 `MossLine`，判断靠 `activeMoss === target`，所以只换它的 `phase`。
- **会被别处读原因的，先记原因再中断。** 记性源退役时同步记下原因和一个完成信号，再分出纤程去停：被中断的操作无论何时醒来都读得到原因。
- **闭包里改的状态放进有类型的属性。** TypeScript 按初值收窄闭包外对 `let` 的读，看不到闭包里的赋值；放进标好类型的对象属性或有名字的类型（[闪播](apps/web/src/features/media/flash-stream.ts)）。
- **页面的帧不拆。** 帧是 Solid 的 store，按 id 逐个 reconcile（[帧](apps/web/src/infra/frame.ts)）；为了联合改成按状态整个替换，会让每次换态重建整份画面。

`practice:check` 的 `loose-flags` 拦一个函数里三个以上的 `let` 布尔：多半是一条没写出来的线；真是几个独立的维度，就照上面分开放、各自起名。不用 XState 等外部状态机运行时：TypeScript 判别联合配合服务端 `SynchronizedRef`、客户端 `state/` 的 `Atom` 与组件内 `createSignal` 加 `variant()`，零额外依赖即可获得编译期穷尽检查并与 `Scope` 组合。

### 错误与回滚契约

- **三层错误各走其道**：外部 I/O 失败在 `Effect.tryPromise({ try, catch })` 边界立即包成带 `cause: Schema.Defect()` 的 `Schema.TaggedError`；业务拒绝用协议 `ApiError`（可恢复时附带 `next: Next[]` 或 `settings: VoiceFix`）；内部数据自相矛盾用 `Inconsistent`（缺陷），绝不伪装成普通拒绝。
- **内部失败走错误通道，资源回滚走 `Scope`**：服务内部方法遇到拒绝或故障时在 `Effect` 错误通道返回，不把 `{ refused?: string }` 塞进成功返回值，也不用 `let refusal = ""` 加 `Effect.tapError` / `Effect.option` 旁路捕获；多步资源获取用 `Effect.acquireRelease` 绑定作用域，失败或中断时自动逆序释放。
- **线上只暴露闭合 `ApiError`，客户端无损转 `UiFault`**：内部细粒度 `TaggedError` 在服务端边界按 `catchTag` 处理或转为 `ApiError`，不泄漏到 HTTP 契约；客户端 `faultOf`（[apps/web/src/infra/api.ts](apps/web/src/infra/api.ts)）将全部 `ApiError`（含 `502`/`503`）归类为明确的业务拒绝并保留 `next`、`settings` 与 `retryable`。

### 从测试困难诊断设计，避免先补工具

| 信号 | 先检查 | 设计方向 |
|---|---|---|
| 测一个判断需要完整应用 | 决定是否混在外部执行中 | 显式输入，提取领域决定 |
| 准备大量无关 mock | 模块是否拿了过宽的依赖 | 收窄真实能力边界，重新分配职责 |
| 返回后仍需 sleep 或固定次数 yield | 完成语义、订阅就绪是否明确 | 等待已定义的结果或阶段 |
| 需要修改全局时间、环境 | 外部依赖是否隐藏 | 在装配或适配器边界接入 |
| 注入失败需要改私有字段 | 故障是否有实际外部边界 | 在该边界控制结果，不改内部状态 |
| 关闭后仍有回调 | 谁拥有任务与订阅 | 成对取得释放，作用域管理 |
| 重构内部实现就坏很多测试 | 断言是否绑定私有步骤 | 对公开行为和必要的交互契约断言 |

不应增加 `isTesting`、跳过校验开关、测试专用业务分支或任意暴露的内部状态。替身可以控制外部端口，但不应复制被测模块的完整业务算法。

### 时间与同步分别建模

| 需要 | 正确的语义 |
|---|---|
| 日期、业务期限、跨重启恢复 | epoch 时间与明确的时区；纯规则显式收时间 |
| 进程内等待与耗时 | 调度和经过时长；有回拨风险时核实单调来源，不将其持久化为跨进程期限 |
| 真实进程保护、测试防挂死 | 独立的真实截止时间，不依赖被冻结的业务时钟 |
| 知道后台工作已完成 | 方法返回、状态、事件或阶段确认，不靠时间流逝猜测 |

同一业务时间线的读取、等待和测试输入应一致。外部事件自带的发生时间与本机接收时间可以不同，但应明确字段语义；浏览器和服务端也不是一个可以一起拨动的时钟。

Clock 的读取不应推进时间；同刻事件的顺序应由业务已有的序号或排序契约表达。测试时间推进与真实 I/O 完成是两件事，虚拟时钟不能使外部进程立即结束。

事件观察应避免「先读取、后订阅」的丢失窗口。生产方法完成与观察器消费完成也应分开；不应让测试观察器的速度成为生产方法返回的条件。证明没有事件发生，应以一次已完成操作或受控时间窗口为边界，而不是任意让出一轮事件循环。

### 模块设计与测试策略共同落地

测试应选择能证明不变量的最小真实环境，不以 mock 越多或启动模块越少为成功标准。

| 行为 | 保留的真实部分 | 可控制的部分 |
|---|---|---|
| 纯业务决定 | 领域函数 | 全部输入值 |
| 事务与锁 | 模块服务、数据库和相关状态更新 | 外部响应、故障、并发交错点 |
| git 与文件协议 | 真实本机资源和适配器 | 临时目录、受控命令输入 |
| 模型或外部服务交互 | 业务调用与结果解释 | 脚本端口；适配器另测协议 |
| 启动、恢复与跨模块交接 | 实际模块组合 | 外部 agent、模型与环境 |
| 页面显示和接线 | 组件或页面及相应运行环境 | 日期、宿主能力等测试所需边界 |

具体层次、入口和预算只在[测试金字塔](docs/subsystems/foundation.md#测试金字塔)维护。高层补接线风险，不重复低层的所有分支；低层测试通过也不能代替真实应用验收。

竞态场景应写出「前态 → 已进入的阶段 → 被阻塞的外部结果 → 取消或故障 → 应保持的不变量 → 观察点 → 收尾」。选择影响结果的交错，不靠随机并发碰撞代替已知竞态。

测试装配应复用生产的领域组合，在外部能力边界替换实现。一个通用等待帮手不能证明事务，一套脚本替身不能证明真实适配器；测试设施自身应验证失败、取消、隔离和清理。

### 设计评审的交付标准

一次以可测试性为目的的设计改动，应能指出：

- 哪项业务语义原本不明确，现在由什么契约表达。
- 哪个模块少承担了什么，调用方少知道了什么。
- 哪类错误由类型、所有权或资源结构避免，不再只靠约定。
- 哪些行为在更小的真实环境中得到证明，哪些仍需完整流程。
- 哪些旧路径和测试帮手被删除，是否保留了原有事务、安全及回归保证。

如果只有新增的接口、开关和通用框架，却说不出减少了什么耦合，应重新评估方案。测试耗时和稳定性应通过运行测量，不从文件数、代码行数或静态命中数推断。

## 器：按边界选择工具

下表列出仓库已有工具与能力，不保证每个调用方都已正确使用。具体 API 约定见 [vv-effect](.agents/skills/vv-effect/SKILL.md)，命令与验收入口见 [开发](docs/development.md)和 [vv-acceptance](.agents/skills/vv-acceptance/SKILL.md)。

| 要表达或验证的边界 | 已有工具 | 使用限制 |
|---|---|---|
| 形状与错误契约 | TypeScript 联合、Schema、带标签错误 | 类型不能独自表达事务、完成与取消语义 |
| 依赖与组合 | Context.Service、Layer；[服务装配](apps/server/src/services.ts) | 在服务捕获依赖前替换；不另建一套测试业务装配 |
| 业务时间 | Clock、TestClock、[timeHere](apps/server/src/infra/time.ts) | 固定起点先于会捕获或读取时间的构建；不负责外部 I/O 完成 |
| 任务与资源 | Scope、acquireRelease、FiberSet、FiberMap | 关闭语义由业务定义，工具只实现归属与释放 |
| 交错控制 | Deferred、[gate](packages/testkit/src/until.ts) | 挡住明确的一步；不靠缩短业务超时制造竞争 |
| 状态与事件观察 | Stream、[whenState](apps/server/src/testing/layers.ts) | 确认订阅和匹配目标；不假设全系统能被 drain |
| 真实边界等待 | [waitFor 与 within](packages/testkit/src/until.ts) | 有界等待和防挂死，不替代业务完成契约 |
| 外部 agent 与模型 | oar 的 scriptedRuntime、[模型替身](packages/ai/src/testing.ts)、[agent 夹具](packages/agent/src/testing.ts) | 控制端口协议，不复制业务；意外调用应失败 |
| 浏览器时间与交互 | Playwright Clock、组件与页面测试 | 浏览器时间独立于服务端；截图不证明动态行为 |
| 边界防退化 | [模块检查](apps/server/src/modules.test.ts)、[lint](scripts/oxlint-plugin.ts)、测试与 health 棘轮 | 检查守住已确定的边界，不用指标代替设计判断 |

工具使用中的失败也可能是架构反馈：大量 Layer 覆盖可能来自过宽依赖，持续增加 gate 可能来自过度耦合的流程，越来越复杂的观察器可能来自缺失的结果契约。应先回到边界审查，不继续堆工具。
