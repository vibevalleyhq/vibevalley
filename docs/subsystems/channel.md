# 频道

主人、管家和帮工说话的地方是频道（`channel`）；农场有一个默认频道（开机时没有就建一个 `general`），主人可以再开，农场的皮把默认频道叫「田头」。主人和每个管家另有一个私聊（`direct`），只有他们两个；主人也能和每个帮工的档案私聊。频道有一个照看它的管家（`Channel.orchestrator`），主人在里面说话、没 @ 别人时是它回答。频道里的消息可以挂一个串（`thread`），派活时开的是工单串。帮工自己在串里汇报、提问、交接，管家不转述。微信、飞书、QQ 经连接器（`connector`）各接一个频道，主人在外面说的话就是在这个频道里说的。「要你处理的事」是 Inbox（来电），归[通知](docs/subsystems/notice.md)。

## 管什么，不管什么

| 管 | 不管（谁管） |
|---|---|
| 频道、串、消息、@，消息号和地址 `#<频道>:<消息号>` | 工单的状态和派活（[工单](docs/subsystems/issue.md)）；派活时 `issue` 开 Session，频道模块只为这张工单开工单串 |
| 一条消息给谁、叫不叫醒，三道刹车，送达的状态 | 一轮怎么跑、能不能插话（帮工经 `Helpers.deliver` 交给 oar，[帮工](docs/subsystems/session.md)） |
| 帮工的汇报贴进工单串；带话、验收意见、冲突经工单串交给帮工 | 汇报怎么读出结论（`session/rules.ts` 的 `summaryOf`） |
| 帮工在 `/mcp` 上的说话工具（`channel_message_send`、`channel_message_list`、`channel_unread_list`）背后的规则 | 工具的定义和认人（`apps/server/src/tool`、`mcp`、`Sessions.who`） |
| 连接器：扫码登录、只认主人、收件和发件、转成纯文本 | 管家怎么回答（`orchestrator`）；连接器把话交给 `orchestrator.Say`，管家照频道的规则被叫醒 |
| | Inbox 和巡查（[通知](docs/subsystems/notice.md)）；定时到点在频道里说的那句（[定时](docs/subsystems/recurrence.md)） |
| | 频道、私聊和串在界面上的样子（[farm-ui.md](docs/reference/farm-ui.md)、`apps/web/src/farm/chat`、`apps/web/src/features/channel`） |

## 在哪

- **频道**：`apps/server/src/channel`（`Channels`）。`chat.ts` 是对外的方法（`say`、`speak`、`read`、`tellSession`、`orchestratorSays`、`spoken`、`notice`、`openChannel`、`makeDefault`、`topOf`、`addressOf`……）、写一条消息、算给谁、叫醒和提示、推进已读和「看到了」、开串和开机恢复、订阅（`follow`、`reports`）；`rules.ts` 是只有它用的纯规则：`mentionsIn`、`parseChatTarget`、`channelNameProblem`、`chatAudience`、`wakeInput`、`busyNotice`，黄金数据在 `testdata/rules.jsonl.gz`；`model.ts` 是它在内存里记着的频道和串、参与者和主人的已读位置，`audience.ts` 是定一条消息给谁、叫不叫醒要用的：谁跟着哪个串、主人上次说话后帮工之间来回了几次、每个人上次被帮工叫醒的时间。`deliveries.ts` 是还开着的投递（待送、提示过、交出去了），每条带着收件箱要显示的；看到了、丢掉了的就不在里面。
- **几处共用的规则在 `apps/server/src/channel/state.ts`**：`targetOf` 写地址，`defaultOf` 认出默认频道，`hopLimit`、`agentWakeCooldownMs`、`wakeBreaker`、`noticeBatchMs`、`wakeMessages`、`summaryChannels`、`retryWindowMs`、`heldShown` 这些常数，核心状态里留多少频道和串（`keepChannels` 100 个）。
- **订阅**：契约是 `packages/protocol/src/rpc.ts` 的 `Subscriptions`（Effect RPC），服务端 `apps/server/src/http/rpc.ts` 挂在 `/api/v1/rpc`，页面经 `apps/web/src/base/gateway.ts` 连、`features/channel/follow.ts` 按频道存。
- **表**：`channel_participant`、`channel`（频道、私聊、串都是一行，照 Discord；`is_default` 至多一行为真，`peer_id` 每个对面至多一个私聊）、`channel_message`（每条带它的修订号、回复的号、改和删的时刻、置顶、回应）、`channel_attachment`（附件的名字、类型、大小，文件在家目录的 `attachments/<sha256>`）、`channel_mention`、`channel_follow`、`channel_read_cursor`、`channel_seen_mark`、`channel_delivery`；连接器的 `connector_account`、`connector_inbound`、`connector_outbox`。表结构在 `apps/server/db/migrations/0001_schema.up.sql`。
- **连接器**：`apps/server/src/connector`（`Connectors`）。`connector.ts` 是桥：账号和它的代际、配对、只认主人、收进来的话交给管家、持久收件、发件表和退避；`text.ts` 是送出去的写法（`ownerLine`、`plainText`、`splitText`、`flushText`）；三家的协议和扫码登录在 `weixin.ts`、`feishu.ts`（飞书用 `@larksuiteoapi/node-sdk`）、`qq.ts`。
- **接口**：`channel.message.send`、`channel.message.update`、`channel.message.delete`、`channel.message.list`、`channel.message.search`、`channel.reaction.toggle`、`channel.pin.toggle`、`channel.pin.list`、`channel.thread.create`、`channel.attachment.create`、`channel.create`、`channel.update`、`channel.default.set`、`channel.markRead`；读附件是 `GET /api/v1/attachment/<id>`（`http/attachment.ts`）；`voice.hear`、`voice.agent.hear`，`connector.list`、`connector.login`、`connector.verify`、`connector.logout`、`connector.channel.set`（[capabilities.md](docs/reference/capabilities.md)）。管家的工具 `channel_list`、`channel_create`、`channel_update`、`issue_comment_create`、`channel_message_list`；帮工的 `channel_message_send`、`channel_message_list`、`channel_unread_list`、`session_list`（`apps/server/src/tool/tool.ts`）。
- **配置**：`chat.notice_batch_ms`（忙时攒多久再提示，默认 3000）、`chat.retry_wake_ms`（叫醒没开口以后多久再叫，默认 3000）。
- **页面**：农场窗口的田头和频道菜单（`apps/web/src/farm/chat`，`ChannelMenu.tsx`，频道之下一段私聊）；整页的聊天页 `/chat`（`apps/web/src/features/channel`，侧栏分频道、私聊、帮工三段；`/chat` 是默认频道，别的在 `/chat/<id>`）；两边的输入框（回车发送、@ 叫人、失败了同一稿用同一把钥匙重发）在 `apps/web/src/features/channel/composing.ts` 的 `createComposer`，两边只画；开频道和改频道的表单两边各画一份，栏、忙和服务端的拒绝都在 `apps/web/src/features/channel/channelForm.ts` 的 `createChannelForm`；连接器页 `/settings/connectors`（`features/connector/ConnectorsPage.tsx`）。

## 模型和不变量

- **数据库是家，先写库再成事实**：一条消息和它的 @、跟帖、投递在一个事务里写进库，提交以后才施加 `message`、`channel` 事实。核心状态 `WorkspaceState.chat` 只放最近的 100 个频道和串（挤出去的只有串），不放消息；每个都带服务端算好的 `unread`（主人没读的、不是自己说的、不是提示）、`last`（最新一条是谁、开头、什么时候），没挂工单和计划的串带 `title`（帮工说话的串是帮工的名字，别的是它挂着的那条消息的开头）。说的话按频道订阅。`message` 事实照旧每条都施加：游戏、通知和工单听它，它把所在 channel 的 `lastNumber` 推到这条的号码。`state.json` 不存频道，开机从库里放回。帮工的已读位置、跟帖、投递不进核心状态：库是它们的家，频道模块在内存里记着要用的那部分（下一条）。
- **消息的去处由库里的身份决定**：连接器引用旧消息时回到它所在的频道或串，发件只送到那里所属的频道接的账号。两条路都由 `messageLocation` 按消息 id 查出它所在的 channel 和顶层频道（`top`）；消息或串被最近状态挤出、服务端重启，都不改变去处。
- **没处理的 @主人 留到读过或回复过**：频道模块从库里的 @、已读位置和主人在同一处的后续消息算出完整集合，经 `ownerMentions` 事实写进 `Chat.ownerMentions`；不受最近 100 个的限制。写出 @主人、主人回复、标记已读和开机时刷新，每次用一条查询带回消息、频道和地址。通知只读这个结论，不再从聊天窗口推测完成条件。
- **记着自己写过的，不再读回来**：频道模块开机时把全部频道和串、参与者和主人的已读位置读进 `model.ts`，此后每写一次库就把同样的改动告诉它（每个方法照它对应的那条查询算），按 id 找频道和串、按消息找串、主人读到哪、谁跟着串、来回了几次、谁刚被叫醒过、谁还有哪些没看都问它们；投递的每次变化（提示、交出、看到、退回、丢掉）先写库再告诉 `deliveries.ts`，开机先把交出去没看到的退回，再读一遍；刚写下的消息也在内存里拼好往下传，不按 id 再读。只有它写这几张表，所以记着的和库里的一样；一个事务失败时，它在事务里告诉过 `model.ts` 的改动库里没有，就从库重读一遍。主人自己说的话、在串里说的、电话里说的，「读到这一条」和这条消息在同一个事务里。
- **写库一个一个来**：改频道的都在 `chat.ts` 的一把锁（`Semaphore`）里，数据库一个连接、一个写入方，所以 `number` 的先后就是提交的先后，不用像多写入方那样等「稳定」。不应开连接池。
- **页面按频道订阅，按修订号续上**：每个频道有一个修订号（`channel.revision`），那里的消息每写下或改动一次（改、删、回应、置顶）就加一，记在那条消息上（`ChatMessage.revision`）。页面经一条 WebSocket 订阅它正看着的频道和串：`channel.follow({ id, after })` 先从库里补 `after` 以后变过的消息（按修订号，每条是它现在的样子），再推之后的每一次变化；落后超过 `catchUpMax`（200）次就回 `Reset`，页面重读最新一页（`channel.message.list`）再从那里接着订阅。先订阅、后读库，两边都有的按修订号去掉，中间的变化不会漏。页面按消息号留修订号大的那份；比读进来的几页更早的消息变了，等翻到那一页时一起读。读得慢的订阅积压到 64 条就结束，页面带着修订号重连。`channel.reports` 是全农场的汇报（农场的日志用）：按消息 id 接着读，没给 id 时从最近 `logKeep`（80）条起。主人自己的消息带它的 `sendKey`，页面的「发送中」那一行按它换成服务端的那条。
- **只放农场自己的页面**：WebSocket 不受 CORS 管，别的网页也能连本机的端口。upgrade 之前，`Host` 要是回环地址（`127.0.0.1`、`localhost`、`[::1]`），`Origin` 有的话要和 `Host` 同源；只查 `Origin` 不够，一个被解析到本机的名字（DNS rebinding）就是它自己的源。经「连接到本机」转来的带设备头，由那一头查过（[连接到本机](docs/subsystems/lan.md)）。
- **一处一列消息号**：主键是 uuidv7，`number` 在每个频道和串里从 1 数，对外的消息号就是它。地址是 `#<频道>`、`#<频道>:<消息号>`（默认频道是它自己的名字，比如 `#general`），私聊是 `@owner`（管家读写它和主人的私聊时写，`@主人` 也认）；频道名 1–24 个字母、数字、汉字、`_`、`-`，不能重名，这样地址能读回来。
- **channel 三种（`type`），照 Discord**：频道（`channel`，有名字，可以带说明、默认项目和分组）、私聊（`direct`，主人和一个对面 `peer`：一个管家（它的档案 id），或一个帮工的档案 `profile:<档案>`；没有名字，列表里用对面的名字 `title`）、串（`thread`，挂在 `parent` 频道的一条消息 `root` 下，`subject_kind` 是 `issue`、`talk`）。
- **默认频道是一条数据**：`channel.is_default`，协议里是 `Channel.default`；没写频道的话（连接器、电话、定时、提醒）去那里，代码只认这个标记，不认名字、不认类型。开机时一个频道都没有就建一个 `general`（`firstChannelName`）设成默认；`channel.default.set` 换一个，在同一个事务里清掉旧的。名字存下来、写进地址，不随语言变；农场的皮把它画成「田头」（`farmChannelLabel`）。
- **私聊在开机时建好**：和每个管家的那一个（`peer` 是它的档案 id），一个对面只有一个（`on conflict do nothing`）；开机以后新建的管家在第一次 `channel.direct.create` 时建。和帮工的档案的私聊在主人第一次点「私聊」时建（`channel.direct.create { agent }`），它挂着这个档案的私聊工单（`subject` 是工单，下一条），所以它也是那张工单的串。它不放活：从私聊里记的工单、定的定时落在默认频道（`topOf`），帮工也不在私聊里。工单串的 `subject_id` 是工单的 id；没挂工单的 Session 开的是 `talk` 串，`subject_id` 是它自己；有人往 `#频道:<号>` 说话时现开的串也是 `talk`，没有 `subject_id`。
- **一张工单一个串**：重开、换帮工都还是这一个串，前后几个帮工的派活、汇报、主人的话都在里面。串的主人是这张工单现在在干活的帮工（`sessionOnIssue`），每次写消息时按工单现算，不存；没有帮工在干时串没有主人。从帮工找串只走一个函数（`threadOfSession`：先找它的工单，再找串），不拿帮工的 id 去找工单串。核心状态里 `message` 事实的 `thread` 是工单的 id。页面的串标题是工单标题，帮工走了也对（`apps/web/src/features/channel/rules.ts` 的 `threadTitle`、`threadOwnerOf`）。
- **谁在频道里**：主人和每个管家在每个频道里（管家是参与者，id 是它的档案 id，名字是档案的名字，说话前照档案更新），私聊里只有主人和它的 `peer`；参与者的种类和别处记「谁做的」是同一组词（`ActorKind`：`owner`、`orchestrator`、`session`、`system`），一条消息的 `fromKind` 就是说话的人的种类，主人的 id 是 `owner`（protocol 的 `ownerId`，`@主人` 指它）；帮工在它的活所在的频道里，在哪个频道派的活，工单串就开在哪个频道下面。帮工派出来时加入（`channel_participant`），离开时打上 `left_at`，说过的话留着，给它没交完的投递作废（`dropped`）。
- **和帮工的档案私聊是一张藏起来的工单**：每个档案一张私聊工单（`issue.talk` 是私聊的 id，交付物 `answer`，派给这个档案），不在看板、不在管家的 `issue_list` 里，没有要主人按的按钮。主人在私聊里说话，就是在这张工单的串里说话：有执行在做它就交给它；没有就派一个（`Issues.talkOn`），交给它的活是只读的私聊规矩加私聊里最近的 12 条（`talkJob`、`talkContext`），在工单的项目里，没有就在档案的工作目录，再没有就在最近干过活的那个项目。它占一个同时干活的名额；每一轮交回来就把它改的清掉（`discardWork`），它说的话和汇报都写在私聊里；交回来以后闲 10 分钟（`talkIdleMs`）就收工，下次再说就派新的一个。要改代码，它或主人把这件事记成工单，照常派、看、合。
- **频道自己能改**：`channel.update` 改名（频道照旧不重名、能写进地址；串可以起一个标题，空着就是它挂着的那条消息的开头）、照看它的管家（`orchestrator`，要是管家的档案，空或默认管家都存成没设，库里 `channel.orchestrator`）、分组（`category`，空是不分组）和位置（`before`：排在哪个频道前面，服务端给全部频道重排 `position`）。侧栏按分组、按位置列，拖一个频道到另一个上就排在它前面、进它的组。归档（`channel.archive.toggle`）的频道和串不在侧栏、串列表里，消息和地址照旧在；默认频道不能归档。删除（`channel.delete`，先试跑 `channel.previewDelete`）只删没人用的：默认频道、还有帮工在那里干活、有定时、接着连接器、有排队的工单、挂着工单串的都拒绝，说是哪一样；删频道连它的串、消息、跟帖和已读一起删，施加 `channelGone`。
- **提醒级别**（`notify`）：每个频道和串一个，`all`（默认）、`mentions`（只有 @主人 的算）、`none`；串没设时照它的频道（`notifyOf`）。`none` 的不算未读、不进 Inbox 的 @ 提醒、不转到连接器；`mentions` 的未读只数没处理的 @主人。`channel.notify.set` 改它。
- **列出来**：`channel.list` 是全部频道和私聊，默认的在前（管家的 `channel_list`）；`channel.unread.list` 是调用者自己没读完的地方，最新的在前，每处带地址、几条、有没有提到它（帮工的 `channel_unread_list`，主人调就是主人的）。
- **标成未读**：`channel.markUnread { id, number }` 把主人在那里的已读退到这一条之前；页面在主人离开那里之前不再自动标成已读。
- **@ 名**：`@w3`（帮工的 id）、`@管家`（这处的管家）、别的管家的档案 id（`@agent-1`，长的先认，`@agent-12` 不是 agent-1）、`@主人`、`@所有人`（只有主人用才算）。反引号和代码块里的不算；名字在它的词结束处结束（`@w3你看` 是 w3）。写 @ 就是叫醒；@ 了不在地里的，消息照发，发的人被告知没送到。
- **这处的管家**（`orchestratorOf`）：频道是它自己设的，没设或设的不再是管家时是默认管家；串跟着它的频道；私聊的对面是管家时是对面，不是时是默认管家。服务端把它写进每个 `Channel.orchestrator`，页面不另算；改了频道的，它的串也重发一遍。
- **给谁、叫不叫醒**（`chatAudience`，「管家」都是这处的管家；每个管家都算在场，都不冷却）：

| 谁说的 | 叫醒谁 | 只让谁知道 |
|---|---|---|
| 主人在频道里 | 被 @ 的；没 @ 别人时是管家 | 这个频道里的帮工 |
| 主人在私聊里 | 对面（`direct`）：那个管家，或档案私聊工单现在的执行；@ 只是字，不记、不投递 | — |
| 管家在私聊里 | 谁也不叫（主人照常算未读） | — |
| 主人在串里 | 被 @ 的、这张工单现在的帮工、跟着这个串的；工单没人在干时只记下 | — |
| 管家或帮工 | 被 @ 的；在工单串里说话叫醒这张工单现在的帮工 | — |
| 帮工的汇报 | 没做成时叫醒管家 | 做完时给管家；计划里的帮工不给，计划自己告诉管家 |
| 派活消息、农场的提示（`notice`）、通话里说过的话 | 谁也不叫 | — |

  在串里说过话或被 @ 过，就跟着这个串（`channel_follow`）。`@主人` 不产生投递，它进 Inbox。

- **三道刹车**只管 agent 叫醒 agent，主人的话不受限：一个频道或串里从主人上次说话算起最多叫醒 4 次（`hopLimit`），到了 @ 照记、照显示，不叫醒，那里贴一句提示（每次主人说话后只贴一次）；同一个帮工被 agent 叫醒至少隔 60 秒（`agentWakeCooldownMs`）；连着 3 次叫醒都在开口前失败（`wakeBreaker`）就不再自动叫它，工单串里贴一句，主人的下一句叫醒它的话解除。被拦下的投递照样记着（`held_by` 是 `hop_limit`、`cooldown`、`wake_breaker`）。来回次数和冷却从 `channel_delivery` 现算；熔断归 `apps/server/src/channel/breaker.ts` 的 `WakeBreaker`：计数在内存里，重启清零；开口只清计数，熔断要主人点名或帮工离开才解除。
- **消息会变，变了不是新闻**：主人能改自己的聊天消息（`channel.message.update`，记下 `edited_at`，@ 不重算），能删任何一条（`channel.message.delete`，正文、附件和回应清掉、记下 `deleted_at`，号留着，还没交出去的投递丢掉，`dropped_why: deleted`，挂在它下面的串留着）；回复记下同一处被回复的消息号（`reply_number`），回应存在消息上（`{ 表情: [谁…] }`，`channel.reaction.toggle` 加上或去掉主人的那个；页面先给 8 个常用的，「更多表情」里是全部），置顶记下 `pinned_at`。改动只推给订阅的人：不施加 `message` 事实、不投递、不叫醒、不算未读。
- **送达看得见**：一条要叫醒帮工或管家的话交到它手上时（投递变成 `handed`，管家是交出去当即），服务端以它的名义在那条消息上加一个 👀。
- **附件**：`channel.attachment.create` 收 base64（至多 25 MB，`attachmentMax`），按 sha256 存一份，回 `Attachment`；发消息带它们的 id，消息的 `meta` 里记下名字、类型和大小。读是 `GET /api/v1/attachment/<id>`：图片、视频、声音内嵌（消息里直接显示、播放），PDF 在新标签页里看，别的下载；都带 `nosniff`，PDF 以外带沙箱（浏览器的 PDF 阅读器在沙箱里打不开），不会当成农场自己的页面跑。主人改消息时能去掉附件（`channel.message.update` 的 `attachments`：留下的那些）。给 agent 的那一行写附件的名字和它在这台电脑上的路径（`messageLine`），帮工直接读文件；回复写成 `reply=<号>`，改过的、删了的也写明。
- **搜索**：`channel.message.search` 在全农场或一个频道和它的串里找含这些字的消息（不分大小写，删了的和提示不算），新的在前，至多 50 条，每条带地址。字里认几个过滤（`parseSearch`）：`from:`（主人、管家、帮工的编号或名字）、`in:#频道`、`has:file`、`has:image`、`has:link`、`before:`、`after:`（日期，本地的零点）；页面原样交给服务端。
- **链接预览**：消息里的 http(s) 链接（至多 3 个），服务端在写下以后去读那一页的标题、说明、站名和图（`embeds.ts`），读到了记在消息上（`channel_message.embeds`，修订号加一）；读不到就没有。只连公网：每次请求和每次跳转前，名字解析出的每个地址都要不是本机、局域网、云的元数据地址；只跟 3 次跳转，3 秒、512 KB 为限，只读 `text/html`，不带任何凭据。主人改了消息就照新的字再读一遍。
- **消息的地址**：页面上一条消息在 `/chat/<频道或串>?m=<号>`：读到那一页、滚过去、亮一会儿。搜索结果、置顶、回复的引用点了都去那里，「复制链接」复制它。一条消息里贴着本农场的消息链接，页面就在它下面显示那条消息现在的样子（`linkedMessages`：频道是页面认得的，从哪个地址来都算，手机有它自己的；默认频道的链接不带频道，只认本页的地址），点了跳过去；服务端不给这种链接读预览（是本机或局域网的地址）。
- **跳到**：工作台里任何一处按 Ctrl+K（Mac 上 ⌘K），或点聊天侧栏顶上的「跳到…」，按名字找频道、串、私聊（`#` 只找频道和串，`@` 只找私聊），还没私聊过的档案也在里面，选了就开一个；名字开头对上的在前，再按未读、按最近说话排，归档的不列（`switchTargets`）。
- **送达**：每条给帮工的投递走 `pending` → `announced`（插过不带正文的提示）→ `handed`（放进了一轮的输入）→ `seen`；离开的是 `dropped`。这一轮真的开口才算 `seen`；没开口就结束、会话关掉、服务端重启都退回 `pending`，过一会儿再叫。宁可重复给，不会丢。给管家的投递交出去当即算看到。
- **主人的话重发不成两条**：`channel.message.send`、`issue.comment.create`、`voice.hear`、`voice.agent.hear` 带页面为这一次发送生成的 `sendKey`（至多 64 个字，长了拒绝）。同一个人带同一个键再发就是已经说过的那一条：不另写、不再送，管家也不再听一遍（唯一索引 `channel_message_send_key` 在发送者和键上）。输入框由 `createComposer` 持有整次发送：文字、频道或串、指定档案、项目和地号共同决定意图；同一意图失败后重发用同一个键，改变其中一项就生成新键。发出去的参数取发送时的快照；迟到的成功只清掉没有再编辑、也没有换目标的那份草稿，输入框关掉后不再读取它的目标或回调。帮工的 `channel_message_send` 不带键：60 秒内（`retryWindowMs`）同一个帮工在同一处说一模一样的话，返回原来那条。连接器按外部消息 id 去重。
- **消息带着产生它的那次干活**（`meta.run`）：过程面板按这个号取事件；没有号的消息不按时间推测归属。`meta` 按自己的 Schema 读回，整份无法解析或形状不对就当没有元数据，不拿半个坏值猜归属。创建频道的接口返回实际的频道号，页面用它跳转，不从名字猜号、不等状态流确认。
- **连接器只认主人**：微信扫码的人就是主人；飞书返回扫码者的 OpenID 时直接绑定，没返回时和 QQ 一样，由第一个私聊机器人发 6 位配对码（前面可以带「配对」和空格）的人成为主人。别人的话丢掉，群里的不收。账号和密钥在 `connector_account`，不进日志、不发给页面；断开就删掉这一行。
- **连接器只往外连**：微信长轮询，飞书、QQ 长连接，都是服务端连出去，不收 webhook。
- **收件至少交付一次**：平台交来的消息先写进 `connector_inbound` 再算收下；管家那边成功、完成标记没写进去时，重试会重复交一次。不保证恰好一次。

## 怎么走

**主人说一句**（`channel.message.send` → `orchestrator.Say` → `channel.Say`）：写库、算投递、推进主人的已读，提交后施加事实；被叫醒的是管家就经 `forOrchestrator` 交给它（带着是哪个管家 `agent` 和那处的 `type`），它在哪个频道、私聊被叫就回在哪里；主人在默认频道和私聊里的话它读成「主人说」，别处读成带地址的群聊消息，现状的最后一行写它正在回话的地方（`addressOf`）。管家每回答一次，说完写成一条完整的消息（`orchestratorSays`），写下就投递；它调工具之前说的那句是单独的一条。还在想、在写的时候，频道里没有这条消息，核心状态记着每个管家在哪个频道里（`orchestrators[<档案 id>].channel`），页面只在那里画「在想…」「正在输入…」，头像和名字是那个管家的。

**派活开工单串**：执行模块告诉频道模块雇了一个帮工（`sessionNews` 的 `hired`），它为新的 Session 建参与者，把它在频道里的已读位置放到最新，按它的工单找串：

1. 工单还没有串：以管家的名义在频道里发一条派活消息（`dispatch`，「派 @w3（名字）去 项目：要做什么」），同一个事务里在下面开工单串，帮工跟着它。开串失败时派活消息也不留。
2. 工单已经有串（重开、换了帮工）：在串里以管家的名义写一条派活的话（「这张工单交给 @w5（名字）接着做，第 2 次派活」：第几次照串里已有的派活消息数，串挂在第一次的下面），同一个事务里让新帮工跟着这个串；已经跟着的就不再写，开机重放不会说两遍。串里的派活消息不让管家跟着串，不然主人在串里的每句话都会叫醒管家。

没挂工单的 Session 照旧在频道里发派活消息，下面开它自己的 `talk` 串。

**叫醒一个帮工**（`kicked`）：

1. 帮工不在地里：给它的投递作废。
2. 帮工在忙：攒 `chat.notice_batch_ms`（3 秒），经 oar 插一句不带正文的提示（`busyNotice`：哪几处、几条、有没有提到你、最后是谁），投递标成 `announced`；同一条只提示一次。它在压缩上下文时不插，压完再提示。
3. 帮工歇着、有要叫醒它的投递、没被熔断：开新的一轮，输入是 `wakeInput`：最新的 3 条全文（`wakeMessages`），别处没读的最多 20 处的摘要（`summaryChannels`），写明旧消息只读不回、除非直接问到它；投递标成 `handed`。
4. 这一轮开口了（`launchActivity` 的 `spoke`）：交给它的都算看到。没开口就结束：退回 `pending`、记一次失败，过 `chat.retry_wake_ms` 再叫。

**帮工说话**（`channel_message_send` → `speak`），发出前按顺序查：

1. 60 秒内同一处一模一样的话：返回原来那条。
2. 刚读的是一个串、却要发到频道顶层：先让它确认一次（`confirm`）。
3. 目标里有它没看过的新消息：先不发，给它看最多 3 条（`heldShown`），记成看过；改了再发，或带 `anyway` 照发。
4. 发出去，推进它的已读；不在地里的 @ 回给它。

`channel_message_list` 默认读 30 条、最多 100 条，推进已读；不写地址时帮工读自己的工单串。`channel_unread_list` 列出它没读的频道和串。

**汇报**：帮工一轮结束（`sessionNews` 的 `reported`），频道模块以帮工自己的名义把这一轮贴进它这张工单的串（`report`）：做完的是最后一段话里的结论（`session/rules.ts` 的 `summaryOf`），没有就用汇报的摘要，截到 1500 字；被打断的不贴。

**带话和意见**：主人的带话、验收没过的意见、冲突和检查失败交回帮工，都经 `tellSession` 以主人的名义说在工单串里，按串的规则叫醒帮工；没有工单串的 Session 直接 `session.Deliver`。

**开机**：说到一半的消息标成说完；所有 `handed` 退回 `pending`；为地里每个 Session 补上参与者和工单串；把最近的频道和串放回核心状态；开始以后把还在地里的帮工的投递再推一遍。

**和帮工的档案私聊**（`channel.direct.create` → `Issues.talkWith`；对面是管家时只开它的私聊，没有工单）：第一次建私聊和私聊工单，把私聊挂到工单上（`linkTalk`）。主人在里面说一句：频道写下、提交，`ownerInThread` 告诉工单；私聊工单现在有执行在做，就照串的规则叫醒它（`chatAudience` 的私聊分支认 `threadOwner`）；没有就 `talkOn` 派一个，它进来时只跟着私聊（`handedOn` 不在私聊里写派活的话）。它答完，汇报贴在私聊里（`publishMessage` 把私聊当工单串），工单清掉它改的，排一个 10 分钟后的收工（`idleLater`）；这期间主人又说话，它接着答，交回来时重新计时。

**外面进来的话**（连接器）：

1. 适配器先用 Schema 解码平台响应，再把消息翻成「谁、说了什么、回复凭据、引用了哪条」；合法 JSON 的形状不对时进入退避，不进入交付。微信的二维码、扫码状态、消息页和发消息结果各有自己的 Schema；`message_id`、`msg_id`、`svr_id` 先把 64 位数字改成字符串再解码，避免精度丢失。每页消息和下一页游标交给 `voiceInbox.accept`，同一个事务写进 `connector_inbound` 和 `connector_account.cursor`，失败就整页回滚、游标不动；飞书和 QQ 的回调等这一行落库后才返回给 SDK。同一个平台消息 id 只收一次（`on conflict do nothing`）。
2. 收件工人（`voiceInbox.run`，有新收件或每秒）按顺序交付：持久化的 Inbound 先按 Schema 读，形状不对或内外编号不一致的坏行记错误日志并结清，不堵住后面的有效消息；这不是把正常投递失败丢掉，后者仍重试。还没配对的，对上配对码就绑定主人、回一句「配对好了」；不是主人的丢掉；主人的先记下回复凭据、补发发件表，再把话交给管家（`orchestrator.Say`）。被引用的是农场发出去的某条消息时，话说在那条所在的频道或串里（比如它的工单串），否则说在连接器接的频道（没接就是默认频道）。引用查询失败时不交付、不改去别处，等恢复后重试。
3. 交付成功，标成已交付、清空正文，只留去重记录。没交付完的，重启后接着交。

**送出去的话**：哪些话出农场归[通知](docs/subsystems/notice.md)（`notice/rules.ts` 的 `forOwner`，经 `Notices.toOwner` 交给每个连接器的协调器），挑出主人要看的：说完了的，不是主人自己的；汇报和派活，管家的话，@主人 或 @所有人 的话；提示不送。只送连接器接的那个频道（和它下面的串）里的。`ownerLine` 加上「【谁 · 做完了 / 没做成 / 派活 / 在工单串里】」，Markdown 转成纯文本，按 UTF-16 长度切开（微信 1800、飞书 4000、QQ 2000，尽量在空行或换行处切），写进 `connector_outbox`；网络发送不阻塞读核心事件。

**发件表**（`voiceOutbox`）：每条马上发，按顺序，遇到发不出去的就停下。状态里的「还有几条没发」记在内存里：不知道时数一次库，此后加件、发出、作废的事务提交后跟着加减；事务失败或数的时候又变了，就回到不知道。发送期间新来的消息留下 dirty 标记，当前这轮结束后立即再查，不丢掉那次唤醒。拒收的（微信、QQ 的回复窗口，`restricted`）留着，30 秒后重试，每失败一次等待翻倍，最多半小时；发出去一条就从 30 秒重来。主人下次说话时先补发，积了 3 条以上就合成一条摘要（「你不在的时候有 N 条消息」，每条留头 60 个字），整批一起确认。飞书、QQ 拿到平台的消息 id 才算发成功。登录过期（`stale`）就暂停这个账号一小时，暂停写库或解除暂停失败时等待 30 秒再试，不密集轮询。收消息断了先等 2 秒重连，连着断 3 次等 30 秒。等待是服务的 Clock 上的 `Effect.sleep` 和一次唤醒赛跑，停下由纤程的中断收尾。

**登录和换账号**：

- 微信、飞书扫码，QQ 填机器人的 AppID 和 AppSecret（先验一次）。一次扫码由各自 SDK 走完：微信拿到二维码后最多等 8 分钟，跟随重定向的域，要输数字时页面显示输入框，二维码过期或验证码被禁用累计 3 次就结束；飞书按注册返回的间隔和有效期轮询，跟随租户跳到 Lark。连接器只把进度（等待扫码、扫过了、要输数字）给页面，成功后保存账号。每个连接器的状态（`ConnectorStatus`：进度、账号、错误、还有几条没发）在它的任何一部分可能变了的时候经 `connector` 事实写进核心状态的 `connectors`，一次一个，轮到时才读，所以最后写的是最新的；一样的不出新帧。页面的连接器页读核心状态，不轮询；`state.json` 不存它，开机由连接器重新说一遍。
- 每个账号同时只有一代任务：登录，或者接收、收件、发件三个工人，一代是服务作用域里的一条纤程，适配器的调用经它的 signal 停下。协调器（`voiceConnection`）不在任何一代里：重新登录或退出时，它先取消并等旧一代结束，再在一个事务里改 `connector_account`、清掉旧收件、退休旧发件（`dropped`），然后起新一代。保存失败就保留旧账号、重新起旧的那一代。SDK 在接收返回后回调的，不再收下；旧连接迟到的结果不写新账号。

## 和谁打交道

- **帮工（`session`）**：频道模块不 import 执行模块，也不读核心状态里的帮工。它定义帮工这类参与者的端口 `Helpers`（在不在地里、地里的帮工、交一句话、现在是哪一轮、汇报的摘要、一张工单现在谁在做），执行模块建的时候用 `useHelpers` 登记，并把每一轮的开口、结束、关掉、压缩上下文交给 `activity`，一轮实际读进去的消息交给 `consumed`，雇了、交回、走了交给 `sessionNews`（`SessionNews`，带着那一刻的 Session），据此开串、贴汇报、推进送达。帮工接回以后执行模块调 `helpersBack`：这时才给地里的每个帮工开好工单串、送出等着的话；接回以前它看不到帮工。
- **核心状态（`core`）**：频道模块施加 `message`、`channel` 事实；读 `WorkspaceState.Sessions` 知道谁在地里、谁在忙。
- **管家（`orchestrator`）**：订阅 `forOrchestrator`（叫醒它的话，按频道分批）和 `orchestratorDigest`（只让它知道的汇报）；用 `orchestratorSays` 说话、`spoken` 记下通话里的话。主人的话经 `orchestrator.Say` 进频道，管家照频道的规则被叫醒。
- **主人在串里的话**：`ownerInThread` 把主人在任何一个串里说完的话（不管经哪条路进来）告诉订阅的人；工单靠它知道主人在工单串里说了话。
- **工单（`issue`）**：带话、验收意见、冲突和检查失败经 `tellSession`；首次派活时记下频道（`channelOf`）。
- **定时（`recurrence`）、计划**：到点时用 `notice` 在频道里说一句再派活；派活工具按 `channelByName`、`channelOf` 取频道和它的默认项目。
- **工具（`tool`、`mcp`）**：管家和帮工的说话工具都调 `speak`、`read`、`Inbox`；`/mcp` 用每个会话自己的令牌认出是谁在说话，令牌只用来分清人，不用来防人。
- **语音（`voice`）**：电话里说的和回答经 `spoken` 留在默认频道，不叫醒谁，管家在电话里已经听过。
- **连接器 → 管家、频道**：收进来的话交给 `orchestrator.Say`；送出去的读核心事件里的 `message`，只读不改频道。主人在外面说话也让农场开门（通话状态成 `live`）。
- **通知（`notice`）**：@主人 的话进 Inbox；巡查的发现没有频道时归默认频道（[通知](docs/subsystems/notice.md)）。

## 为什么这样

- **人和 agent 在同一个群聊里，帮工自己说话。** 星形的对话里帮工的话全由管家转述，会丢细节、说错，主人也没法直接对帮工说话，帮工之间不能交接。照 Raft（botiverse 的人机协作工作区）做频道和串；派一件活开一个工单串，频道里每件活只占一条。
- **@ 和主人在工单串里的话才叫醒帮工，比 Raft 收得紧。** 放弃了「频道成员每条都收、都被叫醒」：Raft 的 agent 长驻，VibeValley 的帮工按工单开会话、按 token 花钱，频道里一句闲聊叫醒六个帮工就是六份钱。成员照样被动知道（忙的收提示、歇着的醒来看摘要），所以主人说「main 刚合了大改动」帮工也知道。
- **防 agent 来回靠结构上的闸，不靠礼节。** Raft 只靠提示词里的礼节，自己的手册承认关键时刻会失灵。来回上限、冷却和熔断不管模型守不守礼节都管用。`session_list` 的名单不带 @、规矩写明 @ 就是叫醒：真跑时帮工把带 @ 的名单原样抄进回答，一连叫醒了管家和别的帮工。
- **管家的回答整条发，不逐字长出来。** 群聊里一条消息是说完的一句话。逐字长的时候，每 120 毫秒改一次正文就是一条事实、一帧整份的核心状态；消息还多了「没说完」这种状态：要标 `final`、开机时把说到一半的补成说完，按消息号补齐时还得带版本。模型调工具之前说的话本来就是单独的一条，主人照样先看到「我看一下」；中间只显示管家在哪个频道里想、在写。看字一个个长出来的地方留在过程面板（执行的日志）和电话的语音线路。放弃了只在长回答时逐字：多长算长说不清，页面还要两种画法。
- **改、删、回应都推消息的整份现状，按修订号补齐。** 放弃了每种变化一种事件（改了、删了、加了回应）：页面要分别合并，补齐时要分别补；一种「这条消息现在的样子」加上一个修订号，补齐和实时是同一件事。回应存在消息上，没另开一张表：只有一个写入方，消息本来就整份推，读的时候不用再查一次。没先把状态帧和窄流并进这条连接（Discord 的 gateway）：聊天的每种变化都能经按频道的订阅续上；并成一条连接归[页面的连接接着带上在线状态和工单的增量](.agents/notes/proposed/architecture/2026-10-27-presence-and-entity-deltas.md)。没做「正在输入」：只有一个主人，没有别人看他打字，管家在想、在写已经在核心状态里。
- **附件是唯一的 GET。** `<img src>` 发不了 POST；文件按内容的哈希命名、不会变，可以一直缓存。
- **消息不跟着状态帧，按频道订阅。** 消息在核心状态里的时候，任何一条事实都把整份状态连同最近 300 条消息推一遍；一个热闹的串把别处的消息挤出状态，页面再拿 `channel.message.list` 补、两份合并；页面只拿得到「最近的」，断线回来只能重拿一整帧；页面对 SSE 的数据也不解码。#119 以后消息写下就不再改，每个频道的号码就是游标。用 Effect RPC：契约一份，两头照 Schema 解码；流式调用中断就是退订；socket 协议带心跳、按退避重连和流的回执，页面只管带着号码重新订阅。代价是页面多带 Effect（主包 gzip 后多约 53 KB），只在 `base/gateway.ts` 用。放弃了照 socket.io 自己写加入、离开、回执、重连；放弃了消息留在核心状态里、只是不进状态帧（帧和状态成了两种形状，服务端多存没人读的消息）；放弃了只把帧缩小、看到号码变大再用 HTTP 拉（多一个来回，设备多了还是要订阅）。
- **用帮工的 id 来 @，不用名字。** 名字有空格、紧跟中文会被吞进去，都会 @ 错人；id 是稳定的，页面上显示名字。
- **串跟着工单，不跟着帮工。** 原来工单串按派出去的 Session 开，重开、换帮工就另开一个串，同一张工单的话散在几个串里，新帮工和主人都要去翻旧串；叫「工单串」，`subject_id` 却是 Session，帮工走了界面上只剩 id。放弃了「重开时把旧串的 `subject_id` 改成新帮工」：串仍然是帮工的，取消后重开要挪串，挪的那一刻谁听得见说不清。也放弃了「串上存一列主人」：现在谁在干这张工单核心状态里已经有，存一份就要在换人时同步，违反核心状态只有一份。
- **最后的汇报自动贴出，`channel_message_send` 只用于一轮中间。** 放弃了「只经工具说话」：帮工本来就用最后一段话汇报，每轮多调一次工具，模型容易忘。
- **帮工的工具走会话级的 MCP，不给命令行。** pi、claude、codex 都接受会话级 MCP，工具有类型，不用处理 shell 引号和多行中文；不接受 MCP 的农机再补命令行。管家跑在服务端进程里，不绕 HTTP 调 `channel_message_send`：它的话直接写进频道。
- **交给它不等于它看到了，开口才算。** 帮工会在任何时候死掉（登录失效、进程崩溃、重启）；不记下交到哪一步，消息要么丢、要么不知道该不该重发。新鲜度拦截、防发错地方、压缩时不插话、只提示一次也照 Raft，因为两个帮工被同时 @ 会抢着答，插话会占上下文。草稿不存：工具调用时模型手里有原文。
- **聊天记录存 SQLite，一个写入方。** 一条消息要同时改消息、@、投递、跟帖、已读，还要按游标翻页、按人查未读，用文件得自己保证一致。只有一个写入方，`number` 的先后就是提交的先后，Raft 为多写入方做的「稳定窗口」和守护进程确认协议都省了。
- **频道是安排活的地方，可以带默认项目。** Raft 的频道和代码仓库没关系；VibeValley 的帮工按工单在项目的 worktree 里干，频道带个默认项目，在那里派的活不说项目也知道去哪。
- **默认频道是标记，不是类型、不是名字。** 原来默认频道是一种类型（`general`），名字「田头」写进了给模型的地址，发消息不写频道就算它：每个分支多一种类型，换语言、换名字就认不出。它和别的频道只差「没写频道的话去哪」这一点，像 Discord 服务器的 `system_channel_id`。放弃了只存一个默认频道的 id 在设置里：和频道分开存，删频道、换默认时要两处一起改。
- **私聊是一种 channel，不是只有两个人的频道。** 只有两个人的频道里还要另设「不收 @、不让帮工进、不放活」；私聊的规则本来就是这几条，照 Discord 的 `DM` 单列一种。一个对面一个私聊，由库的唯一约束管，不靠调用方先查。帮工的 `talk` 串不改成和帮工的私聊：帮工是一次派活，活完就走，它的串挂在派活消息下面，读得出派的是什么；私聊的对面是常在的一方：一个管家，或一个帮工的档案。
- **和档案私聊靠一张藏起来的工单，不另开一种执行。** 每次执行都挂一张工单：串、叫醒、交回、清掉改动、收工都是工单和执行已有的；私聊的执行只是「这张工单的串恰好是私聊」。放弃了让私聊的执行改代码：私聊没有分支和改动清单，改了就绕过「主人看过才合」，所以它只读，每轮清掉，要改就记成工单。放弃了不占名额：一直歇着的执行也占着 runtime 的额度和这台电脑的资源，所以闲 10 分钟就收工，下次带着最近的几条重新派。群私聊不做：几个人一起说话就是开一个频道。
- **提醒分三档，照 Discord。** 一个开关说不清「只在 @ 我时」；`none` 同时管未读、Inbox 和连接器，主人静音一处就是那里什么都不来找他。
- **链接预览由服务端读。** 浏览器跨域读不了别的网站的页；服务端读是它第一次主动连一个别人给的地址，所以限住公网、http(s)、时间和大小，不带凭据。预览里的图由页面直接从它的网站读（不经服务端转），那个网站看得到主人的地址。
- **草稿记在这台设备上。** 字、回复哪条、传上去的附件存在 `localStorage`：刷新、关掉再开都还在；换一台设备不带过去，草稿本来就是这只手上的事。
- **外部渠道是频道的门，不是另一个 agent。** 放弃了用 nanobot 当外壳：它有自己的 agent 循环、记性和子 agent，会和管家、帮工、频道的投递重复成两套，核心状态也不再只有一份。一个桥、三个适配器：账号、只认主人、配对、发件表、补发和摘要在桥里，适配器只管登录、收、发，再接一家只写一个适配器。主人把一个连接器接到一个频道上，一对一；每个外部会话自动开频道，群一多频道就乱。
- **只走出站连接，只认主人，只用官方接口。** webhook 要公网地址，违背「服务端只听 127.0.0.1」。帮工没有权限确认、能在这台机器上跑命令，聊天账号能派活就等于能控制这台机器，所以只认配对过的主人。飞书、QQ 拿不准主人是谁，用配对码，比让主人去找自己在平台上的 id 好用。不用 NapCat 这类非官方客户端：会封号，也等于把登录交给第三方。
- **先当平台能主动发，发不出去再退避。** 每条马上发，微信、飞书在主人没说话时也能送到；QQ 只能在主人说话后的窗口里回，拒收的进发件表，主人下次说话时补发。
- **收件先落盘再交给管家，至少一次。** 内存队列救不回飞书已经确认的消息，也挡不住旧账号的迟到回调。SQLite 的事务不能和管家的工具副作用合成一个事务，先记完成再交付会永久丢指令，先落盘再交付只在一个极窄的窗口里可能重复；所以不声称恰好一次。
- **账号由一个不在任何一代里的协调器换。** 给任务表加 WaitGroup 不行：登录任务本身会触发换账号，等任务表就会等自己。协调器把「结束旧任务」和「发布新账号」的顺序收在一个主人手里。
- **一次扫码登录由平台的 SDK 拥有。** 二维码、重定向域、期限、刷新次数、验证码、轮询间隔、Feishu 到 Lark 的跳转都是平台协议，放在 SDK 里，连接器不碰中间状态。放弃了三家共用一个可配置的登录状态机：QQ 用密钥，微信要验证码和刷新，飞书按租户域轮询，统一起来只会把差异变成更多配置。
