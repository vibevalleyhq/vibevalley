# 工单

一件活从写下到关上是一张工单（`Issue`），农场里是一块地。代码相关的工单带一个 worktree 和一条分支；帮工（Session）在这块地上干活，可以换人，地不换。工单按三段走：**聊清楚**、**安排活**、**完成**；聊清楚是起草：主人写一句想做什么，帮工读过代码把它写成固定格式的草稿（标题、说明、验收标准）；每张工单都有一道验收，照验收标准验，过了才算结果。对主人，工单只有一套状态（「给主人看的状态」）：草稿、排队、在做、等你回答、等你验收、卡住了、收获了、关了，看板、农场和工单页都说这一套。

## 管什么，不管什么

| 管 | 不管（谁管） |
|---|---|
| 工单的模型、状态和能挪到哪 | 帮工怎么跑一轮、事件日志（[帮工](docs/subsystems/session.md)） |
| 起草：派谁起草、交给它的规矩、读回草稿写进工单、起草完重置 worktree | worktree 的重置和清理怎么做（`project.Reset`、`project.Clear`） |
| 派活、排队、重开、取消 | 挑哪个档案（[管家](docs/subsystems/manager.md)） |
| 验收、草、缺肥、帮工对每条标准的自评 | 汇报怎么读（`session/rules.ts` 读出「结论：」「要问主人：」和「标准 N：」交给它） |
| 收获：查冲突、跑检查、本地合或提 PR | 项目和工作目录、worktree 的 git 操作（`project`，[项目](docs/subsystems/project.md)） |
| 给主人看的状态和主人能做的事；工单的时间线 | 怎么画（[farm-ui.md](docs/reference/farm-ui.md)「地里长什么」和工单详情、`apps/web/src/rules/issueState.ts`） |
| | 种植计划里的工单（跟着计划走，[种植计划](docs/subsystems/task.md)）；派给管家的工单（管家答完等主人点头） |

## 在哪

- 服务端 `apps/server/src/issue`（`Issues`）：`issue.ts` 存取和核心状态、挪状态、派活和重开、排队、带话和取消、验收和缺肥、执行历史、派给管家的工单；`draft.ts` 起草（谁来起草、交回来的草稿怎么读进工单，和派活时挑哪个档案 `pickAgent`）；`harvest.ts` 收获（本地合或提 PR、合不进去怎么说、PR 的轮询）；`rules.ts` 是只有工单用的纯规则。worktree、检查、推送和 `gh` 的 git 操作在 `apps/server/src/project`。
- 只有服务端跑的规则在 `apps/server/src/issue`：`state.ts` 的 `issueStatusOf`（状态怎么算）、`issueDraftingOf`（谁在起草）、`withIssue`、`withIssueStatuses`、`issueOrder`、`keepClosedIssues`、`isForManager`、`openFindings`，`attention.ts` 的 `attentionOf`（给主人看的状态和能做的事）和 `attentionIn`，`moves.ts` 的 `statusMove`、`statusMoves`（能挪到哪、挪了做什么），`rules.ts` 的 `conflictBrief` 和只有工单用的规则（`cureWords`、`resumeWords` 动作带给帮工的话，`findingsOf` 打回的意见，`draftBrief` 起草的规矩、`parseDraft` 读草稿、`draftDescription` 拼说明、`issueJob` 交给帮工的活、`splitJob` 一句话拆成标题和说明、`milestonesOf` 时间线）；地的样子（`plotOf`）在 `apps/server/src/game/view.ts`。服务端和页面都要的留在 `packages/protocol/src/rules`：`issues.ts` 的 `shortTitle`（一行的标题），`attention.ts` 的 `attentionLabel`、`actLabel`（每个动作叫什么）、`attentionWantsOwner`。
- 表：`issue`（一张工单一行；验收标准在 `criteria`、帮工的问题在 `questions`、它对每条标准的自评在 `checks`，都是 JSON 数组）、`issue_session`（哪些 Session 干过它）、`issue_queue`（排队的上下文）。
- 接口：`issue.*`（[capabilities.md](docs/reference/capabilities.md)），起草是 `issue.draft`（`POST /api/v1/issues/{id}/draft`），时间线是 `issue.timeline`；命令行 `vibevalley issue …`。
- 页面：工作台的看板在 `apps/web/src/pages/issues`，备选工单的草稿详情是 `TodoDetail.tsx`，派出去以后的详情是 `IssueDetail.tsx`，把服务端的状态说成话的规则在 `apps/web/src/rules/issueState.ts`；农场照同一份规则画 `farm/issue/IssueView.tsx`；农场的播种袋在 `farm/panels/SeedForms.tsx`。

## 模型和不变量

- **一张工单一个 id**，从写下到关上不变；重开是同一张工单的下一个帮工，不是新工单。
- **状态六个**，和 Linear 一样：`backlog`、`todo`、`in_progress`、`in_review`、`done`、`canceled`。只存主人的意思（排没排上队 `queued_at`、怎么关的 `closed`），帮工那一半（在做、交回来了）从核心状态里帮工的阶段算，不另存一份。
- **数据库是家，核心状态有一份**：开着的和最近关的 50 家在 `WorkspaceState.issues`，`Issues` 每改一次库就施加一条 `issue` 事实；页面只读核心状态。
- **主人只挪到 `backlog`、`todo`、`done`、`canceled`**；`in_progress`、`in_review` 是帮工干出来的。每张工单的 `moves`（能挪到哪）和 `attention.acts`（能做什么）是同一张表的两面，都在 reduce 里和状态一起算（`withIssueStatuses`）：帮工这一轮一结束，看板、地块详情、命令行读到的就是新的，不等服务端再发布这张工单；服务端的拒绝调同一个 `statusMove`。
- **动作是服务端的**（`issue.act`，`Issues.act`）：站位给出的每个动作（开工、回答、验收通过、打回、收获、知道了、让它解决冲突、接着做、接着修、带话、叫停、关上、重开）在服务端只有一份实现，带给帮工的话也在这里拼；站位没给的动作拒绝（「#41 现在不能「接着修」：它在做」）。页面只收集要说的话、先开收获清单和关单对话框；命令行的 `issue act` 和管家的工具走同一个入口。
- **工单认编号**（`Issues.idOf`）：接口里的工单可以写 `#41`、`41`、工单 id 或干过它的帮工 id；命令行、管家的工具都用编号。
- **一块地最多一个 worktree**：代码活的分支是 `vibevalley/issue-<号>`，worktree 是 `worktrees/<项目>.<号>`；重开、换帮工、重启都还是这一块。
- **每张工单都有验收**：`in_review` 就是「等验收」。`acceptance` 是 `glance`（收获本身就算验收）或 `required`（没通过 `acceptedAt` 以前不能收获）。
- **种植计划里的工单 `moves` 是空的**，验收和挪状态都拒绝。
- **已完成只由主人点头。** 一轮怎么结束的（`completed`、`failed`、`interrupted`）只决定工单停在哪、请主人做什么，不决定活成没成：帮工最后一轮没做成（站位「卡住了」，`stuck: failed`）时 `moves` 里没有已完成，`statusMove` 和 `merge` 都拒绝，看板、命令行、管家的工具一样；叫停的一轮还能收。
- **派给管家的工单**：管家在答时 `in_progress`；这一轮结束，不管怎么结束，结局记在 `handedBack`（`{ at, outcome }`，表的 `handed_back`）、工单进 `in_review`。答完了（`completed`）主人能挪到已完成（关成 `answered`，页面上是「知道了」）或已取消（`dismissed`）；没答成只能挪到已取消。再交给管家（定时又到点、重开）清掉 `handedBack`。服务端开机时只把还在答的关成 `lost`，等你看的留着；接着做的那一轮结束时，`lost` 的工单重新打开、记下结局。
- **子工单**带 `parent`、`blockedBy`：种植计划用它，计划里的工单跟着计划走，看板不能单独开工、重开。
- **还没派的能改、能删、能排先后**；派出去以后只能改验收方式。交给帮工的是标题，空一行，再是说明，最后是编了号的验收标准，要它交活时逐条写「标准 N：做到了｜没做到｜不确定」和凭据（`issueJob`）。
- **备选的工单是草稿**：起草的帮工（`Session.draft`）只为写这张工单来，不是工单的帮工：不进 `issue_session`，`Issue.Sessions` 一直是空的，工单一直在 `backlog`。谁在起草（`Issue.drafting`）和状态一样从核心状态里的帮工现算，不另存；起草时不能开工（`moves` 里没有待办，`ready` 也拒绝），一张工单同时只有一个起草的。
- **验收标准**（`Issue.criteria`）：一条一个主人能照着验的点。草稿写它，主人在派出去以前用 `issue.update` 改（给一个空列表就是清掉），派活时编好号写在活的最后；验收时详情把它逐条列出来。
- **帮工的自评**（`Issue.checks`）：汇报里「标准 N：做到了 —— 凭据」这样的行（`checksOf`，N 从 1 数，同一条以最后一行为准），存成 `{ criterion, result, proof }`，`criterion` 是 `criteria` 里的下标；最近一次带了自评的汇报算数，重开时清掉。帮工不写就没有，页面只列标准。
- **标题一行**：主人写的一句话直接成为工单时（`splitJob`），第一行太长就取它的第一句、放不下就到最后一个停顿（`shortTitle`，40 个字以内），整段放进说明；起草的标题要求 20 个字以内。
- **排队的上下文和排队一起提交**：首次派发的频道和 `RunTrigger`（定时的 id、是不是补跑）写进 `issue_queue`，和 `issue.queued_at` 同一个事务；重试照它恢复来源，开工成功时同一个事务清掉。

## 怎么走

**三段和状态**：

| 段 | 状态 | 地里 |
|---|---|---|
| 聊清楚 | `backlog`（草稿，可能正在起草）；帮工问了主人还没答是「缺肥」（`questions`） | 荒地；缺肥是干裂 |
| 安排活 | `todo`（种子袋，排队等空地）→ `in_progress` | 播种、发芽、长叶；验收没过修的时候是「除草中」 |
| 完成 | `in_review`（等验收）→ 验收过了 → `done` | 开花；没过是杂草（一条意见一棵）；过了结果；收获后是麦茬 |

**挪状态就是派活**（`issue.status`，转换表在 `apps/server/src/issue/moves.ts` 的 `statusMove`）：

| 挪到 | 从 | 做的事 |
|---|---|---|
| 待办 | 备选 | 派给档案；地都占满了就在待办排队，服务端每 5 秒按先后试一遍 |
| 待办 | 等验收 | 带一句话（必填）再干一轮 |
| 待办 | 已完成、已取消（派过的） | 重开：同一个档案派一个新帮工，告诉它原来要做什么、上次怎么关的、分支上有没有上次的提交 |
| 备选 | 待办；没派过就取消的 | 不排了；挪回备选 |
| 已完成 | 等验收 | 收获（见下）；`required` 且没通过、或最后一轮没做成时不在 `moves` 里 |
| 已取消 | 在做、等验收；备选、待办 | 叫帮工回家，或没派过的直接关上；分支上有提交就留着 |

**起草**（`issue.draft`，带主人的一句话；工单有没答的问题时这句话就是回答）：

1. 加号直接建一张备选工单（`issue.create`），主人那一句是标题，还没说时标题是「新工单」；带着话就马上起草。只有在备选里、没派过、没在起草的能起草，派给管家的不能。
2. 谁起草：工单的 `assignee`；没有就是这个项目上次派出去干活的档案（还能派的话，`issue_session` 里最近的那张工单的 `assignee`）；再没有按 `chooseAgent` 挑。项目是工单的，没有就用档案的工作目录，都没有就拒绝。没写的项目和帮工填成这一次的，主人的第一句话写成标题（还没有说明和验收标准时）；回答问题时 `questions` 先清掉。
3. 在这张工单自己的 worktree 里起草（`project.Workplace` 按工单开，和后面干活是同一块；档案关了 worktree 也照样开），Run 的触发是 `draft`，花费记在这张工单的 run 上。交给它的活（`draftBrief`）：只读代码，不改文件、不提交；拿不准的写「要问主人：」，想得到的回答写在句末「（选项：A｜B）」；`title` 20 个字以内；最后用一个 json 代码块交草稿：`title`、`why`、`todo`、`criteria`、`notDoing`、`files`（列表也可以是一句话）。再起草时附上现在的草稿（主人改过的算数）和上一版的问题、主人的回答或这次的话。
4. 交回来：读最后一个能读的代码块（`parseDraft`），写回工单：`title`，`description` 用固定的小标题拼（为什么、要做的、不做的、可能涉及，空的不写），`criteria`，问题照旧进 `questions`（缺肥）；一次写，第二版整个盖过第一版。读不出来、没做成、被叫停，工单不动，工单串里说一句（串还没开就是一条提醒）。然后把 worktree 重置回主分支（`project.Reset`：`checkout -f -B <工单分支> <主分支>`、`git clean -fd`，提交了也清掉），帮工收工；干净的 worktree 和空分支随收工清掉。
5. 主人改各栏、回答问题再起草，满意了挪到待办开工；没开工就取消或删掉的，在起草的帮工收工，`project.Clear` 清掉起草留下的 worktree 和没有提交的分支。

**排队的待办马上开工**（`issue.dispatch`，待办详情的「现在就试」）：只收排着队的待办；有空就照它排队时记下的来源开工，没空就留在队里原来的位置、说为什么，不重新排。和后台每 5 秒的重试共用一把锁，不会派两次。

**验收**（`issue.accept`）：通过记下 `acceptedAt`，原来的草都拔掉；没过至少一条意见，每条记成一棵草，还没拔的草编号写成一句话交给帮工再修一轮。新的一轮开始（带话、再干一轮）验收作废，草留着，下一次通过才拔。

**主人的话从一处进工单**：主人的话不管从哪来（`issue.comment`、在工单串里 `channel.say`、连接器、农场替主人说的冲突和检查没过），写进工单串就有一条带 `thread` 的 `message` 事实，工单服务订阅田头的 `ownerInThread`：清掉 `questions`，作废验收。帮工没有串时 `issue.comment` 直接送到帮工、没有事实，`comment` 自己做这两步。关上的工单不动。农场替主人说的话也算：冲突解决、检查没过修好以后是新的一轮代码，`acceptance: required` 的工单要再验收一次才能收获。管家用 `accept` 工具也能验，收获照旧要主人说一声。

**缺肥**：帮工汇报里「要问主人：」开头的行，`readReport` 读出来放进 `report` 事实的 `questions`，工单服务记到 `questions`（`{ question, options? }`：句末「（选项：A｜B）」是它想到的回答，少于两个就不算选项）；主人在工单串里说一句就算回答，点一个选项就是把这句原样说出去，问题清掉。

**给主人看的状态**（`Issue.attention`，`attentionOf`）：从 `status`、帮工的阶段、`questions`、冲突、上一轮的结果和验收算出来，`issueOf` 读工单时和核心状态折事实时（`withIssueStatuses`）都填，页面不自己拼。每种状态带开始的时间（`since`），和主人能做的事（`acts`），其中最多一件是主动作（`lead`）：

| 状态 | 什么时候 | 主动作 |
|---|---|---|
| 草稿 `draft` | `backlog`；正在起草时没有动作 | 开工 |
| 排队 `queued` | `todo`，或计划里还没轮到的一步 | 无（可以关上） |
| 在做 `working` | 帮工在干活 | 无（可以带话、叫停、关上） |
| 等你回答 `asking` | 交回来了，有 `questions` | 回答 |
| 等你验收 `reviewing` | 交回来了；`required` 没验过时先验收通过，其余直接收获 | 验收通过 / 收获；可以打回 |
| 卡住了 `stuck` | 冲突（`conflict`）、没做成（`failed`）、停在半路（`interrupted`）、很久没动静（`quiet`） | 让它解决冲突 / 接着修 / 接着做 / 叫停 |
| 收获了 `harvested` | `done` | 无（可以重开） |
| 关了 `closed` | `canceled` | 重开 |

冲突排在问题前面，问题排在没做成前面。种植计划里的工单有状态、没有动作：在计划那边操作。派给管家的工单答完了是「等你看」（主动作「知道了」，还能「关上」），没答成是「卡住了」（只能「关上」）。每种组合钉在 `apps/server/src/core/testdata/rules.jsonl.gz`（`attentionOf`）。

**时间线**（`issue.timeline`，`milestonesOf`）：从已经存着的事实拼，不另存：开单；每次干活的开始（开工、你带了话、重开、定时、起草）和结束（交回来了、问你、没做成、停在了半路、起草好了）；打回（同一时刻的意见合成一条）；验收通过；关单。新的在上，带时间和是哪个帮工；同时给出所有干活加起来花了多少（`spent`）。

**收获**（挪到已完成）：

1. 还在干的不收；关掉会话，没提交的改动替它提交（缓存和依赖目录不提交）。
2. 会冲突就不合：标上 `conflict`，「让它解决冲突」发一句固定的话（`conflictTask`）交回帮工，在自己的分支上把主分支合进来，下一轮结束时再查。
3. 跑项目的检查：帮工分支上的 `.vibevalley/check`，在 worktree 根目录、项目锁外跑，没有这个文件就跳过；本地合的先把主分支合进帮工分支再检查，PR 和种植计划检查帮工当前的分支。退出码非 0、跑不起来或超时（`project.check_timeout_seconds`，默认 1200）都不合，输出的最后 40 行附在拒绝里交给帮工修。工单留在 `in_review`，帮工、分支、worktree 都在。
4. 进锁以后确认分支没在检查后变过、重新查一次冲突、主分支没有没检查过的提交，才合：
   - **本地合**（项目不在 `github.pr_projects` 里，或 `pullRequest.available` 为假）：合进项目克隆的主分支，删掉 worktree 和分支，帮工离开，账本记 `harvested`。
   - **提 PR**：农场 `git push -u origin <工单分支>`，用工单标题、编号、帮工最后一轮的「结论：」那一段（找不到就放最后一轮原话）和检查结果开 PR；已有开着的 PR 只推分支，开完没存下回执的重试先查已有的 PR。推送或 `gh` 失败就拒绝这次收获。`pullRequest` 记 `url`、`number`、`state`；PR 开着时工单留在等验收，再干一轮再收获更新同一个 PR。

**PR 的结局**：农场每 `github.pr_poll_seconds` 秒（默认 180，`github refresh` 手动）查开着的 PR：合了关成 `merged`、没合就关掉关成 `dismissed`，清掉 worktree 和本地分支，帮工离开；帮工还在干或有待开始的一轮就留着现场，下次再结。远端分支归 GitHub。开新分支或结束 PR 前先 `git fetch origin <主分支>` 快进本地主分支，不干净或不能快进就保留本地的、记日志。

**收工**：关掉会话、帮工离开；分支上有没合的提交就留着，重开接着做。

## 和谁打交道

- **帮工（`session`）**：派活经 `Sessions.send` 开一个 Session，起草的带 `HireOptions.draft`、不记关联，它的汇报由工单服务读成草稿；帮工离开（`left`）时，离开的是最后一个就关上工单；汇报（`report`）带来缺肥的问题。
- **项目（`project`）**：worktree、分支、冲突预检（`git merge-tree`，不碰工作区）、检查和合并、推送和 `gh`、起草后的重置（`reset`）和取消时的清理（`clear`）；工单服务只决定什么时候做。
- **田头（`channel`）**：派活时在频道里开工单串，一张工单一个串，重开、换帮工都在这个串里（[田头](docs/subsystems/channel.md)）；带话和验收没过的意见经它交给帮工。
- **定时（`recurrence`）**：一个定时一张工单，到点是它的一次干活（[定时](docs/subsystems/recurrence.md)）。
- **种植计划（`task`）**：计划是带 `graph` 的父工单，每一件是带 `task` 的子工单，跟着计划走，不归这里的转换表。
- **管家（`tool`）**：派活、带话、验收、收获都是同一个服务的方法，收获要主人说一声。
- **GitHub 检测（`setting`、`project`）**：开机查 `gh` 装没装、登没登录（`github.status`、`github.refresh`），项目查 origin 是不是 GitHub、有没有写权限，结果缓存在 `project.pullRequest`；收获只读缓存决定走哪条路。
- **农场的皮（`plotOf`、`game`）**：`FarmView.plots` 按工单做键（`plotKey`），地的样子看工单和地上帮工的阶段；农具直接调 `issue.status`、`issue.comment`、`issue.accept`，不经帮工找工单；仓库是关成 `merged` 的工单。游戏只读事实算画面和账本，不调工单。

## 为什么这样

- **工单是服务端的一样东西，帮工挂在它下面。** 原来「工单」是页面从帮工的轨迹拼出来的，重开换 id、几台设备各看各的。放弃了「接回原来的会话来重开」：分支合了、会话可能过期，新派一个帮工、把该知道的写给它，任何一种关法都能用。叫 `Issue` 不叫 `ticket`，和 Linear、GitHub、Multica 一致，界面上叫工单。
- **状态只存主人的意思，帮工那一半现算。** 存一份完整的状态，帮工半路死掉、农场重启时都要对一遍，违反「核心状态只有一份」；现算的话帮工离开，工单自己回到主人定的那一列。
- **挪状态就是派活，一个接口 `issue.status`。** 原来是 start、unqueue、merge、cancel、reopen 五个动作，主人看到的是列、要做的是动作；看板、命令行、管家都得记哪个动作挪到哪。放弃了「只在拖卡片时翻译成动作」：只有页面受益，规则写在页面里。in_progress 不让主人挪进去：和挪到待办只差没空地时怎么办，多一个入口没换来什么。
- **一块地是一张工单，不是帮工的位置。** 地跟着帮工走时，重开的工单换地、地块详情和工单详情两页、工具要先找帮工再找工单。也没选「地是 worktree」：主人派的、看的、收的都是工单，worktree 只是代码活的一部分。
- **已完成只由主人点头，不由一轮的结局推出来。** 原来管家的工单一轮跑完（`completed`）就关成已完成，可管家说一句「没查到」也是 `completed`；帮工的工单最后一轮没做成，页面藏了收获键，服务端却照样能收，`glance` 的收获又算验收。两处都是拿「这一轮没崩」当成「活干成了」。放弃了「只把失败的留下，答完的照旧自动关」：答没答上，runtime 判断不了；也没让管家用工具自己报结局，那是把规则交回模型。代价是每天的定时汇报这样的管家工单要主人点一下才关；定时下次到点接着用同一张，不会越积越多。
- **每张工单都有验收，`in_review` 收窄成「等验收」。** 没有这一关，「交回来」和「做完了」分不开，地的阶段也没法标；没加新状态，因为它和 `in_review` 是同一件事。缺肥从帮工汇报里固定的一行读，不让管家读工单串去判：帮工最清楚自己缺什么，固定的开头读得准，不调模型。草整批拔：汇报里读不准修了哪几条，下一次通过就都拔。
- **对主人只有一套状态，由服务端算。** 原来工单的六个状态、帮工的阶段、页面的三段进度和标签各说各的，没有一套说「卡在谁身上」：帮工问了问题、一行没改，进度条停在「完成」，主按钮是收获。改成从这几处事实算一套给主人看的状态和唯一的主动作，放在 protocol 里、用黄金数据钉住每种组合：算错了比没有更误导。没把它存进库：它全是现算的，存一份就要对一份。放弃了照搬 Linear 的工单页（标题、描述、属性栏、评论流）：这里是 agent 在做，主人要知道的是卡没卡、要不要我、做到了没有、交出了什么，评论流答不了这些。
- **聊清楚是起草：主人写一句，帮工照格式写成工单。** 主人想说的只是「看板拖卡还在调旧接口」；要做什么、怎么算做完、碰哪些文件，是读过代码的人才写得出来的，工单写得粗，验收也没有依据。放弃了让管家起草：管家只看得到农场的状态，读不了代码，写不出要碰哪些文件、怎么验收。草稿交回来直接填进工单，不让主人再点「填进工单」：主人随时能改每一栏，多一步确认没换来什么。加号写了一句话就马上起草，不另等主人点按钮：主人写这句话要的就是一张写好的工单；代价是每张都花钱，花费记在工单上，以后可以加「不起草，直接写」。
- **起草在工单自己的 worktree 里，交回来就重置。** 在项目的主检出里只读起草不用开 worktree，快；可「只读」只能写在提示里，帮工改了文件就改在主人的主分支上。用工单自己的 worktree，交回来 `checkout -f -B` 回主分支、`clean -fd`，改了什么、提交了什么都不出这张工单，开工时从主分支起步。
- **起草的帮工不是工单的帮工，「正在起草」现算。** 记进 `issue_session` 的话，状态就从帮工算成处理中、等你看，还会被「最后一个帮工离开就关单」关上；另存一个「起草中」又是第二份状态。只标在 Session 上（`draft`），工单从核心状态里认出它，帮工离开就自己没了。起草的规矩和读草稿只有工单用，放在 `issue/rules.ts`，不放进 `session/rules.ts`。
- **一张工单一条分支、一个 worktree，跟着工单不跟着帮工。** 按帮工开时，取消后重开的帮工不在原来的分支上接着干，旧 worktree 还会留着，一张工单两个 worktree。约束放进 `project.Workplace`：按工单开，有就复用，不靠调用方记着。
- **合并在不碰工作区的地方预检，冲突交回帮工。** 遇到冲突再中止要碰主人的工作区；冲突交给主人在终端里解决，不如让最清楚改动的帮工解决、跑测试、说清怎么取舍。
- **检查写在仓库里（`.vibevalley/check`），在锁外跑。** 写在项目设置里会和代码分开，帮工也看不见合并时跑什么。在锁里跑会让同一个项目几分钟开不了新 worktree；锁外跑、进锁再核对分支没变。
- **能提 PR 的项目一律提 PR，开关 `github.pr_projects`。** 本地合和提 PR 都可选会有两套状态，主分支有时在本地动、有时在 GitHub 上动，农场的克隆和 origin 迟早分叉。帮工自己不 push：推送和开 PR 留给农场，帮工照旧只在工作目录里提交。
