# 性能优化验证清单（Benchmark Checklist）

专治凭直觉猜测的伪性能优化（适用切片读放大、数据库慢查询、构建提速、渲染卡顿等专项）。没有测量基线、瓶颈资源指认和可重复 A/B 数据，不接受「更快」的宣称。

## 1. 必答 `Why not double?`（指认真实瓶颈资源）

动代码前，先用真实 profiler、耗时计数或指令采样（`cargo nextest` 计时、`tracing` span、SQLite `EXPLAIN QUERY PLAN`、`sccache --show-stats`、`dtrace`/Instruments）回答：**如果把当前实现再提速一倍，第一道卡住它的物理瓶颈资源是什么？**

- 瓶颈必须落到可观测资源（CPU 热点函数、SQLite 锁/全表扫描、JSON 序列化分配、磁盘 fsync、跨桥复制、Cargo 重建单元）。
- 仅凭看源码猜测「这里分配太多」而不量出占比，不算定位瓶颈。

## 2. 7 句性能口诀（从最便宜处试起）

按下面顺序逐级排查，前面能解决就不做后面的微调：

1. **不做无用功**：整段工作能不能直接删掉或靠缓存/去重完全跳过？
2. **不重复做**：循环里或高频路径上有没有重复解析、重复查库、重复构建同一对象？
3. **少做**：能不能缩减扫描范围、字段集合、序列化体积或触发频次（如按脏切片而非全量广播）？
4. **延后做**：启动或首帧不需要的计算，能不能推迟到首次访问时惰性执行？
5. **后台做**：重计算、磁盘读取、高亮与渲染能不能离 UI / 异步主线程卸载到后台？
6. **并发做**：互不依赖的 I/O 或纯计算能不能并行批处理（避开锁竞争与并发 `cargo`）？
7. **最后才优化单次成本**：确认前 6 步已挖尽后，再做数据结构微调、零拷贝或算法替换。

## 3. A/B 双边对比纪律

1. **同配置 release 交替测量**：Baseline（A）与 Candidate（B）必须在相同构建配置（优先 `--release`）与相同数据集下**交替运行至少 5 轮**（`A → B → A → B → ...`），排除冷缓存和温控漂移。
2. **报告中位数与波动区间**：记录每轮读数、中位数（p50）与最小–最大波动区间（或 IQR），不挑最好的一次报喜。
3. **核算阿姆达尔上限与错误计数**：给出被优化部分占总耗时的比例及理论加速上限（`S = 1 / ((1 - p) + p / s)`），并同时报告失败/超时/错误计数（确保提速不是靠跳过工作或引入静默失败换来的）。
4. **结构化落库**：把每轮测量数据写入 `NoteType::Base` 实验台账（用 `formula` 列自动算净降幅），在工单或 PR 正文用 `kpi` / `chart` 块呈现前后中位数，原始输出收进 `toggle`（`collapsed: true`）。
