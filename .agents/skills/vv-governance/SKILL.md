# 用白皮书的眼光看这个仓库

白皮书的判断是：代码由 agent 写以后，写代码不再稀缺，稀缺的是架构的一致、契约的完备和主人的注意力；挡问题要按成本从低到高，能用编译器和检查挡的不花模型和人。这和根目录 [AGENTS.md](AGENTS.md#怎么让-agent-做对) 的四层手段是同一个原则。

**本 skill 不是规矩的家。** 规矩在 `AGENTS.md`、`docs/` 和各包的 README，和白皮书说法不同时照它们。白皮书是为一个通用的、多人的仓库写的（`src/contracts`、`src/features`、`bun`、ast-grep、300 行上限），每一条在这里的处境见 [whitepaper.md](.agents/skills/vv-governance/whitepaper.md)：已有（在哪）、已做（在哪）、以后做（什么时候）、不做（为什么）。用到一条时先查它在那里的处境，不照白皮书的原样做。

## 1. 加一条规矩或一个检查

1. 先说清它挡的是哪一类问题，对上六种病里的哪一种（[whitepaper.md](.agents/skills/vv-governance/whitepaper.md#六种病)）。说不出一类、只是一次的事，不立规矩。
2. 按顺序选手段，能用前面的就不用后面的：代码（类型、结构、边界，把这一类整个消掉）→ 检查（lint、测试、CI、棘轮）→ 文字（规矩、skill）→ 人看。白皮书的「机器能拦的不花 token」就是这条。
3. 写成检查时，失败的话写三样：错在哪和为什么、`Fix:` 能照抄的改法、`See` 仓库里一个文件（[写法](docs/style/code.md#检查管着的写法)）。lint 规则用 `scripts/oxlint-plugin.ts` 的 `says`，`no-restricted-imports` 的话写进 `vite.config.ts` 的 `refused`；规则算得出改法的就算出来，能机械改对的给自动修复。
4. 只许减不许增、数得清又没有动机去刷的，做成棘轮（`packages/health` 的逃生口）；会被刷的读数（行数、测试数）只出报告，不做门槛。
5. 给检查写测试：一个该拦的、一个不该拦的，加上报错的格式。
6. 写不成检查的才进文字：一句规矩放进 `AGENTS.md` 并链到它的家，理由写进对应子系统的「为什么这样」。

## 2. 评审一块代码有没有在变坏

逐条问，每条都有现成的办法查：

| 病 | 问 | 怎么查 |
|---|---|---|
| 局部缝合 | 同一段逻辑是不是抄了第二份？加一个渠道、工具、runtime 时，有没有把超时、重试、清理又写一遍？ | 在仓库里搜这段逻辑的关键调用；看扩展点的文件（`apps/server/src/connector/` 下各聊天软件的 adapter、`apps/server/src/tool/`）有没有自己的 `AbortSignal.timeout`、`sleep`、重试循环 |
| 只加不删 | 换了新写法，旧的删了没有？ | `vp run deadcode`；搜旧函数名；`内部不留兼容`：不留旧路、不写兜底 |
| 绕开约束 | 有没有 `as`、`!`、关 lint 的注释、`Effect.orDie`、`Effect.ignore`、空的 `catch`？测试的断言是不是改松了？ | `vp run health:verify`（逃生口的棘轮）；diff 里的测试改动；`regression: ` 开头的测试被动了要在 `## Regression` 里点名 |
| 温室假设 | 循环里有没有逐个查库、逐个起 git？流是不是假设一次到一整行？写盘是不是每来一点就写一次？ | 读循环体；看 `docs/subsystems/foundation.md`「贵的东西归拥有它的模块管」；测试里有没有大一点的数据 |
| 架构漂移 | 有没有新加依赖？有没有跨层、跨模块、穿过别人 `index.ts` 的 import？ | `pnpm-workspace.yaml` 的 catalog 的 diff；`vp check`（`page-layers`、`import/no-cycle`、`no-restricted-imports`）；`apps/server/src/modules.test.ts` |
| 看不过来 | 这个 PR 主人要读哪几行才能放心合？契约（`packages/protocol`、`db/`、服务接口、黄金数据）改了什么？ | 把契约的 diff 单独列在 PR 正文最前；一个 PR 讲一件事（[vv-pr](.agents/skills/vv-pr/SKILL.md)） |

查到的照 [vv-simplify](.agents/skills/vv-simplify/SKILL.md) 的格式列给主人：每处带证据、怎么改、靠哪个测试证明没变坏。

## 3. 写计划前问清边界

白皮书的「需求不清就挂起提问」。写计划 Note 或开工前，下面四类有一类说不清，就问主人，给出推荐的选项，不猜：

- **失败和边界**：外面的接口超时或失败时，是忽略、重试几次，还是停下回滚？
- **并发和重复**：同一张工单、同一个人重复触发时，是排队、丢掉新的，还是取消旧的？
- **规模**：列表会不会超过一百条？要不要分页或上限？
- **存量数据**：这里的答案固定是不兼容：表结构直接改，旧库挪开（[地基](docs/subsystems/foundation.md)）；只有对外 HTTP 的 v1 例外。

问的时候用选择题，一题一个决定，推荐项放第一个。

## 4. 做一张纯重构的单

白皮书的「除草」和「代数归约」：重构是一道单独的工序，不和功能放在一个 PR。

1. 靶子来自读数，不来自印象：`vp run health` 的热点、`vp run deadcode`、[vv-simplify](.agents/skills/vv-simplify/SKILL.md) 找到的重复。
2. 分开不变的和变的：几处一样的控制流（截断、退避、重试、失败时发什么）收进一个地方（拥有它的模块的服务，或一个骨架函数），各处只留自己不同的那一点（报文怎么拼、怎么签名），作为参数或窄接口传进去。
3. 分支用 `refactor/`。行为不变：测试只因改名、挪地方而变，断言不减；`regression: ` 开头的测试一律不动；黄金数据不变（变了就不是纯重构）。
4. 结果要可量：删了多少行、调用方少知道了什么、哪个测试证明行为没变，写进 PR 的 `## What changed`。行数不设门槛（会被刷），但一张重构单没有让代码变少或变简单，就不该合。

## 5. 一次改很多文件

同一种机械改动跨很多文件（改名、改签名、去掉一批 `export`），用工具改，不逐个文件手改：

- 改名用 TypeScript 的语言服务（编辑器的重命名）；去掉没人用的 `export` 用 `vpx knip --fix --fix-type exports,types`；结构性的改写用 ast-grep 或 ts-morph 写一次性的脚本，脚本放在临时目录，不进仓库。
- 先在一个文件上跑，看 diff 对了再全量跑；全量跑完立刻 `vp check`。脚本出过错的，把它碰过的文件从 `origin/main` 恢复，重新来，不在坏的结果上修补。
- 每处不一样、要逐处判断的（删死代码、改调用方的逻辑），即使文件多也逐处看过再改。
- 漏改由 `tsc` 和 `scripts/stale-names.ts` 兜底：改名是一个决定时，把旧名写进 `stale-names.ts`。
