# Agent Note: 在不同的频道里安排任务：多频道、外部渠道、定时任务

Status: implemented

## Problem

VibeValley 本质上是一个 personal agent：主人说一句，管家派活，帮工去干，主人验收、收进来。农场和像素村只是把这些状态画出来的一层皮。主人要的是在不同的地方、不同的时间安排任务：

- **不同的频道**：按项目、按事情分开说话。当时只有一个田头，所有项目的派活、汇报、提问都挤在一处，靠工单串分开（[农场群聊](2026-10-11-farm-group-chat.md)明确写了「不做多个频道」）。
- **不同的渠道**：人不在电脑前时，也想在微信、飞书里说一句就派活、收到汇报。当时只有本机的页面、语音和桌面通知。
- **不同的时间**：「每天早上跑一遍依赖检查」「周五把这周的提交整理成周报」。当时派活只能是说一句干一件，加上种植计划；没有按时间来的活。

两个参照：

- **Raft**（botiverse 的人机协作工作区，田头就是照它做的）：人和 agent 在频道、私信、话题串里一起说话，任务挂在消息上，有认领和状态。
- **nanobot**（HKUDS 的轻量个人助理）：外面接一圈聊天渠道（Telegram、Discord、Slack、微信、邮件、飞书……），每个渠道的话进同一个 agent 循环，回复原路送回；按话题隔开上下文；有定时任务（Automations、cron）、长期记性和子 agent。

VibeValley 已经有了 Raft 那一半的大部分（田头、串、@、投递、刹车），有 nanobot 的子 agent（帮工）和记性，缺的是：多个频道、外部渠道、按时间来的活。

## Decision

到点以后怎么派，后来改成了一个定时一张工单、每次到点是它的一次 run，没写档案的派给管家：[定时是一张工单的触发](../architecture/2026-10-16-a-schedule-is-a-trigger.md)。

一句话：**频道是安排任务的地方，渠道是频道通向外面的门，定时是按时间往频道里说的话。** 派活、汇报、投递、刹车全部照田头的规则走，不另起一套。现在的样子见 [server.md](../../../../docs/reference/server.md)「田头」「定时」「巡查」「连接器：微信、飞书、QQ」。

### 多个频道

- 对话多一种 `channel`（`ConversationKind`）。田头是默认的频道（`square`）；每个频道有名字（`#clock-in`）、说明，可以带一个默认项目：在这个频道里派的活，没说项目就在这个项目里干。
- 地址是 `#<频道>`、`#<频道>:<seq>`（读地址的 `parseChatTarget` 在 `server/internal/channel/rules.go`，写地址的 `TargetOf` 在 `server/internal/protocol/chat_rules.go`），帮工的 `channel_say` 接口不变。
- **谁在频道里**：主人和管家在每个频道里；帮工在它的活所在的频道里，在哪个频道派的活，工单串就开在哪个频道下面。投递照旧是 `AudienceOf`：其中的 `helpers` 是这个频道的帮工，`onFarm` 是地里的全部，用来判断 @ 的人在不在地里。三道刹车、送达状态都不变。
- 管家的「农场现状」按频道分组；管家在哪个频道被叫，就回在哪个频道。`dispatch` 带着频道和它的默认项目；管家还有 `channels`、`open_channel`、`channel_settings` 三个工具（`server/internal/manager/tools.go`）。
- 私信不做：频道加上串已经够分开事情。
- **界面**：农场窗口标题里有频道菜单（`app/lib/chat/channel_menu.dart`）。另有一整页的聊天页（`/chat`，`app/lib/workbench/chat/`），布局照 Raft：频道和帮工的侧栏、频道头和「聊天 / 任务 / 定时」标签、平铺的消息行和串的预览、右边的串、创建频道的对话框。起初做成了 Raft 原样的白底黑线、常规字体，主人要的是和像素农场一套，于是改成农场的纸色、木色、像素字和像素图标。农场窗口和这一页显示的是同一个对话，输入框按它显示的对话发。

### 外部渠道

- 一个频道可以接到一个外部会话上。外面进来的话，写成频道里的一条消息；频道里管家和帮工说的话送到外面去，送哪些、怎么排版见 server.md「连接器」。
- 每种渠道是服务端里的一个适配器，只负责两件事：把外面的消息翻成「谁在哪个频道说了什么」，把频道里的消息发出去。写库仍然排队走同一个写入方，`seq` 的顺序就是提交的顺序这条假设不破。
- **只走出站连接**：服务端照旧只听 127.0.0.1，不为渠道开公网端口、不收 webhook。
- **只认主人**：帮工没有权限确认、能在机器上跑命令，所以外部渠道里只有主人自己的账号说的话会进频道；别人说的话丢掉并记一笔。密钥在服务端的数据库和 `$VIBEVALLEY_HOME` 里，不进仓库、不进日志。
- **做了微信、飞书、QQ**（主人要的这三个），设置在「连接器」页（`app/lib/workbench/connectors/`）。几个决定：
  - **都用官方接口**：微信是腾讯给机器人的 iLink 接口（官方的 `@tencent-weixin/openclaw-weixin` 用它），飞书是扫码建个人机器人应用加官方 SDK 的长连接，QQ 是 QQ 开放平台的机器人加 WebSocket 网关。不用 hook 客户端、破解协议的办法（比如接 QQ 的 NapCat）：会封号，也等于把登录交给第三方。三家都只往外连。
  - **一个桥，三个适配器**（`server/internal/connector/connector.go`，适配器在 `connector/weixin.go`、`connector/feishu.go`、`connector/qq.go`，三家自己的接口在 `server/pkg/weixin`、`feishu`、`qq`）：账号、只认主人、配对、发件表、补发和摘要都在桥里，适配器只管登录、收、发。再接一家（Telegram、钉钉、企业微信）只写一个适配器。
  - **主人怎么认**：微信扫码时就知道是谁；飞书、QQ 拿不准，统一用配对码：连上后页面显示 6 位码，第一个私聊机器人发码的人成为主人。比让主人去找自己在那个平台上的 id 好用。
  - **马上发，拒收的进发件表**：每条都马上发，微信、飞书在主人没说话时也能送到；QQ 只能在主人说话后的一段时间里回复。应用拒收的进发件表，按指数退避重试（30 秒起，翻倍，最多半小时），主人下次说话时也补发，多了合成摘要。原先以为微信也只能跟着主人最近一句话回复，汇报要等主人开口；后来改成先当它能主动发，发不出去再退避重试。
  - 默认接在田头上，连接器页可以改接到别的频道：进来的话说在那个频道，出去的只发那个频道里的。

### 定时任务

- 表 `schedule`（`server/migrations/0001_schema.sql`）：在哪个频道、什么时候、说什么、交给谁（某个帮工档案，或者让管家决定）、开没开、上次什么时候跑的。「什么时候」照 Raft 的提醒：一次性的时刻、每隔多久（至少 1 分钟）、每天几点、每周几几点，带时区；不做 cron 表达式，管家和主人都更难写错（后来加了，见[定时加上 cron](2026-10-18-cron-and-follow-ups.md)）。
- 规则是 protocol 的纯函数（`server/internal/protocol/schedules.go`：`NextRun`、`DueSchedules`、`AfterRun`、`ScheduleProblem`、`DueText`）。服务端的 `Schedules`（`server/internal/schedule/schedule.go`）每 20 秒看一遍：到点了先在频道里说一条「⏰ 定时「…」到点了：…」，再交给管家（等它这一轮做完）；写明了帮工档案的是周期工单，每次触发写一张新工单开工（地满了排队），不经过管家（[概念先行](../../proposed/architecture/2026-10-15-concepts-first.md) 第 6 步）。之后就是一次普通的派活：开串、干活、汇报、收获。
- 主人在任何频道里都可以说「每天早上九点在 #clock-in 跑一遍测试」，管家用 `schedule`、`list_schedules`、`cancel_schedule` 建、看、删。VibeValley 自己的 agent 当管家时，不用它自带的定时（它的 `schedules.json`；`foreman.go` 里关掉了）。聊天页的「定时」标签和频道菜单里的「定时」可以开关、删。
- 几个决定：
  - **下次什么时候不存**，从上次跑的时间算：服务端没开着时错过的，开机后只补一次并说明是补的，循环的从现在往后排，中间错过的几次不一个个补。打开、重启都不用改它。
  - **到点先在频道里说一声**，再派活：主人在频道里看得到每次定时做了什么；写了帮工的不经过管家，不花管家的一轮。
  - **定时是农场的，不是 agent 的**：存在农场的表里，页面能看到、能关；管家只是用工具建它。
- **巡查代替心跳**：nanobot 式的「隔一阵自己醒来看看」每次都是一轮、要花钱，所以不默认叫醒管家，先做一个不调模型的检查。protocol 的 `patrol.go` 看 Inbox 里放着没人管的（@主人 没人回 15 分钟、帮工没动静 20 分钟、做完没收或有冲突 2 小时、计划里没做成的步骤 30 分钟；[要你处理的事是一个 Inbox](../architecture/2026-10-15-inbox.md)），过了宽限期才报，同一件事 4 小时内只报一次；服务端的 `Heartbeat`（和 `Schedules` 同在 `schedule/schedule.go`）每 10 分钟（`patrol.heartbeat_minutes`，0 关）巡一遍，有事才按频道各叫醒管家一次（`【巡查】`）。

### 对照 Raft（v1.21.2 源码）

| 问题 | Raft 怎么做 | VibeValley |
|---|---|---|
| 频道上面是什么 | 一层「服务器」（工作区），频道在里面；类型有频道、私密、共享、私信、串，串就是挂在一条消息下的频道 | 只有一台机器一个主人，没有服务器这一层；串照旧 |
| 频道和代码仓库 | **没有关系**。每个 agent 有一个固定的工作目录（`~/.slock/agents/<id>`），靠聊天和自己的笔记知道该去哪个仓库 | 帮工按工单在项目的 worktree 里干，所以频道可选地带一个默认项目；这是 VibeValley 加的，Raft 没有先例 |
| 外部聊天 | 只有 Slack；一个 Raft 频道对一个 Slack 频道，两边都唯一；Slack 的人不是 Raft 的用户，只是「外部投影」；进来的事件先进一张收件表、出去的消息先进一张发件表，各有工人重试；一张消息对照表管串的对应和防回声；带 bot 标记的事件直接丢 | 一个连接器接一个频道、发件表重试、只认主人。不同：Raft 用公网 webhook 加签名校验，VibeValley 只用出站的长轮询、长连接；外面只认配对过的主人，不另建外部身份 |
| 定时 | 提醒：只有 agent 能建（人在界面上只能看），挂在一条消息上，一次性、间隔、每天、每周加时区，没有 cron；到点只叫醒建它的那个 agent，频道里什么也不发 | 时间写法照搬。不同：主人也能建（经管家），到点在频道里发一条看得见的消息再派活 |
| 定时的任务 | 任务表本身没有定时字段；循环的活是「循环提醒叫醒 agent，它再建任务」 | 一样：每次触发是一张新工单 |
| 心跳 | 没有。agent 只在有消息、被 @、提醒到点时醒 | 不叫醒管家；不调模型的巡查有事才叫 |

## Alternatives considered

**直接用 nanobot 当外壳，VibeValley 只当它的一个工具。** 渠道是现成的，但 nanobot 有自己的 agent 循环、记性和子 agent，会和管家、帮工、田头的投递和刹车重复成两套，核心状态也不再只有一份。

**直接用 Raft。** 频道、任务、Slack 同步都有，但它是多机、托管的协作服务；VibeValley 选的是跑在本机、帮工直接在这台机器上的仓库里干活（[帮工是 oar 的子 agent](../architecture/2026-10-10-helpers-as-oar-subagents.md)）。

**外部渠道走 webhook。** 飞书、Telegram 都支持，但要有一个公网能访问的地址，违背「服务端只听 127.0.0.1」。长轮询和长连接只要出站，足够个人用。

**每个外部会话自动开一个频道。** 群一多，频道就乱；改成主人把一个连接器接到一个频道上，一对一。

**现在就做私信。** 对主人来说，和管家的私信就是一个只有自己和管家的频道；先用频道代替，等真有需要再加。

**心跳默认开着。** nanobot 是一个循环，醒一次不贵；VibeValley 的管家每醒一次是一轮模型调用，几个频道一起心跳就是持续的花销。用不调模型的巡查挡在前面。

**接 QQ 用 NapCat 这类非官方客户端。** 能收能发、不受回复窗口限制，但会封号，也等于把主人的登录交给第三方。

## Consequences

- 派活、投递、刹车只有一套规则，频道、渠道、定时都是往同一个对话里说话。
- **安全**：外部渠道等于让一个聊天账号能在这台机器上派活跑命令。只认配对过的主人、密钥只在 `$VIBEVALLEY_HOME`，是硬要求；那个聊天账号被盗，就等于这台机器被控制。
- **花钱**：定时和外部渠道都会让活在主人不看着的时候发生。每条定时都能单独关，每个连接器都能断开。
- **各家的格式不同**：出去的话一律变成纯文本，太长按段落切开，各家的长度上限见 server.md「连接器」。
- 频道多了，界面多一层：农场窗口有频道菜单，聊天页有侧栏，未读按频道算。

## Deferred

- Telegram，照同样的适配器做；邮件放在后面。
- 像素村里的频道：频道可以是院子里的一处地方，帮工在哪个频道的活上干就往哪边走；外部渠道是邮筒、电台这类门。这是皮，排在功能后面。
