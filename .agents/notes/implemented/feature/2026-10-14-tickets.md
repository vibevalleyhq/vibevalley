# Agent Note: 一次种植是一张工单

Status: implemented

## Problem

主人把一块地上的一次种植看成一张工单（ticket）的全过程：开单，来回几轮（带话、评论某一步），验收，关单。代码里这件事一直都有：派一个帮工就是开单，收获或收工就是关单，它的轨迹记着每一步。可界面上没有「工单」：帮工一走，田就空了，这张工单只能到帮工档案页的轨迹里去翻，看不出它是收获了还是没收就关了，关了以后也没法接着做。

## Decision

行为见 [server.md](../../../../docs/reference/server.md)「工单」和 [farm-ui.md](../../../../docs/reference/farm-ui.md)「工单」。工单是什么、存在哪、状态谁算，后来被 [工单是一样东西](../architecture/2026-10-15-issue-is-one-thing.md) 取代：工单成了服务端的 `Issue`，帮工是它的一次执行，重开是同一张工单的下一次执行。本篇留下的是看板和工单的用法。

- **帮工离开时，轨迹头记下这次执行怎么关的**：`closed`（现在是 `merged`、`merged_into_task`、`dismissed`、`lost`），最后一轮怎么样（`outcome`、`summary`），几轮，花了多少。Session 的收获、合进计划、收工动作在内部完成离场，工单跟着它最后一次执行关上。
- **重开是派一个新帮工，不是接回原来的会话**（`server/internal/issue/dispatch.go`）：同一个帮工档案，同一个项目，发在田头。交给它的第一行是这次要做的，后面是原来的工单、上一次怎么关的、最后一轮说了什么。
- **工单页是看板**（`/tickets`，`app/lib/workbench/tickets/`）：待办、处理中、等你看、已关四列，一张工单一张卡片，顶上能找、能按项目和帮工筛（都在客户端）。拖卡片就是操作，规则是纯函数（`moveOf`）：待办到处理中是开工，处理中或等你看到已关是关单（等你看的先过收成清单），已关回处理中是重开，别的方向拖不过去。点卡片在旁边打开：谁在做、几轮、花了多少、按轮的干活过程（[轨迹](2026-10-13-trajectories.md)），开着的能评论某一步、能带话。
- **种植计划里的工单跟着计划走**：它的帮工做完自动合进计划分支，只能随整个计划收获，所以看板上不能单独关、单独重开（`moveOf` 的 `split`），服务端的重开也拒绝合进计划分支的工单。
- **地满了就排队，由服务端开工**：看板上的人以为拖进「处理中」的活总会做，所以地都占满时待办排上队（`queued_at`），服务端每 5 秒按看板的先后试，有空地就开；开不了的退出队列、在田头说明。随手写的待办默认带上次选的帮工和项目；没选全的拖去处理中时打开表单补上，不报错。
- **种植计划跟着看板走**：计划本身也是看板上的一张卡（在拆、在做的在处理中，拆好、暂停、做完等收获的在等你看），点开去农场的计划板；计划里每步的工单和拆计划的那一张记着它属于哪个计划（当时是 `Issue.task`；现在计划就是父工单，拆计划是它的执行，每一步是 `parent` 指向它的子工单，见 [种植计划是带子工单的父工单](../architecture/2026-10-15-tasks-are-parent-issues.md)），标题写成计划名和步骤名，不再露出派给帮工的长提示。
- **窄屏一次一列**：手机上四列横排太挤，改成顶上切换列。跨列不拖，用卡片打开后的按钮。
- **待办存在服务端**：就是还没派出去的工单，按主人排的先后（整列重新编号，待办不会多）。开工就像管家派活一样派出这个档案的帮工、发在田头。几台设备看到的都一样（工单在核心状态里，[工单进核心状态](../architecture/2026-10-15-issues-in-core-state.md)）。

## Alternatives considered

**新建一张「工单」表，帮工挂在工单下面。** 这样一张工单能先后由几个帮工来做。可是现在一张工单正好对着一个帮工、一条轨迹，另建一层只多了一份要保持一致的状态。重开用链表示，已经够用。

**重开时接回原来的会话（smith 的 resume）。** 上下文最全，可是原来的分支收获以后已经合进主分支、删掉了，worktree 也清了，接回去的会话还以为自己在旧分支上。没收获就收工的，分支可能还在，但会话可能早就过期了。新派一个帮工，把该知道的写进工单里，任何一种关法都能用。

**在核心状态里加工单的状态。** 开着的工单的状态完全由帮工的阶段决定，关了的写在轨迹头里。放进核心状态，就得让 TS 和 Go 两份规则一起改，换来的只是工单页少读一次轨迹列表。

**排队放在客户端：看板开着时替你隔一会儿重试。** 关掉看板、换一台设备，排的队就没了，也会几台设备抢着开。放在服务端，排队和看板开不开没关系，顺序也只有一份。

**看板只读，状态全由农场自己变，卡片上放按钮。** 不会拖错，但主人要的是看板：活从左往右流，拖一下就推进一步。拖到不能去的列直接拖不过去，会改主分支的收获先过收成清单，叫停、收工也要先点确认，所以拖错的代价不大。

**待办放进核心状态。** 几台设备能马上看到别人新写的待办，但待办和帮工、田头没有关系，只有看板用它。放进核心状态就得让 TS 和 Go 两份规则一起改、对照数据重新生成。看板本来就要轮询轨迹列表，顺手一起问。

## Consequences

- 这次改动以前关的工单，头上没有 `closed`，工单页里只显示「已关」。
- 重开的帮工不认得原来的会话，它只知道工单里写给它的那些，要从项目现在的样子重新看起。
- 看板跟着核心状态里的工单变；轨迹列表在工单的执行变了时重新读。

## Verification

- `server/internal/workspace/work_test.go` 的 `TestCrewIssueClosesAndReopens`：收获以后头上记着 `merged`、`completed`、最后一轮的结论、几轮；开着的不能重开，没有的那张 404；重开交给帮工的第一行是这次要做的，后面是原来的工单和上一次怎么关的。
- `TestCrewIssueWrittenDownStarts`：空的写不下，没选帮工不能开工；开工以后帮工的工作就是写下的，再开一次 409；优先级默认普通、可以给；排到另一张前面、排到最后，新写的排最后。
- `TestCrewIssueWaitsForAFreeBed`：项目的地占满时开工排上队；没空地时不开，空出来以后自己开工；手动排上、拿出来。
- `app/test/tickets_test.dart`：工单的状态怎么读；拖动的规则（哪些方向能拖、各是什么操作）；看板四列，卡片上的优先级、轮数、用时和花费，搜索和清掉筛选，在列里打一行回车写待办，待办拖到另一张上排到前面，待办拖到处理中发出开工；随手写的待办带上上次选的帮工和项目；没选帮工的拖去处理中不开工、提示补上；地满时排上队、提示、卡片标「排队中」；打开的工单显示几轮、花了多少、最后一轮，重开时把这次要做的发给服务端。
- `TestCrewTicketKnowsItsTask`：计划里一步的工单头记着计划和步骤。`app/test/tickets_test.dart` 另测：会冲突的工单主按钮是「让它解决冲突」，点了把冲突交给帮工；拆计划的工单标题是「拆计划：计划名」。
