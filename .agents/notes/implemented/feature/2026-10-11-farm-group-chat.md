# Agent Note: 农场群聊：主人、管家和帮工在同一个对话里

Status: implemented

## Problem

原来的对话是星形的：主人只和管家说话，管家用工具派活、带话，帮工从不在对话里出现。帮工的汇报、卡住时的疑问，都由管家转述。这带来几个问题：

- **转述有损**：帮工的原话、它在问什么，主人要点开地块详情才看得到；管家转述时会丢细节，偶尔还会说错。
- **主人没法直接对帮工说话**：只能经管家转（「告诉老周……」），或者去地块详情里「浇水」，那句话不会出现在对话里。
- **帮工之间不能交流**：前端等接口签名，只能等后端汇报、再等管家转述；种植计划里的步骤只能靠结论传话。
- **一个对话装不下**：同时有几张工单时，进度、疑问、汇报全挤在一条对话里，看不清哪句是关于哪件事的。

Raft（botiverse 的人机协作工作区，[源码](https://github.com/botiverse/raft-source)，本文对照的是 v1.21.2）已经把「人和 agent 在频道、话题串里一起说话」做成了产品。本文后面的「参考」细读了它是怎么实现的；VibeValley 的田头哪些照着做，哪些因为 VibeValley 的帮工是花钱的、按工单开的会话而故意不同，见「Decision」和「哪些复杂度是必要的」。

## Decision

田头是一个跑在本机的小 Raft：人和 agent 在同一个群聊里说话，帮工自己汇报、自己提问、互相交接。行为和接口见 [server.md](../../../../docs/reference/server.md)「田头」、[architecture.md](../../../../docs/architecture.md)「核心状态」、[farm-ui.md](../../../../docs/reference/farm-ui.md) 界面 16；规则是 protocol 的纯函数（`server/internal/protocol/chat.go`、`chat_rules.go`）。下面只记决定了什么。

### 对话的样子

- **田头**：一个主频道。主人、管家、地里的每个帮工都在里面，帮工派出来时加入，收工时离开（它说过的话留着）。
- **工单串**：派一件活，管家在田头发一条派活消息，下面开这件活的串；帮工的确认、疑问、汇报，主人的追问，都在串里。田头上每件活只占一条，挂着「几条回复、几条新的」。
- 种植计划的每一步照常各有一个工单串。不做私信，也不做多个频道。（多个频道后来加上了，田头是默认的那个，见 [频道和定时](2026-10-11-channels-and-schedules.md)。）

### 用帮工的 id 来 @

- 帮工是 `@w3`，管家是 `@管家`，主人是 `@主人`，`@所有人` 只有主人能用。页面把 `@w3` 画成小标签，输入框打 `@` 弹出地里的帮工和管家，插入的是 id。
- 帮工读到的消息头同时带 id 和名字（`from=w3 后端老周`）。
- 代码里的 @（反引号、代码块）不算。@ 了不在地里的人，消息照发，发的人被告知没送到，不静默。
- 写 @ 就是叫醒那个人。只是提到谁，写名字或编号；`session_list` 的名单也不带 @。

### 谁会被叫醒：送达和注意力分开，比 Raft 收得紧

照 Raft 分三层：谁看得见、谁会收到、谁被点名。VibeValley 只收紧「谁会收到」：帮工按工单开会话、按 token 花钱，不能每条闲聊都叫醒它（`AudienceOf`）。

| 谁说的 | 叫醒谁 | 只让谁知道 |
|---|---|---|
| 主人在田头 | 被 @ 的；没 @ 别人时是管家 | 地里每个帮工（忙的收到提示，歇着的下次醒来在摘要里看到） |
| 主人在串里 | 被 @ 的、工单串的帮工、跟着这个串的 | — |
| 管家或帮工 | 被 @ 的；在一个帮工的工单串里说话，叫醒那个帮工 | — |
| 帮工的汇报 | 没做成时叫醒管家 | 做完时给管家；种植计划里的帮工不给，计划自己告诉管家 |
| 派活消息、农场的提示 | 谁也不叫 | — |

在一个串里说过话、或者在串里被 @ 过，就跟着那个串，和 Raft 一样。

### 帮工怎么说话：农场的工具

服务端在 `/mcp`（只听本机，MCP 官方 Go SDK 的 Streamable HTTP，`server/internal/mcp/mcp.go`）上给帮工四个工具：`channel_say`、`channel_read`、`channel_inbox`、`session_list`。派帮工时，通过 smith 的 `mcpServers` 交给它的会话，带一个这次会话专用的令牌（`Authorization: Bearer …`），换会话、收工就作废；令牌只分清是谁，不防人。

- **最后的汇报照旧自动贴出**：一轮的结论以帮工自己的名义贴进它的工单串，原文在「干活过程」里。`channel_say` 只用于一轮中间：确认、提问、交接。
- **新鲜度拦截照 Raft 做**：`channel_say` 的目标里有它没看过的新消息，就先不发，把最多 3 条给它看，改了再发或 `anyway: true` 照发。

### 帮工收到的是什么

- **歇着时被叫醒**：新一轮的输入直接带上叫醒它的消息（最多 3 条全文，`WakeInput`），别处没读的给摘要（最多 20 个对话），写明旧消息只读不回，除非直接问到它。比 Raft 少一次读的来回。
- **忙的时候**：攒 3 秒，经 smith 插进这一轮一句不带正文的提示（`BusyNotice`），它自己决定什么时候读；同一会话里同一条只提示一次。

### 刹车：防止 agent 之间来回

Raft 只靠提示词里的礼节。VibeValley 加了三道结构上的闸，模型守不守礼节都管用：

1. 帮工之间只有 @ 才叫醒。
2. 一个对话里从主人上次说话算起，agent 叫醒 agent 最多 4 次（`HopLimit`）；到了，@ 照样记、照样显示，但不叫醒，串里贴一句。主人一说话重新计数。
3. 同一个帮工被 agent 叫醒，间隔至少 60 秒。

主人的话不受这三道限制。

### 送达要靠得住

- **交给它不等于它看到了**：投递有五个状态（未交付、提示过、已交付、看到了、不给了）。消息放进一轮的输入记为已交付，这一轮真的开口才算看到；没开口就结束、进程死了、服务端重启，都退回未交付，下次再给。宁可重复，不可丢。
- **叫不醒就别一直叫**：连续 3 次叫醒都在开口前失败，就停止自动叫醒它，它的串里贴一句；主人亲自对它说话时解除。被拦下的投递照样记着（`held_by = 'wake_breaker'`）。
- **压缩上下文时不插话**；**重试不发两遍**（同一个帮工 60 秒内在同一处说一模一样的话，返回原来那条；管家用幂等键）；**防发错地方**（刚读的是一个串、却要发到田头顶层，先拦一次）；**自己的话和农场的提示不算未读、不叫醒**。

### 管家

- 管家是田头的一员，跑在服务端进程里：它的回答是逐字长出来的消息（`ForemanSays`），在串里被问到就回在串里。给它的话（主人在田头上没 @ 别人的话、@管家、没做成的汇报）直接进它的会话，当即算看到。
- 帮工自己汇报，管家不再转述。做完的汇报在它下次开口时一起交给它（`ForemanDigest`，记成一条不显示的 `farmNews` 消息），它只在要人拿主意时开口。
- 工具：`tell` 改成以管家的名义说在工单串里；加 `read_chat`。

### 页面

- 聊天窗口变成田头：消息带头像（帮工是它的小动物，管家是管家像），派活消息下挂着它的串，点开在同一个窗口里看整个串、在串里回复。
- 输入框打 `@` 弹出能叫的人；主人没读的有红点和计数，主人的已读位置存在服务端，几个客户端看到的一样。
- 地块详情有「看工单串」，在田头窗口里打开它的串。

### 核心状态和存储

- `CoreState.chat`：田头和最近的串（最多 100 个），以及它们最近的消息（总共 300 条）。新的事实 `message`（新消息，或管家在说的那条用同一个 `seq` 再发）和 `conversation`（新开或变了）取代原来的 `transcript`。更早的消息页面用 HTTP 取。
- 聊天记录的家是数据库：一条消息先写库，成功了再施加事实。`state.json` 不存田头，启动时从库里放回核心状态，两份不会对不上。
- 帮工的已读位置、跟着哪些串、投递，只有服务端用，只在库里。
- 投给谁、叫不叫醒、帮工收到的话、核心状态里留哪些，都是 protocol 的纯函数，有单元测试。

## 数据表

存储是 Go 服务端的 SQLite（modernc，纯 Go，一个文件 `$VIBEVALLEY_HOME/vibevalley.db`），不另起数据库服务。表在 [`server/migrations/0001_schema.sql`](../../../../server/migrations/0001_schema.sql)，查询在 `server/pkg/db/queries/` 里每张表的文件，[`server/internal/channel/db.go`](../../../../server/internal/channel/db.go) 把它们读成田头的行。当初在 TypeScript 服务端上是 PGlite 加 effect-sqlc 生成的查询；换成 Go 时表照 PG 的迁移折成最后的样子，时间存毫秒（[服务端用 Go 重写](../architecture/2026-10-13-go-server-on-smith.md)）。

写库排队一个一个来，消息、@、跟帖、投递、串的摘要在一个事务里。服务端只有一个写入方、数据库只有一个连接，所以 `seq` 的顺序就是提交的顺序；Raft 要等 3 秒「稳定」，是因为它有多个写入方。这是一个要守住的假设：不开连接池。

八张表：

| 表 | 一行是 | 对应 Raft 的 |
|---|---|---|
| `participants` | 对话里的一个人：主人、管家、一个帮工、农场（系统提示）。帮工收工后这一行留着 | 用户表、agent 表 |
| `conversation` | 田头，或者一个串（挂在一条消息下，关联到工单） | `channels`（`thread` 类型） |
| `message` | 一条消息，`seq` 是全局顺序，也是对外的消息号 | `messages` |
| `mentions` | 一条消息里写到的一个 @，以及它解析成了什么 | `message_mentions` |
| `follows` | 谁跟着哪个串，为什么 | `thread_follows` |
| `read_cursors` | 一个人在一个对话里连续读到哪；主人的也在这里 | `agent_channel_read_cursors` |
| `seen_marks` | 看过、但不连续的几条（叫醒时直接带进这一轮的） | 守护进程的「模型看到了」记录 |
| `deliveries` | 一条消息给到管家或某个帮工：为什么、叫不叫醒、被哪道闸拦下、走到哪一步 | `inbox_notification_facts` 加 `mention_delivery_occurrences` |

有意不建的表：

- **来回计数和冷却**：从 `deliveries` 现算，不另存。
- **令牌**：每次开会话新发一个，只在内存里。重启后帮工的会话重开，令牌跟着换。
- **熔断的计数**：在内存里，重启清零；被熔断拦下的投递照样记进 `deliveries`。
- **被拦下的草稿**：Raft 存草稿，是因为它的命令行重发时不带正文；`channel_say` 是工具调用，模型手里有原文。

## 哪些复杂度是必要的

Raft 的实现里有很多看起来繁琐的地方。逐条对照 VibeValley 的处境，分三类：

**在 VibeValley 里一样躲不开，照着做**

| Raft 的做法 | 为什么 VibeValley 也需要 | 在本设计里 |
|---|---|---|
| 先落盘再投递；交给 runtime 以后，要等模型真的开口才算看到 | 帮工会在任何时候死掉：登录失效、进程崩溃、VibeValley 重启。不记下「交到哪一步」，消息要么丢，要么不知道该不该重发 | `deliveries` 的五个状态；开口才算 `seen`，没开口就退回 |
| 忙时攒一下、只提示一次；同一组未读不重复提示 | smith 的插话每次都占这一轮的上下文；提示一多，模型就被打断得干不了活 | 攒 3 秒；同一会话只提示一次（`session`） |
| 成员都收到，@ 只是注意力 | 主人在田头说「main 刚合了大改动」，帮工必须知道，哪怕没人被 @ | 被动投递：不叫醒，忙的提示、闲的看摘要；外加 `@所有人` |
| 重启或长时间离线后，补课模式只读不说 | 否则重启后几个帮工同时回一堆过期的话 | 醒来时旧消息只给摘要，规矩写明只读不回 |
| 连续 3 次叫醒都早早失败，就熔断 | 登录失效的帮工每被 @ 一次就失败一次，田头全是提醒 | 叫醒熔断，主人亲自对它说话时解除 |
| 新鲜度拦截 | 两个帮工被同时 @，都会抢着答 | 照做，最多给 3 条新消息 |
| 发送幂等 | 工具调用超时会重试，模型也会自己再调一次 | 60 秒内同一处同样的话算重试；管家用 `send_key` |
| 压缩上下文时不插话 | 压缩中途插进去的话可能被压掉 | 压缩完再提示 |
| 防发错地方 | 回复发到田头顶层，串里的人看不到 | 拦一次确认 |
| 哪些消息不算未读、不叫醒 | 系统提示如果叫醒帮工，就是自己制造噪声 | 自己的话和系统提示都不算 |

**VibeValley 的处境让它变简单了**

| Raft 的做法 | 为什么 VibeValley 不需要那么复杂 |
|---|---|
| 已读位置只推进到 3 秒内已经稳定的那一段 | Raft 有多个写入方，`seq` 的顺序不等于提交的顺序。VibeValley 只有一个进程、数据库只有一个连接，写入是排队的，`seq` 的顺序就是提交的顺序。这是一个假设，要守住：不开连接池 |
| 服务端和守护进程之间的确认协议（最多重试 24 次） | VibeValley 的「守护进程」就在服务端进程里，交给 smith 是一次函数调用，没有网络 |
| 本机代理和每次启动的令牌文件，真密钥不交给 agent | VibeValley 的帮工本来就在这台机器上、没有沙箱；令牌只用来分清是谁在说话，不用来防谁 |
| 草稿存 10 分钟，`--send-draft` 原样重发 | 我们的工具调用里模型手里有原文，被拦下后重发带上就行 |
| handle 和显示名、空格和中文吞字、@ 不在频道里的人要发起邀请 | 用帮工 id 来 @；只有一个田头，没有私密频道，不存在「不在频道里」 |

**Raft 的规模才需要，VibeValley 不做**

多台服务器之间转发、多台机器上的守护进程、RisingWave 算未读、外部 agent 登录、私密频道和权限矩阵、Slack 同步。

## 参考：Raft 的群聊是怎么实现的

路径都在 raft-source 的 `packages/` 下。

### 数据

- **频道**（`server/src/db/schema.ts` 的 `channels`）：`type` 是 `channel`、`private`、`joint`、`dm`、`thread` 之一。话题串也是一行频道，带 `parent_message_id`；第一次回复时在事务里建（`channelService.ts` 的 `getOrCreateThread`），不能嵌套。串没有自己的成员，能不能发言看父频道。
- **消息**（`message`）：
  - `seq` 是全库一个 `bigserial`，到处当游标用。注释说明「seq 的顺序不是提交的顺序」，所以已读位置只推进到 3 秒内已经稳定的那一段（`READ_POSITION_SETTLE_MS`）。
  - `sender_type` 是 `user`、`agent` 或 `external_projection`。
  - agent 的每次发送带一个幂等键 `agent_send_key`，在（发送者, 键）上唯一：重发返回同一条，内容不同就报 409。
- **@**（`message_mentions`）：每条消息 × 每个被 @ 的人一行，记下发送时的 handle、发送时能不能通知到（`notifiable_at_send`）。被 @ 的 agent 另有一行送达记录（`mention_delivery_occurrences`），状态从 `recorded` 经 `server_decided`、`daemon_received`、`daemon_drained` 到 `acked`：先落盘再投递，靠比较后写入推进。
- **跟帖**（`thread_follows`）：原因有 `replied`（回过帖）、`authored`（父消息是你发的）、`mentioned`（在串里被 @、而且是父频道成员）、`manual`。打开一个串不算跟帖；退出跟帖保留这一行，只打上时间。
- **已读**（`agent_channel_read_cursors.last_read_seq`）：
  - 读历史时推进，只推进到和原位置连上的那一段；
  - agent 自己发言时推进，但前提是中间没有别人的未读；
  - 守护进程报告「模型看到了」时推进，只推进到连续的那一段。
- **收件箱事实**（`inbox_notification_facts`）：和消息在同一个事务里，给每个该收到的人写一行，记下是不是点名提到他、算不算未读。它同时是串的投递名单、静音的豁免名单和新鲜度拦截的锚点。
- **任务**（`tasks`）：
  - 挂在一条顶层消息上，状态有 `todo`、`in_progress`、`in_review`、`done`、`closed`；
  - 认领是加锁：已经被别人认领、或者已经关闭，认领就失败，靠 `revision` 比较后写入；
  - 指派给 agent 时发一条系统消息，带点名的注意力，能穿透静音。

### 服务端：投给谁、叫不叫醒

- **写入路径**（`server/src/services/messageService.ts` 的 `broadcastAndDeliver`）：
  1. 解析目标；
  2. 抽出 @，解析：私密频道只认成员，公开频道和私信认全服务器的人，但只有成员能被通知到；
  3. 在一个事务里写消息、@、收件箱事实；
  4. 用 Socket.IO 推给浏览器；
  5. 投给 agent。
- **投给哪些 agent**（`deliverMessagesToAgents`）：
  - 频道里除发送者以外的**全部** agent；串里是跟帖的 agent。
  - 静音的 agent 去掉，但被 @ 的、任务负责人照收。
  - 再按「算不算未读」过滤：自己发的不算，一些系统消息不算。
  - agent 发的和人发的，在投递上几乎一视同仁：服务端唯一的防循环，是不投给发送者自己。
- **叫不叫醒**（`agentLifecycleReducer.ts` 的 `taskWakeAction`）：
  - agent 没在跑：启动它，带上这条消息、离线期间各对话的未读数（最多 20 个对话，私信优先），以及按需补发的几条（最多 8 个对话、共 20 条）。
  - 在跑：放进内存里可重放的收件箱，经 WebSocket 发给守护进程，等它确认，最多重试 24 次。
  - 被停掉的：不叫醒，消息留成未读，下次启动时补上。

### 守护进程：什么时候、以什么形式交给模型

- **每个 agent 一个收件队列**（`daemon/src/agentProcessManager.ts` 的 `deliverMessage`），按消息 id 去重、按 seq 排序。之后分情况：
  - 空闲：放进队列，写一条提示开新的一轮。
  - 忙：攒 3 秒（`STDIN_NOTIFICATION_INITIAL_DELAY_MS`）合成一条提示，插进这一轮；写失败 15 秒后重试。
  - 在压缩上下文或在审改动：等它做完再提示。
  - 没进程：缓存起来，启动时带上。
- **能不能插进正在跑的一轮**看驱动（`drivers/types.ts` 的 `busyDeliveryMode`）：
  - claude、codex、pi、grok、kimi 能：claude 往 stdin 写一条 user 消息，codex 调 `turn/steer`，pi 调 `session.steer`。
  - cursor、gemini、opencode、copilot 不能：等这一轮结束、进程退出后，下一轮再带上。
- **交给模型的提示不带正文**（`daemon/src/agentRuntimeInput.ts`）：

  ```
  [Raft inbox notice:
  Inbox update: 7 unread messages total; 4 changed targets
  #general  pending: 1 message · latest sender @x · you were mentioned
  ]
  These messages have not been read. Choose when to read them: … Deferring them does not establish that there is no work.
  ```

  只有三种情况带正文：在一个串里被 @、自己又没有这个串的上下文（附上父消息和最近 6 条）；重启后补发；一次性的系统提示。
- **防通知风暴**（`runtimeNotificationState.ts`）：
  - 同一组未读在同一个会话里只提示一次；
  - 每条消息在一个会话里只宣布一次；
  - 一轮结束时只提示新的。代码注释说，以前每轮结束都重发已宣布的消息，形成过死循环。
  - 另外，服务端在 60 秒内连续 3 次「刚启动就退出」时，停止自动唤醒（`wakeCrashLoopBreaker.ts`）。这防的是崩溃循环，不是聊天循环。
- **状态**：从模型事件推出 `thinking`、`working`、`online`、`error`、`offline`；每 60 秒发一次心跳；服务端带递增序号转发给页面，页面丢掉过时的。没有「正在输入」。

### agent 拿到的规矩和工具

- **只能用 `raft` 命令说话**（`daemon/src/drivers/systemPrompt.ts`）：「命令之外你说的话谁也收不到」；一次工具调用只跑一条 `raft` 命令。
- **身份**：守护进程往 PATH 里放一个 `raft` 包装脚本，导出本机代理的地址和一个每次启动新发、权限 0600 的令牌文件；真正的密钥留在守护进程里（`daemon/src/agentCredentialProxy.ts`、`drivers/cliTransport.ts`）。
- **说话**：`raft message send --target <t>`，正文从标准输入的 heredoc 读。
  - 目标写法：`#频道`、`#频道:<8 位>` 是串，`dm:@某人` 是私信。回复「永远照抄收到的那条消息的 `target`」。
  - **新鲜度拦截**：发送时带上「我看到哪了」。目标里有没看过的新消息，就先不发，存成草稿（保留 10 分钟），把最多 3 条新消息给它看。它可以改了再发、原样发（`--send-draft`）、硬发（`--anyway`），或者不发。认领和更新任务也会这样被拦。
  - **防发错地方**：刚读的是一个串、却要发到频道顶层，先拦一次让它确认。
- **读**：
  - `raft message read --target <t> [--unread|--around|--before]` 读一个对话，推进已读位置。
  - `raft message check` 一次取完所有新投来的。
  - `raft inbox check` 列出有未读的对话，每行附上「下一步该跑哪条命令」。
- **消息头**：

  ```
  [target=#engineering msg=abcd1234 time=2026-04-21 06:30:00Z type=human] @alice: ship it
  ```

  正文的续行前面加 `  │ `，防止消息内容伪造出一行消息头。
- **礼节**（`shared/src/raftCliGuide.ts`）：
  - 「只有被 @ 或明确在叫你时才插话」；
  - 「只有干活的人汇报这件事」；
  - 「不说空话」；
  - 「收到具体的消息，先决定要不要尽早确认」；
  - 「在串里被 @，先读这个串」；
  - 「要做事（不只是回答），先认领任务；认领失败就别做」；
  - 「用提醒，别靠 sleep 轮询」；
  - 有子 agent 时，「只有你在 Raft 上说话」。

## Alternatives considered

**照 Raft，频道成员每条都收、都被叫醒。** 合适的是长驻、按身份存在的 agent。VibeValley 的帮工按工单开会话、按 token 花钱，田头一句闲聊叫醒六个帮工就是六份钱，所以只让 @ 和主人在工单串里的话叫醒它们。

**照 Raft，帮工只通过命令行工具说话，最后的话不贴出来。** 统一，但 VibeValley 的帮工本来就用最后一段话汇报，农场规矩也要求写「结论」；不贴出来，就得让每个帮工多调一次工具，模型也容易忘。所以保留自动贴出，工具只用于一轮中间。

**给帮工一个 `heybro` 命令行，而不是 MCP 工具。** Raft 这样做，是因为它的 agent 在别的机器上，跑什么 runtime 都有。VibeValley 在用的 pi、claude、codex 都接受会话级的 MCP，工具有类型，不用处理 shell 引号和多行中文的 heredoc，身份靠请求头里的令牌。将来接回不接受 MCP 的 runtime（比如 cursor）时，再补一个命令行。

**用 handle 和显示名来 @，像 Raft。** Raft 的手册花了大量篇幅讲显示名被当成 handle、有空格的名字只抽出第一个词、紧跟中文会被吞进 handle 里，这些都会 @ 错人或 @ 不到人。VibeValley 的帮工本来就有稳定的 id，用 id 来 @，页面上显示名字，就没有这些问题。

**聊天记录继续存 JSON 文件**（像 `state.json`、`steps/*.json`）。一条消息要同时改消息、@、投递、跟帖、已读好几处，还要按游标翻页、按人查未读；用文件就得自己保证一致和自己建索引。

**用 SQLite（Node 24 自带 `node:sqlite`）。** 不加依赖，也够用；但主人自己的 effect-sqlc 只生成 PostgreSQL 的查询，用 PGlite 就能直接用它，表和查询都有类型。（这是 TypeScript 服务端时的取舍；服务端换成 Go 以后用的就是 SQLite。）

**多个频道和私信。** 一个农场的人不多，话题串已经能把事情分开；先不做，等真有需要。

**只靠提示词里的礼节防循环，像 Raft。** Raft 自己的手册承认，靠记的规矩在关键时刻会失灵。帮工之间互相叫醒是花钱的事，所以加上只有 @ 才叫醒、来回上限和冷却。

**串在侧边展开**（提案时的写法）。聊天窗口只占右下角一块，侧边再开一栏会盖住地；串改成在同一个窗口里打开，顶上有返回田头，别处有新话时顶上有一个标签。

**管家也用 MCP 上的四个工具**（提案时的写法）。管家跑在服务端进程里，它的话本来就是逐字流出来的（`Chat.ForemanSays`），给它的话直接进它的会话；再让它绕一圈 HTTP 调 `channel_say`，只多出一次工具调用和一份令牌。所以管家只加了 `read_chat`，`tell` 改成在工单串里说话。

**`session_list` 照聊天里的写法列出 `@w22`**。帮工会原样抄进自己的话里（「地里有 @主人、@管家、@w22」），每个 @ 都叫醒一个人，见下面「Verification」。所以名单不带 @，农场规矩和管家的提示词都写明：只在要叫醒对方时写 @，提到谁写名字或编号。

## Consequences

- **花钱**：每次叫醒都是一轮。只用 @ 叫醒、冷却和来回上限是为了这个。模型会把读到的 @ 名单原样抄进自己的话，每个都叫醒一个人；名单不带 @、规矩写明 @ 就是叫醒，是对这一点的补救。
- **结构上的闸不靠模型自觉**，但礼节还是靠：DeepSeek Flash 和 claude 守礼节的程度不同，第一次真跑里 pi 的帮工用 `sleep` 轮询等别人回话，没有等提示。
- **claude 的一次「工单」可能是好几轮**：它在后台开的计时器到点会自己再开一轮，每轮结束都贴一次汇报，串里会多出几条进度。
- **SQLite**：一个文件、一个连接，写库排队。备份就是拷贝 `$VIBEVALLEY_HOME/vibevalley.db`。
- **状态多了**：投递有五个状态，交付和看到之间靠会话的事件推进；判断都写成纯函数，状态的转移用脚本扮演的帮工测「开口前死掉」「重启」两种情况。
- **一次迁移**：没有库的旧农场，启动时把 `state.json` 里的旧对话（`lines`）写进田头一次，只在库是空的时候做。

## Deferred

- 种植计划自己的串（拆计划、开工、某步失败、熟了），现在这些仍由计划告诉管家（[种植计划](2026-10-11-tasks.md)的 Deferred）。
- 管家的「农场现状」里列出每个串有几条主人还没回的提问。
- 串的静音和退出跟帖、私信。Raft 的认领锁不照搬：种植计划的步骤由服务端派，没有人去抢（[种植计划](2026-10-11-tasks.md)「对照 Raft 的任务」）。
- 不接受 MCP 的农机（比如 cursor）用的命令行版农场工具（[其他农机](../../proposed/feature/2026-10-10-other-runtimes.md)）。
