# Agent Note: 种植计划：把长任务拆成一张图，交给不同的帮工

Status: implemented

## Problem

以前一张工单交给一个帮工，一轮做完。长的编码任务（一个功能要改数据层、接口、页面、测试、文档）这样做有四个问题：

- **上下文越拉越长**：一个会话从头做到尾，越往后做得越差；中途失败就整轮重来。
- **没法并行**：互不依赖的部分也只能一个帮工排着做。
- **没法按长处分工**：写接口、写页面、写测试，本可以交给不同的帮工档案（不同的人设、模型、技能）。
- **管家跟不住**：管家可以在对话里一单一单地派，但它是个便宜的模型，跟不住几十分钟、十几步的进度。谁先谁后只在它的上下文里，重启就没了，主人也看不到全貌。

## Decision

**种植计划**（代码里叫 playbook）是一张有向无环图：每一步是一张工单，边表示「做完 A 才能做 B」。一张计划经历拆、审、做、合、收五个阶段：

1. **拆**：派一个读代码的帮工去拆。它只读不改，汇报最后用一个 json 代码块给出计划。服务端校验后存为草稿；不合格就打回一次。
2. **审**：主人在计划板上看草稿，可以改步骤、加步骤、删步骤。点开工才动。
3. **做**：开工时，从主分支开出计划分支。等的步骤都合进去了或跳过了，下一步就派帮工，在计划自己的并行数和农场的上限以内，互不依赖的步骤同时做。每一步的 worktree 从计划分支当时的提交开出来，工单附上前面每一步的结论和提交号。
4. **合**：一步做完，先跑它的检查命令，过了就合进计划分支（不动任何检出），帮工收工。检查没过、一轮失败、合并冲突，农场自己让它重来两次；再不行就停下等主人：重试、改工单、跳过。
5. **收**：所有步骤都合进去或跳过后，主人看清单，一次合进主分支。

代码落在这些地方：

- **核心状态**：计划曾经整张放在 `FarmState.playbooks`，每变一次施加一条 `playbook` 事实；后来计划成了带子工单的父工单（[种植计划是带子工单的父工单](../architecture/2026-10-15-plans-are-parent-issues.md)），存在工单里，从核心状态里的工单拼出来。帮工带 `playbook`，说明它在哪个计划的哪一步。
- **规则**：都是 protocol 的纯函数（`server/internal/protocol/playbook.go`）：`PlanProblems`、`ParsePlan`、`Startable`、`EditNode`、`NodeTask`、`LayersOf`。客户端的 `app/lib/rules/playbook.dart` 移植了画计划板要的几个（`layersOf`、`blockedBy`……）。（当时网页的模拟服务器也用这些，它随网页删掉了。）
- **服务端**：`server/internal/tickets/playbooks.go` 听工地事实，一次只做一件事。管家多了五个工具（`plan`、`playbooks`、`plan_edit`、`plan_action`、`node_action`），计划里帮工的汇报不再转给管家，只在要人拿主意时由计划告诉它。
- **页面**：院子里的图纸桌（或农场手机上的「计划」）打开计划板，步骤按先后分列，每步一张卡片，最下面是计划的经过。
- **经过**：计划只经服务端的一个 `put` 写。每写一次，和写之前比一比（protocol 的 `PlaybookChanges`），变了什么记一行，带是谁做的（主人、管家、农场）和为什么，存在田头的数据库里（`playbook_events`，`server/internal/tickets/playbook_log.go`）。事实里仍是整个计划的快照；经过是另存的，回答「这一步怎么走到这里的、工单被谁改过」。
- **规划的规矩**（`server/internal/runs/rules.go` 的 `PlanningTask`）：不互相依赖的步骤改不同的文件；别拆成一条串行的长链，有先后的按阶段分组。

行为细节见 [docs/server.md](../../../../docs/server.md)「种植计划」和 [docs/game-ui.md](../../../../docs/game-ui.md) 界面 18。

## 对照 Raft 的任务

Raft（[源码](https://github.com/botiverse/raft-source)，对照的是 v1.21.2）里和种植计划最像的是任务（task）和工作流（workflow）。主要在 `packages/server/src/services/taskService.ts`、`workflowService.ts`、`db/schema.ts` 的 `tasks` 和 `task_events`，以及给 agent 的规矩 `packages/shared/src/raftCliGuide.ts`。

**Raft 的任务是什么**：一张挂在频道消息上的工单卡，用来防止几个常驻的 agent 重复干同一件事。

- **数据**：`tasks` 一行，带频道里的编号、标题、描述、状态、负责人、认领时间、乐观锁的 `revision`，以及宿主消息 `message_id`。讨论在宿主消息下面的串里。
- **状态**：`todo → in_progress → in_review → done`，`closed` 表示不做了，从哪都能到。`in_review` 是等人验收；`done` 可以重开。
- **认领**：「我开始做了」，负责人设成自己并进 `in_progress`；**指派**只换负责人，被指派的人认领了才算开工。认领失败（已关闭、已做完、在别人手上）是一把并发锁：规矩要求 agent 认领失败就别做，但读、协调、评审、请求转派不受限。
- **并发**：每次写都比较 `revision` 和预期状态（CAS）。
- **记录**：每次变化写一行 `task_events`（创建、换状态、换人、重开、关闭、改卡片），按全局 `seq` 排序；改卡片记下改前改后。
- **权限**：改状态、改卡片、取消认领是频道成员都能做的；删除限创建人，或有 `deleteAnyTask` 权限的人。
- **工作流**：模板是一串有顺序的步骤，一次只为当前一步建一个任务，它 `done` 了才建下一步。是一条线，不是图。

**哪些已经是这样，哪些借，哪些不借**：

| Raft 的做法 | 种植计划里 | 结论 |
|---|---|---|
| 任务挂在一条消息上，讨论在它的串里 | 每一步派出的帮工有派活消息和工单串（[农场群聊](2026-10-11-farm-group-chat.md)）；计划本身还没有 | 已经是这样；计划自己的串见 Deferred |
| 指派（谁该做）和认领（开工了）分开 | `PlaybookNode.agent` 是该派谁，`helper` 是现在谁在做；开工由调度决定 | 已经是这样 |
| 认领锁：多个 agent 抢同一张卡，失败就别做 | 步骤由服务端按图派给新开的帮工，一步只有一个帮工，没有人去抢 | 不借，见 Alternatives |
| `revision` 乐观锁 | 只有主人一个人改；服务端一次只做一件事；改步骤前按步骤的状态检查（开工后只能改没开始或没做成的） | 不借：状态检查已经挡住改到正在做的步骤 |
| `in_review`：每张卡做完等人验收 | 每一步过机器的检查命令就合进计划分支；人只在收获整张计划时看一次 | 不借：每步等人会让并行停下来；人审在收获，帮工审见 Deferred 的审查步骤 |
| `closed`：不做了，不影响别的卡 | `skipped`：不做了，等它的步骤照常开工 | 保持不同：图里有依赖，「不做」必须说清下游怎么办 |
| `done` 可以重开 | 只有没做成的步骤能重试；合进去的不重开：它的提交已经在计划分支上，重开要先撤 | 不借：要返工就加一步 |
| `task_events`：每次变化一行，改卡片记前后 | 计划的经过：每次写计划时比出变了什么，带谁做的；改工单记前后 | 借了。不同的是事件由比较得出，不靠每个写的地方自己记，漏不掉 |
| 工作流模板：一串步骤的骨架，每次实例化 | 计划模板还没有 | 借它的形状：模板只存步骤的骨架和先后，见 Deferred |
| 拆任务的规矩：尽量并行，按阶段分组，别拆成一条串行的链 | 规划的规矩照这样写了 | 借了 |
| 资源回执：创建外部资源的任务，做完前必须登记谁负责回收、何时到期 | 帮工只在本机的 worktree 里干活 | 不借，直到帮工会建外部资源 |

种植计划比 Raft 多的：步骤之间的先后是图，互不依赖的同时做；每一步有自己的分支、检查命令和合并；没做成的自动重来两次。这些是因为 VibeValley 的步骤是同一个仓库里的代码，Raft 的任务是任意的工作项。

## Alternatives considered

**让管家在对话里一单一单地派。** 现在就能做，但进度只在管家的上下文里：便宜的模型跟不住十几步，重启就丢，主人看不到全貌，每一步调度还要花一次模型调用。拆图需要模型，调度不需要。

**让管家直接拆。** 更快更便宜，但管家不读代码，拆出来的步骤对不上现有的结构。所以交给一个在项目里读代码的帮工；管家只负责起头和转告。

**交给 runtime 自己的子 agent 或工作流**（claude 的 workflow、codex 的子线程；oar 只报告它们的 task 事件）。整件事在一个会话里：农场看不见每一步，只能用一种 runtime，也没法给每一步单独的分支、检查和收获。

**每一步做完直接收进主分支，或者每一步都要主人点。** 主分支上会出现做了一半的功能，主人要审十几次，并行的步骤还会在主分支上互相冲突。计划分支把这些挡在主分支外面：中间的合并自动做，主分支只在最后收获时变一次。

**所有步骤在同一个分支、同一个 worktree 上排队做。** 没有并行，也分不清哪个提交属于哪一步。

**把计划的每个变化拆成细的事实**（计划状态变了、某一步开始了、某一步合进去了……）。一张计划最多 12 步，整个发一次也很小；细的事实要在 `reduce` 里多写七八种，模拟服务器也要跟着写。所以一条 `playbook` 事实带整个计划，内容没变的不算新闻。

**照 Raft，让帮工自己从任务板上认领步骤。** 这适合 Raft 的处境：一群常驻的 agent 都看得到任务板，谁有空谁领，认领锁防止两个人做同一件事。VibeValley 的帮工是按步骤新开的会话，派谁、何时派由服务端按图和上限决定，一步只会有一个帮工，没有谁去抢；让帮工自己领，反而要多一套「谁有空、该不该领」的规矩，和一份花钱的轮询。

**照 Raft 的工作流，计划做成一条线。** 一次只做一步，简单，也不会并行冲突；但长活里互不依赖的部分（接口和页面、文档）就只能排着做。Raft 自己给 agent 的规矩也要求拆任务时尽量并行、别拆成串行的链。

**以项目仓库里的计划文件为准**（比如 `.vibevalley/playbook.yaml`）。适合做模板，但正在跑的状态（谁在做、做到哪）属于农场的核心状态，放两处就会对不上。

## Consequences

**换来的**：
- 长活可以拆开、并行、按长处分给不同的帮工。
- 进度在核心状态里，页面、管家和重启后的服务端看到的是同一份。
- 主分支直到收获才变。
- 调度是确定的规则，测得到。

**付出的**：
- **多一轮规划的钱**；拆得不好，后面的帮工都白做。靠主人审草稿、最多 12 步、规划的规矩（每一步可以单独验证、写清留下什么）挡一部分。
- **并行冲突**：同时做的步骤改同一个文件，合并时会冲突，多一轮让它解决。`scope` 只是提醒，不强制。
- **约定靠结论传**：步骤之间的约定（接口签名、数据格式）只靠结论里的文字传，下游可能对不上。所以规划的规矩要求最后一步做整体验证。
- **抢地**：一张计划差不多能占满 6 块地，和散单抢地，先到先得。
- **核心状态更大**：计划整张放在里面。（当时模拟服务器也要实现一遍计划，好在规则是共用的；它随网页删掉了。）

## Verification

- `server/internal/tickets/playbooks_test.go`，用脚本扮演帮工、用真的 git 仓库，跑了四种情况：
  - 菱形的图：b、c 同时做；d 在两者合进去之后才开工，并且看得到它们的文件；收获前主分支不变；收获后计划分支和步骤分支都删掉。
  - 一步失败两次后停下，不相干的步骤照做；检查没过的一步被打回一次；跳过以后后面的步骤开工；放弃后分支留着。
  - 有环的计划打回给规划的帮工，重给的成为草稿。
  - 服务端重启后，计划暂停，继续后接着做完。
- `server/internal/protocol/playbook_rules_test.go` 测纯函数：校验、分层、能开工的步骤、读规划的结果、改计划、`NodeTask`、`Reduce` 按家族只留最近 `KeepClosedIssues` 家关上的工单、两版计划之间比出的经过和它的说法。
- 菱形的那次跑完以后读经过：计划这一层依次是要拆（主人）、拆好了（农场）、开工（主人）、熟了（农场）、收获（主人）；管家改 d 的检查记成管家、只改了「检查」；每一步都是开工、合进去，合进去带帮工、提交号和结论。坏步那次里，检查没过的退回记下了为什么。
- 计划里的帮工的地不能用收获工具：`app/test/farm_rules_test.dart`（`aimTool`）。收获整个计划给金币，合进去的步数到「五谷丰登」的档位：`server/internal/protocol/progress_rules_test.go` 的 `TestPlaybookHarvested`。（原来这两条在 `packages/core/test/`，随网页删掉了。）

## Deferred

- 审查步骤：一个不改代码的帮工看上游的 diff，不通过就带着意见退回上游重做。
- 计划模板：存下来的图，下次一句话就能套用。照 Raft 工作流模板的形状，模板只存步骤的骨架（标题、说明、先后、检查命令），套用时再由规划的帮工按项目填工单。
- 做到一半时，重新规划剩下的步骤。
- 跨项目的计划。
- 计划分支合进主分支会冲突时，派一个帮工去解决。现在只是不合，提醒一句。
- 计划自己的串：拆好了、开工、某一步没做成、熟了，发在计划的串里，在田头上就能跟着看；计划板上的经过是完整的记录。
