# Agent Note: 要你处理的事是一个 Inbox

Status: implemented

## Problem

「有事要你处理」在代码里有两套规则：

- 农场手机的来电（`IncomingCalls`，放在 `view.calls` 里）：熟了的活、没做成的、冲突、没动静、计划拆好了或能收了或卡住了、@ 你没读的话；
- 巡查的发现（`Findings`）：@ 你没人回的话、没动静的帮工、做完没收的、计划里没做成的步骤。

两套大半重叠，又各有细节不一样：@ 你的话一个看读没读、一个看回没回；计划里的帮工没动静，一个不打电话、一个要报。照 [概念先行](../../proposed/architecture/2026-10-15-concepts-first.md)，这是同一个概念，Linear 叫它 Inbox。来电还放在农场的画面（`view`）里，可它不是皮，是实际要你处理的事。

## Decision

行为见 [server.md](../../../../docs/server.md)「Inbox」「巡查」和 [game-ui.md](../../../../docs/game-ui.md)「农场手机」。

- **一条规则**：`protocol.Inbox(state)`（`server/internal/protocol/inbox.go`）从核心状态现算出此刻要你处理的事（`InboxItem`），新的在前。不存，同一件事的 id 不变（沿用来电号）。
- **巡查只看 Inbox**：`PatrolStep` 不再自己找，而是看 Inbox 里哪些放过了宽限期（`PatrolGrace`，按种类），过了的才告诉管家。没写宽限期的种类（没做成的一轮、计划拆好了、计划能收了）巡查不报：没做成当时就告诉管家了，计划是主人自己要看的。冲突放 2 小时没人管也报（以前算在「做完没收」里）。
- **@ 你的话**：没读、也没回才算。回了（在那个对话里说过话）就不算，没读也一样；读了不回也不算，巡查不再催。
- **计划里的帮工**：熟了、没做成、冲突交给计划（由管家替计划报），但没动静照样算，计划不知道它卡着。
- **在帧上，不在画面里**：`SiteFrame.inbox` 和 `state`、`view` 并排；`FarmView` 只剩等级和地块。客户端的 `inboxProvider` 读它：农场手机把它当来电，桌面版的通知和菜单栏摘要也读它。
- **改名**：`IncomingCall` → `InboxItem`，`CallWhy` → `InboxKind`（JSON 字段 `why` → `kind`），`Caller` → `InboxFrom`，`CallTarget` → `InboxTarget`。种类的值（`harvest`、`fix`……）先不动，和别的名字一起在提案的改名一步里照 Linear 改。

## Alternatives considered

**两套规则都留着，只在文档里对照。** 改动最少，但以后改一处忘一处，手机响了巡查不报、巡查报了手机不响的情况还会有。

**Inbox 存进数据库，像 Linear 那样有已读、归档。** 可以记住哪些看过，但这些事都能从核心状态现算出来，存一份就要保持一致；接没接过现在由客户端记，够用。

**留在 `view` 里。** 不用改帧的形状，但 `view` 是农场的画面，提案要把它和实际的东西分开；Inbox 是实际的东西。

## Consequences

- 读过但没回的 @，巡查不再提醒管家；回过但没点开的，手机不再响。
- 计划里的帮工没动静，手机也会响。
- 黄金数据（`testdata/parity.jsonl.gz`、`play.jsonl.gz`）用 Go 的结果重写过：每一步多了 `inbox`，`view` 里没有了 `calls`；巡查的用例记的是 Inbox 和每一轮报了什么。
- 经院门连进来的旧版手机读不到 `view.calls`，要和桌面版一起升级。
