# Agent Note: 查询带齐真实关联，创建返回自己的身份

Status: implemented

## Problem

频道创建只回成功，客户端按名字等状态流，再猜哪个频道是刚建的。帮工档案和技能的新 ID 由客户端扫描列表分配，服务端保存却是 upsert；两个设备用同一份旧列表创建，会写到同一个 ID。

工单看板分别读工单、执行历史和核心状态，自己对齐关联；缺记录时补一个 `PhaseResting` 的执行。农机探测、档案和技能又共用一个加载结果，一次农机请求失败会挡住与它无关的档案编辑。

## Decision

- 频道创建直接返回服务端分配的 ID。页面按 ID 打开，名字规范化仍归频道。
- 档案和技能的创建分别分配 ID，与持久化在同一个锁内提交。创建拒绝非空 ID；带指定 ID 的保存仍是原有 upsert，给编辑和导入用。
- 工单历史是服务端的一次关联查询：只带真实执行，找不到的 ID 明列为缺失。它不进入核心状态，也不补造阶段。客户端只有显示当前记录或更早记录的选择。
- 农机目录独自拥有探测、推送、错误和命令回包；档案与技能的读取不再等待农机。农机命令使用返回值更新自己的目录，不刷新全部配置。
- 消息在产生时记录 Run ID，并随消息元数据存盘；汇报的轮次在执行结束清空当前 Run 之前捕获。客户端按事件的 Run ID 展示这一轮，旧消息没有记录关联时直接说明。

## Alternatives considered

**继续在客户端分配 ID，保存前查重。** 查重和写入分两次请求，仍不能挡住两个设备同时创建。

**工单缺执行时补一个可显示的执行。** 这样会把“记录缺失”变成“执行休息中”，后续按钮和统计会依据不存在的阶段工作。

**给配置快照增加更多局部错误字段。** 三类数据没有共同事务；继续合在一个加载动作里，只会让每个调用方都理解部分成功的组合。

**按消息时间向前找输入，再加三秒容差。** 两轮相隔很近时会把后一轮的事件算到前一条消息里；传输延迟不构成可靠的关联键。

## Consequences

创建与保存是两种明确操作；已有指定 ID 的入口无需迁移。看板能显示历史缺口，但缺记录的卡片不提供执行动作。农具页的请求失败不再让帮工列表和技能库失去已有数据。

## Verification

- `agent` 的并发创建测试验证同名创建各有身份，指定 ID 的保存仍更新原记录。
- `handler` 验证频道创建返回可立即读取历史的 ID；`issue` 验证历史关联只包含真实执行和明确缺失。
- Flutter 验证不等状态帧即可选择新频道、农机失败不影响档案、运行时命令不再读取全部配置，以及缺执行记录时看板不补造状态。
- 消息的 Run 经流式更新与数据库读取保持不变；两轮只差 100 毫秒时，客户端仍只展示被关联的那一轮，无关联旧事件不混入。
