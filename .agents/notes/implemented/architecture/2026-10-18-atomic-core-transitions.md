# Agent Note: Core 提交完整状态，订阅者读取对应的因果变化

Status: implemented

## Problem

游戏订阅原始事实后自己再次 Reduce，以取得事实前后的状态；计划收到排队的汇报事件时却读取当前 Session，可能拿到事件之后的状态。消费者承担了事实与状态版本对应的知识。

计划的父子工单在数据库里是一次事务，核心状态却逐条更新；调用者必须先发子工单、最后发父工单，读取者仍可能在中间看见半个计划。

## Decision

Core 提供内部 Transition：在事实折叠时绑定该事实自己的 Before、Fact、After。消费者读取对应状态，不再重折核心状态或用最新状态推断过去。

相关事实用 ApplyBatch 提交：先在局部状态逐条 Reduce、收集效果和 Transition，再一次替换可见状态，最后按原顺序发布事实。每条 Transition 保留自己的真实 After；整个批次的最终状态只用于对外状态读取。

当前接口约定在 [Core](../../../../server/internal/core/README.md)。游戏只解释变化，不重新维护核心状态；计划用对应的 Session 解释汇报，再依据当前计划决定动作，避免用旧快照覆盖后来的编辑。

## Alternatives considered

**只保留子工单先于父工单的约定。** 排序不能把多次可见更新变成一次提交，调用者和消费者仍要理解中间状态。

**每条事实都附整个批次的最终状态。** 第一条事实会被赋予后续事实造成的变化，事件驱动的规则失去因果对应。

**增加对外 FactBatch 类型。** 原有事件消费者已经认识单条事实。内部提交和订阅保证足以解决问题，无需扩大生成协议和客户端的类型集合。

## Consequences

HTTP 事件仍逐条发送原有 Fact，读取 State 时只能看到完整提交。内部 Transition 保留所引用的不可变状态，因此依赖 reducer 不修改旧值的既有约定。

批次提交不替代数据库事务；工单先完成数据库事务，再发布核心状态。数据库与核心状态之间的恢复仍由拥有持久化的业务负责。

## Verification

- Core 测试断言首条事件可见时 State 已是完整批次，而每条 Transition 的 Before、After 只对应本条事实。
- 后续 Apply 不改变已交付的 Transition 和初始快照。
- 游戏账本和计划的完整流程在切换订阅后通过 race 回归。
