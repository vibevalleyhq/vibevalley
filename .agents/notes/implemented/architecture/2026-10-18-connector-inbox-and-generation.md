# Agent Note: 连接器的持久收件与账号代际

Status: implemented

## Problem

平台接受确认和管家完成回复不是同一件事。飞书先把消息放进内存就返回，进程退出后无法重放；微信把交付和翻页拆成两个回调，每个 Adapter 都要自己记住失败时不能翻页。登录、接收和重试又由几个调用方分别取消，旧账号的回调可能跨过账号替换继续写库。

## Decision

收件由 `voiceInbox` 拥有。平台交来的消息与游标一起持久接受，交给管家的工作在独立工人中完成。传输 Adapter 不知道去重查询、完成标记或管家的重试时机。当前行为见 [connector 的约定](../../../../server/internal/connector/README.md)。

账号由 `voiceConnection` 协调器拥有。登录任务只交回结果；协调器取消并等待旧代结束，再提交账号变更并启动新代。协调器不是自己等待的任务之一，登录成功不会自等待。SDK 的接受入口在接收返回时封口，并等正在写入的回调退出。

保留至少一次交付：SQLite 接受事务不能与管家的工具副作用组成一个事务。先保存接受、后交付，允许极窄窗口内重复，避免先记完成却永久丢失指令。旧版本只有去重标记，没有可恢复正文；迁移把这些行保留为已交付，不尝试猜出原消息。

## Alternatives considered

**继续使用内存队列，并在失败时不推进游标。** 能处理同一进程内的临时失败，不能恢复飞书已经确认的消息，也不能隔离跨账号的迟到回调。

**给命名任务表加 WaitGroup。** 登录任务本身会触发连接替换，直接等待任务表会等待自己。独立协调器把发布新账号和结束旧任务的顺序收回同一个所有者。

**声称端到端恰好一次。** 管家的执行可能已经产生文件或外部副作用，收件完成标记仍可能写失败；没有共享事务，不能做这种保证。

## Consequences

接受消息只等本机事务，不等管家回复；管家暂时不可用时，收件仍可落盘。成功交付后删去收件正文，只留下去重标记。退出会等待正在结束的旧代；Adapter 必须响应取消。重新登录或退出成功代表主人结束旧账号的连接，旧收件不会投递给新账号。

## Verification

`connector` 的测试覆盖：整页接受与游标一起回滚、重复页去重、真实数据库重开后恢复、管家成功而完成标记失败时再次交付、旧登录迟到结果、退出等待接收任务、服务停止等待管家交付，以及 SDK 在接收返回后的迟到回调。迁移测试覆盖旧去重行的已交付回填与重复升级。
