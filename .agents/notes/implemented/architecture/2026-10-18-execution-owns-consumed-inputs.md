# Agent Note: 执行拥有实际消费的输入、Run 和终结

Status: implemented

## Problem

管家在输入排队前创建 Run，再在全部工作停稳时把暂存的工单都按成功关闭。模型失败、未消费的排队输入和多条输入合进同一实际执行，没有共同的归属依据。日志又由管家单独写，不能从某张工单的 Run 找到完整事件。

派发队列只记排队时间，重试时重建成默认频道和普通工单触发；管家读取摘要时就标成已读，排队后取消也无法再取到这些汇报。两处都把“准备交付”当成“已经接受”。

## Decision

执行 owner 以实际消费和终结事件为准。一个实际 agent loop 对应一个 Run；首触发留在 Run 上，同轮实际消费的其他工单用关系表关联。未消费的输入不提前归入 Run，工单只在真实成功终结后关闭。

日志与 Run 由同一个 owner 排序；终结失败进入待终结状态，先按原结果完成重试，再接受新 Run 的输入。待终结与仍在执行是两种状态，不能共用“run id 非空”的判断。

派发队列持有待执行命令的来源，重试恢复频道和触发原因。摘要消息的回执由执行真正消费后提交；读取摘要只是准备上下文。调用者不需要在发送以后补一个确认步骤。

当前约定在 [session](../../../../server/internal/session/README.md)、[issue](../../../../server/internal/issue/README.md) 和 [manager](../../../../server/internal/manager/README.md)。

## Alternatives considered

**每张排队工单都先开一个 Run，结束时一起关。** 入队与实际消费可以隔着停止、失败和重启；它会产生从未执行的 Run，并把未消费的工单关闭。

**多个工单复制多份相同日志。** 一次模型请求和工具执行会出现多次，统计、排障和消息归属都失真。保留一个真实 Run，用关系表达多工单关联。

**终结写入失败后继续复用 Run。** 待终结的旧 Run 会吞入下一次独立启动失败。重试保留旧结果，恢复后新建 Run，不能只保留一个非空 id。

**让发送者确认摘要。** 发送成功只说明进了队列，无法证明模型消费；只有执行 owner 知道这条事件。

## Consequences

聊天和语音输入即使没有工单也有 Run。管家的频道参与者和农场核心状态仍保持自己的形状；这项决策不要求把管家变成占地的帮工。

Run 与事件文件仍分别持久化，不构成跨 SQLite 与文件的事务。终结落库失败不发布成功完成通知；工单关闭失败也不伪装成成功。消费回执失败会让摘要再次出现，接受重复上下文而不提前丢失它。

## Verification

- 管家执行测试覆盖成功、模型失败、启动失败、中断、多工单实际消费和未消费队列。
- 持久化终结失败后再次启动，两个输入归入不同 Run；重试和停机保留原失败结果。
- 队列测试覆盖直接重试、后台重试、频道与定时 missed 标记。
- 摘要测试取消一个未消费输入，下一次真实消费仍能取得摘要，并在 Run.Heard 中追溯。
