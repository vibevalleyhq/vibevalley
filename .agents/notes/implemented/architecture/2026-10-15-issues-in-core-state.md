# Agent Note: 工单进核心状态，有标题和说明

Status: implemented

## Problem

[工单是一样东西](2026-10-15-issue-is-one-thing.md) 把工单放在数据库里，不进核心状态，看板和地图隔几秒问一次。接下来要把种植计划并成带子工单的父工单（[概念先行](../../proposed/architecture/2026-10-15-concepts-first.md) 第 6 步），可计划在核心状态里、经 SSE 实时推给客户端，工单却靠轮询：两样要合成一样，就得放在同一个地方，不然就是两份。轮询还让看板上工单的状态最多晚 3 秒。

另外，计划有标题和目标，每一步有标题和要做的事，工单却只有一段 `text`。

## Decision

行为见 [server.md](../../../../docs/reference/server.md)「工单」。

- **数据库是家，核心状态有一份**，和定时、田头一样：开着的工单和最近关上的 50 张（`KeepClosedIssues`）放在核心状态的 `issues` 里，按看板的顺序（`IssueOrder`：没派的按排的先后，其余新的在前）。`Issues` 每改一次数据库就施加一条 `issue` 事实（删掉的是 `issueGone`），开机时从数据库放回去；`farm.json` 不存工单。
- **状态由折叠算**：`Reduce` 每折一条事实，都按帮工现在的样子重算工单的状态（`IssueStatusOf`），帮工开工、做完一轮，工单的状态当场就跟着变。
- **标题和说明**，和 Linear 一样：`title` 是一行，`description` 可以空。交给帮工的是标题加说明（`IssueJob`）；直接派出去的活（管家、计划）按第一行切成标题和说明（`SplitJob`）。迁移 `0007_issue_title.sql` 照同样的办法切开老工单。
- **客户端**：看板和地图从核心状态读工单，不再轮询；看板只在工单的执行变了、关上了的时候重新读轨迹头。比核心状态里留着的更早的关单，打开「更早的」时才问 `GET /api/issues`。

## Alternatives considered

**工单留在数据库，计划也搬进数据库，都靠轮询。** 少一种事实，可计划板就不再实时，工单的状态也一直晚几秒。

**全部工单都放进核心状态。** 简单，但关上的工单越积越多，每一帧都要带着它们。只留最近的，和以前计划只留最近 10 个是一个道理；现在两者合成一条：关上的工单连同它的子工单按家族留最近 `KeepClosedIssues`（50）家。

**只留 `text`，界面上取第一行当标题。** 不用迁移，但计划的标题和目标、步骤的标题和要做的事就没处放，标题也没法单独改。

## Consequences

- 工单的状态又和帮工一起实时变了。
- 每改一张工单就多一条事实，挪动待办时排过先后的每一张各一条。
- 写待办要分开填标题和说明；看板上在列里打一行就是标题。
