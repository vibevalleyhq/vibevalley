# Agent Note: PR Review：日常评审看证据，同题比较再评分

Status: proposed

## Problem

PR 评审需要同时回答三件事：需求做对了多少，改动是否值得保留，现在能否合并。同题实现比较时，总分用于辅助比较交付质量；合并门槛阻止已确认的严重缺陷进入主分支。文档、格式和测试数量的高分不能抵消资源泄漏、数据损坏或权限问题。

本稿用于有代码改动的 PR，覆盖功能、修复、重构及同题实现比较。纯文档、素材等任务按对应验收要求评审，不强套本表。具体仓库规则以评审时冻结版本的 [AGENTS.md](AGENTS.md)、[文档规则](docs/AGENTS.md)、[Note 规则](.agents/notes/README.md) 和相关子系统约定为准；本稿不另建一份规则清单。

## Proposal

### 日常 PR 的最小评审

日常 PR 记录固定 base/head、任务范围、已确认缺陷、执行过的检查、真实程序证据和未验证项；结论为可合并、请求修改或待验证。使用下文合并门槛，不要求计算十维总分。

下文百分制仅用于明确要求的同题实现比较，比较前固定口径与验证预算。十轮复测只在该比较或有不稳定性证据时执行；日常 PR 按变更运行必要测试，竞争问题用受控次序覆盖，不能用反复跑绿替代。


### 评分口径

| 维度 | 满分 |
|---|---:|
| 1. 完成度与正确性 | 15 |
| 2. 测试 | 15 |
| 3. 在真实程序上验证 | 10 |
| 4. 范围与大小 | 10 |
| 5. 仓库规矩 | 10 |
| 6. 杠杆：消除一类问题 | 10 |
| 7. 简洁与可维护 | 10 |
| 8. 文档与 Note | 5 |
| 9. PR 正文与诚实 | 10 |
| 10. 风险与回退 | 5 |
| 合计 | 100 |

评审开始时固定 `base_sha`、`head_sha`、规则版本、任务范围和验收清单。运行结果必须能对应到提交；提交变化后，旧结果只能证明旧版本。比较同题实现时使用同一个基线、问题集合、条目粒度及验证预算。

每项得分限制在 0 到该项满分，最后汇总并保留一位小数。证据不足标「待验证」，列出可能得分区间；未补齐前不发布确定总分。确认没有执行必需检查，属于已知缺项；仅无法取得记录，属于待验证。

每个发现分配一个编号，记录触发条件、影响、根因、证据和修复方向。区分新增回归、基线遗留问题、设计建议和未验证假设。同一根因的回归只扣一次；测试缺失、证据失实等另有事实依据时可分别计分，不按受影响文件数重复扣同一故障。

### 合并门槛

以下任一条件成立，结论为「请求修改」或「待验证」，总分不改变结论：

- 存在未解决的 P0/P1：P0 指已证实的严重安全、数据损坏或整体不可用问题；P1 指已证实的重要功能失效、资源泄漏或状态错误。分级必须写出实际触发条件和影响范围。
- 适用的必需检查失败，或必要运行验证尚未完成。基线已有失败须提供同环境复现，单列归因，不能笼统写成「环境问题」。
- 提交遗留会使其他用例不运行的 `.only`，或绕过检查而没有等价验证。
- 新引入或显著扩大的安全、数据、锁与资源风险尚无证据支持。

P2 是不构成以上阻塞、但有明确行为影响的缺陷。命名、排版或个人风格偏好不按 P2 回归扣分。

### 1. 完成度与正确性：15 分

有工单或 Note 时，从其验收条件建立实现清单。没有清单的开放式审查，先合并所有答卷和一名独立评审找到的候选，逐条确认、按根因去重、排除范围外条目，形成「已确认问题集合」。它不代表所有潜在问题，也不自动成为本次必须实现的清单。

开放式审查分别记录：

- 发现召回率 `R = 正确发现的条目数 / 已确认问题集合的条目数`。
- 发现精度 `P = 确认成立的独立问题数 / 答卷声称存在的独立问题数`。明确标为待验证的假设另列，不当作已确认发现；关键假设未裁决时诊断分待定。
- 实现完成度 `C = Σ(wᵢ × xᵢ) / Σwᵢ`。`xᵢ` 为做对 1、部分 0.5、没做或做错 0；权重默认 1，需要加权时在评分前统一确定。

「部分」须指出哪些验收已满足、哪些未满足；已实现部分违反关键不变量时不能记 0.5。延期项列出理由和处置，由评审确认是否属于本次义务，作者不能为了提高完成度自行从分母删除。

| 任务类型 | 得分 |
|---|---|
| 有明确验收清单的功能、修复或重构 | `15 × C − D` |
| 同时要求诊断和落地的开放式审查 | `5 × F1 + 10 × C − D`，其中 `F1 = 2PR / (P + R)` |

`D` 为引入回归的扣分：每个独立 P0 扣 5、P1 扣 3、P2 扣 1。未修复的基线问题通过完成度反映，不重复算新增回归。已确认集合非空而答卷未声称任何问题时，P、R、F1 均为 0；`P + R = 0` 时 F1 为 0。确认不存在范围内问题时诊断项不适用，将这 5 分归入实现验收，所有同题答卷使用同一口径。实现清单也为空时只出诊断结论，不强出交付总分。

证据为「条目 → 做对 / 部分 / 没做 → 提交中的文件行号或测试名」表。一个根因不能拆成多个函数、多个调用点来增加条目数。

### 2. 测试：15 分

| 子项 | 满分 | 计分办法 |
|---|---:|---|
| 红绿与行为保持 | 6 | `6 × 有效验证单元数 / 应验证单元数`；单元按独立行为或重构保证确定 |
| 不削弱测试 | 3 | 未解释的删除或放宽断言、新增跳过，每个独立缺口扣 1 |
| 稳定性抽查 | 3 | 新增或实质修改的相关测试连跑 10 轮：0 轮失败得 3，1 轮失败得 1，更多得 0 |
| 复用仓库测试设施 | 3 | 无理由重复已有设施、把待测业务本身模拟掉、用固定睡眠猜完成顺序，每处扣 1 |

有效红绿要求测试在固定基线和目标提交上均能加载并执行到目标断言，基线因目标行为不符而失败，分支通过。缺少新 API、导入失败或编译错误不算红灯。无法直接移植测试时，可在分支上撤回最小修复，保留测试和必要夹具；须记录反向补丁，证明没有改动被比较的行为。

纯重构不强造失败测试：旧行为断言保持约束并全绿即可。改名、夹具或接口调整可以改变测试文本，但须证明断言未被削弱。混合改动分别标明行为单元和重构单元，同一行为有多个用例不增加分母或重复得分。

稳定性记录应包含命令、环境、随机种子、10 轮各自结果及首次失败。不得先重试到通过再记为全绿。十轮全绿只证明抽查通过：在独立且每轮失败概率为 5% 的假设下，十轮全绿仍有约 59.9% 的概率。竞争与取消测试还应通过受控事件次序覆盖关键交接窗口。

仓库设施包括 scriptedRuntime、真实临时 git 仓库、faux 模型和 testing/until。专用的延迟门、测试替身和资源接缝可用于控制竞争，不因「自造 fake」扣分。按条件等待与固定睡眠赌顺序应区别判断；测试定时行为本身的受控延迟不受罚。

测试行数、测试声明数量和覆盖率只作描述指标，不直接换分。旧代码失败、新代码通过的证据也不等于开发过程确实先写测试；没有过程记录，不宣称采用了测试先行。

### 3. 在真实程序上验证：10 分

从冻结版本的 [命令表](AGENTS.md#命令)、改动路径及适用验证 skill 生成必跑检查矩阵。每漏一个独立检查能力扣 2；聚合命令已运行的子检查不重复要求，也不重复扣分。

改动触发 [acceptance](.agents/skills/vv-acceptance/SKILL.md) 的适用分册，却没有其要求的运行证据，另扣 4。仅纯函数改动等豁免按 skill 原文判断；没有模型钥匙或未获付费调用授权时，应记录验证边界，不擅自运行。

每次执行保留：提交 SHA、工作目录、命令、环境要点、退出码、测试文件数和通过/失败/跳过数，以及可访问的日志、截图或结果文件。末几行用于快速核对，完整产物支持复查。只给临时目录名、没有可取得的内容，不算完整证据。

### 4. 范围与大小：10 分

分别报告生产代码、测试和文档的新增与删除行数。生成物、testdata、锁文件和 CATALOG 不进入评分行数，但仍检查其业务含义；大规模测试和文档仍须有可执行的阅读分批方案。

评分行数 `L = 生产语义变更行数 + 0.1 × 可重放的生产机械变更行数`，行数按新增加删除计算。忽略纯空白差异并识别纯重命名。机械折扣要求独立提交、提供脚本与运行方式，并核对重放结果与该提交一致；手写业务差异不能混入折扣。测试和文档不直接推高 L，避免少写验证反而得高分。

关注点 `K` 是能够独立合并或回退、又不破坏其余改动目的的变化数量。共同完成一个行为所必需的接口、实现与测试属于同一关注点；标题出现「和、；」仅作检查提醒，不参与计算。

| 条件，按顺序匹配 | 得分 |
|---|---:|
| `L ≤ 500` 且 `K = 1` | 10 |
| `L ≤ 1,200` 且 `K = 1` | 8 |
| `L ≤ 2,500` 且 `K ≤ 2` | 5 |
| 超出以上，但按关注点分成可审查提交，每个提交主题清楚，并有该提交通过 check 的证据 | 2 |
| 其余 | 0 |

以上分档和 0.1 折扣是试评政策，不是研究证明的最优值。引用本仓库 P75/P90 时，须附采样范围、样本数、排除规则、计算方法和原始输出。历史分位数说明仓库习惯，不自动证明习惯合理。

### 5. 仓库规矩：10 分

每条违规引用冻结版本中的原规则和变更位置。规则的完整定义只保留在其所属文档，本项按后果区分扣分：

- 重项每个独立问题扣 3：破坏状态单源、业务归属、服务依赖次序、存盘约定或 Effect 的作用域与运行时边界等明确约束。
- 轻项每个独立问题扣 1：违反目录、命名、注释或穷尽处理等明确约定。

合法的 SDK 回调、Promise 与受管运行时桥接不等于在 Effect 内另起失控运行时。旧名字检查用于阻止已经决定淘汰的名字回来，不要求把每个新名字登记进去。批准的新设计可以修改现有约定，但须同时修改其权威文档，不能用「违反旧惯例」阻止有依据的改进。

基线已有且本次未扩大影响的违规单列，不按新增违规扣分；若修复它属于本次承诺，则计入完成度。规矩扣分与回归扣分不能仅因引用了同一处代码就自动叠加，须分别说明规则违例与行为后果。

### 6. 杠杆：消除一类问题：10 分

只评本次确定要解决的问题类别，在评分前固定类别粒度；不把单纯新增功能硬解释成系统性治理。层级对应 [工程流程](docs/subsystems/process.md) 的「代码、检查、文字」顺序。

| 层级 | 保证 | 证据 |
|---|---|---|
| L3 | 代码、类型或资源所有权使已定义的一类错误无法通过合法调用产生 | 不变量、调用边界及反例验证；不能仅以使用某个 API 或新类型为据 |
| L2 | lint、结构测试、回归测试、黄金数据或 CI 能拦住违规 | 将违规重新引入后，检查稳定失败 |
| L1 | 依赖文档、注释或人工遵守 | 规则明确，但没有可执行约束 |
| L0 | 只修眼前实例，没有防止同类错误的机制 | 局部补丁 |

得分为 `10 × 平均层级 / 3 − 未解释残留数 × 0.5`。残留仅限本次治理范围；语义相关的多个位置若属于同一根因，记为一个残留。

记录搜索命令、范围、匹配位置及逐项裁决。git grep 命中只是候选，不能把所有 Promise、Effect.gen 或 as 都算违规。结构搜索或反例测试适用于文本不能识别的同类问题。说明保留理由不能替代不变量：若合法调用仍能产生所声称消除的错误，就不能给 L3。

没有适用的治理类别时，本项标 N/A，不赠送 10 分；报告适用满分和按适用满分折算的百分制分数。同题答卷须使用相同类别集合，不能通过选择 N/A 改变排名。

### 7. 简洁与可维护：10 分

从 10 分开始扣，只统计本次新增或扩大的问题：

- 无依据的类型逃逸或检查屏蔽，每处扣 1；有集成边界理由、但仍把安全义务交给调用方的，每处扣 0.5。
- 仅转发参数，不拥有规则、不隐藏复杂度、也没有隔离或测试价值的新包装，每个扣 1，最多扣 3。
- 没人使用的导出、无意义的旧路径，每个独立问题扣 1。
- 评审者提供短至少 30% 的替代补丁，并证明行为、类型约束、诊断与清理能力等价，扣 2；没有补丁不凭印象扣分。

只有一个调用方不构成扣分理由。类型负例测试中用来验证非法调用被拒绝的 @ts-expect-error 不属于逃逸；有工具误报证据的定点关闭不等于掩盖缺陷。文字理由本身不能证明逃逸必要。

### 8. 文档与 Note：5 分

从 5 分开始扣：

- 每个用户可见行为或共享约定变化，所属子系统文档缺少对应更新，扣 1。一个行为涉及多处实现仍只算一项；纯内部重构不强加行为说明。
- 已完成并确认的决定仍错误标为 proposed，扣 1；仍待决定或未完成的提案不扣。Note 的沉淀与删除按 [Note 规则](.agents/notes/README.md) 执行。
- 同一事实形成两份需同步维护的权威定义，扣 1。PR 摘要、带提交版本的历史评审和链接引用不因此扣分。

由本次改动导致 docs:verify 不通过，本项为 0，并进入合并门槛。尚未运行属于待验证，不能写成检查已失败。

### 9. PR 正文与诚实：10 分

| 子项 | 满分 | 计分办法 |
|---|---:|---|
| 结构 | 2 | 标题不超过 100 字且说清结果得 1；正文交代变化、验证、未覆盖与风险得 1，不要求恰好三段 |
| 说法准确 | 6 | 核验声明全对得 6；至少 90% 得 4；至少 70% 得 2；其余得 0 |
| 未验证边界 | 2 | 每个事先确定的关键场景未验证且未披露，扣 1 |

评审者优先抽取数字、范围承诺和「全部、不再、保证」等实质声明，核对最多 10 条；高风险声明必须全部核对，超过 10 条时按实际条数计算。声明不足 10 条时全部核对，无可核对说明时准确项为 0。禁止用琐碎事实挤掉关键承诺。任一关键声明尚待验证，则该小项待定。

已披露的限制仍可能阻止合并，但不按隐瞒扣分。未覆盖范围以需求与风险清单为准，不无限追问任意场景，避免奖励冗长免责文字。证明作者的验证声明错误时应更正记录；不能从结果不符推断其主观动机。

### 10. 风险与回退：5 分

从差异路径开始识别风险，再追踪调用链；路径没有命中不代表没有风险。

| 风险面 | 需要核对 |
|---|---|
| 线上契约 | 请求、响应、事件及旧客户端的可用边界 |
| 存盘与外部副作用 | 表、家目录文件、外部资源；代码回退后已有数据怎样处理 |
| 安全边界 | LAN、语音、HTTP、密钥与授权 |
| 锁、队列和启动关闭 | 依赖顺序、死锁、取消、重复调用、迟到结果 |
| 性能与运行成本 | 时延、内存、积压上限、慢消费者隔离及额外外部调用 |

每个适用风险面须写出影响、测试或验证证据、回退或止损步骤，以及回退后的检查。任一部分缺失，该风险面扣 2，同一风险面不重复扣，最低 0 分。确认没有适用风险面时，应附差异审查理由。

回退不止写「git revert」：说明哪些已发生的存盘或外部操作不会随代码恢复，如何停止继续产生影响，怎样验证恢复结果。性能预算在评审前确定；有界局部队列不能作为端到端有界或业务不受慢客户端影响的证明。

### 评审记录模板

#### 版本与结论

| 字段 | 内容 |
|---|---|
| PR、任务原文、任务类型 | 待填 |
| base_sha / head_sha / 规则版本 | 待填 |
| 验收清单版本、范围及排除项 | 待填 |
| 总分 / 适用满分；待验证分数范围 | 待填 |
| 合并门槛 | 通过 / 请求修改 / 待验证 |
| 阻塞发现编号与最小修复 | 待填 |

#### 条目与证据

| 条目 ID | 验收条件或已确认问题 | 本次义务 / 延期 / 范围外 | 做对 / 部分 / 没做 / 待验证 | 证据：SHA、文件行号或测试名 |
|---|---|---|---|---|

## Alternatives considered

**十项各 10 分，主要依赖评审者判断。** 不采用。完成度和测试合计 30 分，且每项给计算口径与证据，能减少文档和风格分掩盖行为错误。

**照答卷并集计算所有实现义务。** 不采用。并集适合衡量发现能力，落地义务还受范围、收益和依赖约束；诊断用召回与精度，实施用确认后的验收清单。

**按代码行数、测试数量和工具名称自动扣分。** 不采用。规模数据只能描述评审成本；单调用方抽象、条件等待和测试类型负例可能是正确设计。自动检查负责收集候选，裁决仍须对应行为或明确规则。

**只扣严重缺陷分，不设门槛。** 不采用。其他维度的分数无法补偿安全、数据和资源生命周期缺陷。

## Acceptance criteria

- 选取 5–10 个已完成评审的代码 PR，覆盖功能、修复、重构和开放式审查；固定提交、规则、适用项及证据。
- 两名评审者独立评分。单个维度相差超过 2 分时，记录分歧来自事实、严重度还是计分口径，先修模糊规则，再调整阈值。
- 每个得分和扣分均能追到条目、声明、命令结果或具体代码；同根因重复扣分和因缺证据猜分的情况清零。
- 每个红灯均来自目标断言；编译、导入和夹具不兼容不计为有效红灯。
- 规模统计能重放并区分生产、机械、测试、文档及排除项；涉及分位数时提供样本与计算结果。
- 有阻塞缺陷的 PR 无论总分多少都不得通过门槛；同题答卷不得通过调整清单或 N/A 获得排名优势。
- 试评结论获得确认后，再决定是否沉淀为仓库评审约定或检查工具；不为复现某两份答卷的预期排名调整规则。

## Risks

- 并集只能覆盖已发现的问题。对同题实现报告召回时，明确参照的是已确认集合，不能宣称发现了仓库全部问题。
- 新增不必要的类型、封装或 lint 可以刷杠杆分。L3/L2 必须有反例和调用边界证据，机制成本仍由简洁与范围项约束。
- 固定阈值可能使作者少写测试或拆成无法独立理解的碎片。生产、测试、文档分开统计，关注点按行为依赖判定。
- 评分本身有成本。先执行静态检查和合并门槛；同题比较需要完整评分，普通小改动可只做验收，但不能把未评维度填满后宣称完整分数。
- 试评期间本稿只定义评审方法，不修改 CI 或现行合并权限。研究和历史样本用于校准，不代替对当前改动的证据判断。
