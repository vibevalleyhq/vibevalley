# Agent Note: 给仓库做体检：读数指出先看哪里，只有类型逃生口是棘轮

Status: proposed

## Problem

挡问题的手段（[四层](docs/subsystems/process.md)）都在「拦」：lint、测试、`docs:verify` 拦下写错的东西。拦不住的是慢慢变坏：一个文件越改越大、两个模块总是一起改、写下去的代码几天后又被改掉。这些在单个 PR 里都看不出来，人也没有精力每个 PR 细看。

2026-10-29 的两次审查都是凭印象挑的地方：上一轮拆了 `connector/connector.ts`（879 行），按「改动次数 × 行数」它不在前十；排第一的是 `channel/chat.ts`（30 天 34 次改动、1982 行），其后是 `issue/issue.ts`（42 次、1262 行）、`session/session.ts`（29 次、1312 行）。凭印象挑会挑错。

医生的做法可以借：几项生命体征天天量，和这个人自己的过去比，异常了再做专项检查；指标是筛查，不是诊断；报警太多就没人看。

## Proposal

一个包 `packages/health`（`@vibevalley/health`），三层：读 git 和源码（`collect.ts`）→ 纯函数算读数（`readings.ts`）→ 报告和棘轮（`report.ts`、`cli.ts`）。包不认识 VibeValley：算哪些文件、怎么分区（服务端照 `modules.ts`）、哪些文件本来就热、棘轮放在哪，由仓库的配置给（`scripts/health.config.ts`）。纯函数不碰 git 和文件，以后能搬进 `apps/server/src/project`，给主人的项目做体检。

读数分两种：

- **报告**：只排出先看哪里，不拦合并。对象是一个文件或一个区，和这个仓库自己的前一个窗口比。
- **棘轮**：只许减不许增，CI 查。只给数得清、意思明确、没有动机去刷的读数。

分四步，每步一个 PR：

1. **热点和逃生口的棘轮**（做完了）。热点是 30 天的改动次数乘行数，改过名的文件跟到今天的名字（`git log -M`），一次动了 500 个文件以上的改动算机械的；本来就热的（`shapes.ts`、`schema.ts`、`api.ts`）带理由放在一边，文件不在了理由就过期。逃生口是 `x!`、`as unknown as`、关掉 lint 的注释，用 oxc 解析数，按区记在 `scripts/health.ratchet.json`；少了也失败，要求降棘轮。
2. **代码存活率**：一个 PR 新写的行，14 天后用 `git blame` 看还归在它名下的比例。agent 写的代码一次写对和写完反复修，测试都是绿的，这一项分得开。按 PR 算，报告列最低的几个和按区的中位数。
3. **跨模块一起改**：两个文件一起出现在 PR 里的支持度和置信度，只报分属不同区的。契约和用它的地方一起改是正常的，写进配置当作本来就有的。
4. **回测和取舍**：第 t 周的热点能不能预测第 t+1 周的低存活率；预测不了的读数删掉。之后再考虑变异测试，只对 `rules` 里的纯函数。

报告同时出 JSON（`--json`），让管家拿排第一的热点开一张工单，接上[用 VibeValley 开发 VibeValley](.agents/notes/proposed/process/2026-10-18-build-vibevalley-with-vibevalley.md)。

## Alternatives considered

- **设门槛**（文件不超过 N 行、圈复杂度不超过 M）：agent 会照数字机械地切文件，读数好了，代码没变好。只有逃生口做成棘轮。
- **和行业的数比**：仓库的大小、阶段、写代码的方式（agent 写、PR 很大）都不一样，别处的阈值没有意义；和自己的前一个窗口比。
- **放在 `scripts/`**：`scripts/` 里是拦问题的检查；体检要自己的测试、依赖（oxc 的解析）和以后给主人的项目用，所以是一个包，仓库只留配置。
- **用 TypeScript 编译器数逃生口**：仓库用的 TypeScript 7 是原生实现，没有 `createSourceFile` 这类 JS 接口；Vite+ 带的 oxc（`vite` 的 `parseSync`）解析出带 TS 节点的 AST，不另加依赖。
- **把历史读数存起来画趋势**：要另维护一份数据；热点和存活率本来就从 git 历史算，过去某个窗口的数随时能重算。

## Acceptance criteria

- `vp run health` 出报告；`vp run health:verify` 跑包的测试再对棘轮，在 CI 的 check 里。
- 在一个算进去的文件里加一个 `x!`，`--check` 报出那一区，退出 1；删掉一个，也退出 1，要求 `vp run health:write`。
- 第 2、3 步各自有测试（手搭的 git 仓库），报告里有对应的一节。
- 第 4 步的回测结果写进本 Note，留下的读数写进 [工程流程](docs/subsystems/process.md)，删掉的写明为什么。

## Risks

- **历史太短**：仓库从 2026-10-16 开始，前一个 30 天的窗口是空的，报告注明「历史不够，不比」。第 4 步的回测要等到有两三个月的历史。
- **大 PR 让热点失真**：squash 以后一个 PR 是一个提交，功能 PR 常常动一两百个文件，每个文件都记一次改动。机械改动的界线（500 个文件）是看这个仓库的分布定的，只排掉了整棵树的重写；改名、格式化这类 PR 如果落在 500 以下，会抬高一批文件的数。
- **棘轮让小改动变红**：删掉一个 `!` 也要跑 `vp run health:write`。这是有意的，失败信息里写了要做什么。
- **读数被当成考核**：报告每一节写明它提示什么；不把热点当成 PR 的门槛。
