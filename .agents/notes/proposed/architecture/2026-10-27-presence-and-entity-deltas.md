# Agent Note: 页面的连接接着带上在线状态和工单的增量

Status: proposed

## Problem

频道的消息已经按频道走 Effect RPC（[频道](docs/subsystems/channel.md)「页面按频道订阅」）。同一条连接还缺两样聊天室和 Linear 都有的东西：

- **服务端不知道主人在不在看。** 连接器的发件表每条马上发：主人坐在电脑前看着群聊，同一句话照样推到微信。
- **工单、计划、帮工仍是整份状态帧。** 工单多了以后，任何一条事实都把它们全部推一遍；页面没有「我看到哪了」的游标，断线回来只能重拿一整帧。

## Proposal

### 1. 在线状态

`Subscriptions` 加一个流式的 `presence.attend({ device })`：页面在前台时一直开着，服务端开始时登记这台设备，客户端断开时 RPC 服务端中断它，收尾里注销；`presence.focus({ focused })` 报前台和后台。服务端的 `Presence`（Collaboration）记每台设备，给出 `ownerHere` 和它的变化。连接器的发件表在 `ownerHere` 时先不推；主人离开时，没读过的（按已读游标）再推，读过的不推。

这一版只有一个主人；设备按连接记，「是谁」留在连接上，以后要多人时加在这里。

### 2. 工单、计划、帮工的增量

照 Linear 的同步：服务端在出帧的地方按 id 比较前后两帧，只发改了的实体，带全局序号；页面记住最后的序号，重连时带上它，服务端从内存里最近一段改动补，太旧了发整份快照。走同一条连接（`core.entities({ after })`）；状态帧最后只剩命令行和调试用。

## Alternatives considered

- **在线状态用心跳加过期计时**：要自己定间隔和过期；RPC 的流在客户端断开时就被中断，收尾就是离开。
- **工单也按频道订阅**：工单是全局的实体，不是在一个频道里说的话；按 id 的增量比按频道订阅合适。

## Acceptance criteria

- 主人在电脑上看着群聊时，管家的话不推到微信；切到后台或关掉页面，没读过的推过去，读过的不推。
- `/api/v1/state` 不再随每条事实推整份；页面断线重连后按序号补齐，工单板不重画。
- 测试：`Presence` 的登记和注销（真的 WebSocket，断开即离开）；连接器在主人在看时不推、离开后推没读的；增量补齐和快照的分界。

## Risks

- 主人开着页面却不在电脑前：前台判断靠浏览器的 `visibilityState` 和焦点，离开座位不会被发现；要不要加「多久没动就算离开」，量过再定。
- 增量和快照要用同一套比较；比较本身花的时间随实体数增长，要量。
