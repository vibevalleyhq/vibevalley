# Agent Note: 工单为本：完成是主人对工单的结论，合并只是交付的一种

Status: proposed

## Problem

VibeValley 以工单为单位：工单写明要什么、怎么算完，帮工的每一轮只是一次尝试，同一张工单可以重开、换人、拆成子工单。可工单怎么结束，现在不是由工单说了算：

- **已完成只有一条路，就是合并。** 帮工的工单从等你看挪到已完成，`statusMove` 给的挪法是 `merge`（`apps/server/src/issue/moves.ts`），`harvest.ts` 的 `merge` 要么本地合进主分支，要么开 PR。查一下原因、跑一遍检查、确认已经修好了，这些工单没有提交，本地合照样「成功」（「这一单没有新的提交」），关成 `merged`；用 PR 的项目会去开一个空 PR。有提交、这次不想合的，只能挪到已取消，看板上一件做完的活成了「不做了」。
- **关单方式一个字段两个意思。** `IssueClose` 是 `merged`、`merged_into_graph`、`answered`、`dismissed`、`lost`：前两个说代码去了哪，`answered` 说管家答完了，`dismissed` 说不做了，`lost` 是事故。看板要从它反推「完成了没有」（`issue/state.ts` 的 `closedStatus`）。
- **关单规则按「谁做的」分叉。** 帮工的工单走 `merge`；派给管家的工单另有一套挪法（`orchestratorMove`：`answered`、`putAway`，结局记在 `handedBack`）；种植计划的步骤跟着计划走，关成 `merged_into_graph`。同一件事三套规则，加一种做活的人就要再加一套。
- **工单事先不说交付什么。** 「查一下」只能写在说明里，帮工照样可能改文件、提交；完成时只能看有没有提交去猜它是哪种活。

## Proposal

一句话：**工单定义要什么、怎么算完；执行是一轮一轮的尝试；完成是主人对工单下的结论；交付是完成时对工单产物的处理，去哪由工单在层级里的位置决定。**

### 一、工单写明交付物

`Issue.deliver`：`change`（改动，进项目）或 `answer`（结论，写在工单上）。不填是 `change`。

- 写工单的时候定：主人说「查一下」「为什么」，管家记成 `answer`；起草的帮工可以建议改它，主人拍板。
- `answer` 的工单，帮工在工单自己的 worktree 里只读，交回来就重置（和起草同一个办法，抽成一个函数）；交回的最后一个 json 代码块是结论（`conclusion`、`evidence`、`unsure`、`next`），服务端读进 `Issue.answer`。读不出结论或没有依据，这一轮算没做成。
- 派给管家的工单就是 `answer` 工单：管家的回答就是它的结论。

### 二、关单拆成结论和交付

| 字段 | 取值 | 谁定 |
|---|---|---|
| 结论：`status` | `done`（完成）、`canceled`（不做了） | 主人 |
| 不做了的原因：`Issue.canceled` | `dismissed`（主人关的）、`lost`（干活的目录丢了） | 主人或服务端 |
| 交付：`Issue.delivered` | `merged`（项目主分支）、`merged_into_parent`（父工单的分支）、`pull_request`、`kept`（分支留着不合）、`none` | 完成时算出默认，主人可改 |

`closed` 和 `IssueClose` 删掉。现在的关单方式对过来：`merged` 是完成、合进主分支；`merged_into_graph` 是完成、合进父工单的分支；`answered` 是完成、没有交付；`dismissed`、`lost` 是不做了。不留兼容：表结构直接改，本机的旧库作废。

### 三、完成只有一个挪法

等你看挪到已完成是 `complete`，带交付方式；默认值由工单算，不由谁做的算：

| 交付物 | 分支上有没有提交 | 默认交付 | 还能选 |
|---|---|---|---|
| `change` | 有 | 合进上级：子工单进父工单的分支，顶层进项目主分支；项目用 PR 时开 PR，PR 合了才算完成 | 留着分支（`kept`） |
| `change` | 没有 | `none`，收获清单上写「这一单没有改动」 | — |
| `answer` | — | `none`，结论在工单上 | 照结论起一张改动工单，`parent` 指向这张 |

验收的规矩不变：`required` 没通过、最后一轮没做成，都不能完成。交付是完成的一部分：合不进去（冲突、检查没过）就不算完成，工单留在等你看，和现在一样。不做了的工单分支上有提交就留着，也和现在一样。

### 四、谁做的不改变工单怎么走

- 派给管家的工单、帮工的工单、计划的步骤，都是同一套状态和挪法。`orchestratorMove`、`answered`、`putAway` 删掉；`handedBack` 由这张工单最后一次执行的结局代替（管家的一轮也是工单的一次执行）。
- 种植计划是一张有子工单的工单，步骤是子工单：步骤的交付进父工单的分支，计划推进时调同一个 `complete`；整个计划完成时，父工单的交付进项目主分支。
- 看板、命令行、管家的工具都走 `complete`：管家的 `merge` 工具并进 `issue_status` 挪到已完成（带交付方式），落地仍要这一轮有主人的话。

### 五、叫法

农场里「收获」就是完成：地收了，不管有没有代码合进去。收获清单写这一次的交付：「合进 clock-in 的 main」「开 PR」「合进计划 #12 的分支」「留着分支，不合」「没有改动」「结论」。看板上是「已完成」。

### 步骤

每一步单独能上线：

1. 关单拆成结论和交付；`complete` 一个挪法，没提交时交付 `none`，有提交时能选留着分支；不开空 PR。改 `packages/protocol` 的形状和 `issue` 表，`moves.ts`、`harvest.ts`、`attention.ts`、页面的收获清单和看板。已经做了，现状在[工单](docs/subsystems/issue.md)「完成和交付」；帮工离开的方式另成 `SessionClose`（多了 `completed`），不再和工单共用一个类型。
2. 派给管家的工单并进同一套：删 `orchestratorMove` 和 `handedBack`。
3. `Issue.deliver` 和 `answer` 工单：只读的执行、`Issue.answer`、`parseAnswer`，管家记「查一下」时填它。
4. 计划的步骤改走 `complete`，交付进父工单的分支。

## Alternatives considered

**按有没有提交自动判。** 前一版的提议：有提交就收获，没有就收下。它是事后去猜工单是哪种活：「查一下」的帮工顺手改了文件，完成时就变成了合并；工单也没法事先告诉帮工别改代码，验收也不知道该验一份结论还是一处改动。交付物要在工单上，由主人和管家写工单时定。

**给工单加种类，每种一套规则。** 取代的那篇 Note「查询是一种工单：帮工只读地查，交回一份有依据的答案」的提法：`Issue.kind` 是 `change` 或 `question`，查询另有关单的挪法。按种类分叉和现在按「谁做的」分叉是同一个毛病。交付物只决定帮工怎么干、完成时默认怎么交付，生命周期还是一套。本文取代那一篇，它的帮工规矩（只读、交回就重置、结论的格式）并进第一节。

**接着往 `IssueClose` 里加 `kept`、`none`。** 一个字段两个意思越来越多，看板、站位、统计都要从关单方式反推「完成了没有」。

**完成和合并分成两步，先完成、再单独合并。** 完成以后工单关上了，合并要是冲突或检查没过，工单该回哪里、谁来修都说不清。交付是完成的一部分：合不进去就不算完成。

## Acceptance criteria

- 一张没有提交的 `change` 工单能完成，交付是 `none`，git 没有动；用 PR 的项目不开空 PR。
- 一张有提交的工单能选「留着分支，不合」完成，看板上是已完成，分支还在。
- 派给管家的工单和帮工的工单走同一个 `complete`，`moves.test.ts` 里没有按做活的人分叉的分支。
- `answer` 工单交回后 worktree 回到主分支、没有提交，结论在 `Issue.answer`；读不出结论这一轮算没做成，不能完成。
- 计划的步骤完成时交付进父工单的分支，整个计划完成时父工单进项目主分支；`merged_into_graph` 不再存在。
- 看板、命令行、管家的工具对同一张工单给出同样的挪法和同样的拒绝原因。

## Risks

- **改动面大。** 协议、表、挪法、站位、收获、计划、页面、管家的工具都动；按步骤分开上线，每一步的黄金数据（`core/testdata/rules.jsonl.gz`）都要重写、看过 diff。
- **交付物填错。** 管家把要改代码的活记成了 `answer`，帮工只读、改不了；工单页能改交付物，改了以后下一轮按新的走。
- **PR 项目的完成是异步的。** PR 开了到合上之间，工单一直在等你看；和现在一样，只是收获清单上写明在等 PR。
- **农场的画面要跟。** 收获的动画和清单按交付分几种说法；地块的状态不变。
