# Agent Note: 一块地上几个人一起种

Status: proposed

## Problem

一块地就是一张工单（[工单](../../../../docs/subsystems/issue.md)），现在一张工单只派给一个档案：一次派一个帮工，重开再派下一个。主人想要的更像一班人：

- **@ 谁就是叫谁下地**：在田头 @ 另一个档案，它就来这块地上帮忙，不用另开工单。
- **分工**：一个写代码，一个写测试，一个看改动挑毛病；验收不一定是主人或管家，可以派一个「看地的」帮工。
- **配好的一班人反复用**：主人早就说过要有「小队」，照一份方案组织不同的 agent 干活（原来写在 [Run 和 Session](../../implemented/architecture/2026-10-16-runs-and-sessions.md) 的提案里，那两层落了，小队没做）。

设计稿第四、五节画过（`design/issue-farming/index.html`）。

## Proposal

**一块地可以有几个人：主种、帮手、看地的。锄头只有一把。** 代码活一块地一个 worktree，两个人同时改会打架，所以写的权利像接力棒：谁拿着锄头谁改，别人能看、能说、把意见交给拿锄头的。不是代码活就没有锄头这回事。

1. **地上的人**：工单记一份 `crew`（档案和角色：主种、帮手、看地的）和锄头在谁手上。现在的「地上的人」是做过这块地的帮工，只用来显示。
2. **@ 下地**：田头里 @ 一个档案、话挂在这张工单的串上，就给它在这块地上开一个 Session（帮手，不拿锄头），它读工单、串和改动；要改代码时锄头交给它。锄头怎么交：主种交回这一轮就放下，下一个被 @ 的接过；也能由主人或管家指定。
3. **看地的**：验收方式多一种「派一个看地的」：工单交回来，农场派一个和主种不同的档案读工单的验收标准和改动，逐条打勾，再调 `issue.accept`（过、或者带着草不过）。验收标准在聊清楚时写下（工单上一份 `criteria`）。
4. **小队**：一班配好的档案加一份方案（谁先、谁接着、谁看、什么时候交回主人），派给小队就照方案开 Session。方案和种植计划的 DAG（[Task 是 DAG](2026-10-18-tasks-are-dags.md)）用同一个引擎，计划是管家临时拆的一份，小队的方案是存下来反复用的一份。

先做 3（看地的），它最独立、最能减轻主人的验收；再做 1、2；4 等前面稳了再设计。

## Alternatives considered

**几个人用几张工单。** 不用改模型；但同一件活拆成几张，验收、收获、看板都各算各的，主人要自己拼回来。一块地一张工单，人可以几个。

**两个帮工同时改同一个 worktree。** 快；但改同一批文件会互相覆盖，提交也会交错。锄头一把，靠交接。

**看地的就是管家。** 已经能做（管家的 `accept` 工具）；但管家要同时管全农场，逐条读改动又贵又慢；派一个专门的档案更像人的做法，管家只在拿不准时出面。

## Acceptance criteria

- 一张工单派一个看地的：它读改动、逐条判验收标准，`issue.accept` 过了地就结果、没过地就长草；测试用 `oartest` 和真的 git 仓库。
- 田头 @ 一个档案，它在这块地上开一个 Session，「地上的人」里多它一个；锄头交给它以后它能改代码，另一个不能。
- 地块详情里看得到每个人的角色、谁拿着锄头、每一轮是谁干的。

## Risks

- 上限：一块地上几个 Session 都占农场和项目的并发数，看地的也算。
- 看地的和主种用同一种农机、同一个模型时，挑毛病的效果有限：默认挑和主种不同的档案。
- 交接锄头时上一个人没提交的改动要先提交，不然下一个接手时工作区不干净。
