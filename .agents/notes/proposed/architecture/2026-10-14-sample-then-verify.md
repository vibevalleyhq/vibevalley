# Agent Note: 先采样，再验收：规划和运行分开，故障回流成样本

Status: proposed

这里的「验收」指种植计划里先写好、写好就冻结的那一步检查（`protocol.AcceptancesOf`）；工单交回来以后主人或管家判过没过的「验收」是另一件事，见[工单](docs/subsystems/issue.md)。

## Problem

帮工交回来的东西，农场一直当结论收：帮工说做完了，就在它自己的 worktree 里跑它自己能改的检查，过了就合；没过就在同一个会话里让它接着改，最多两次。这样有几种坏法，用 coding agent 修代码的人都见过：

- **改测试让它过**：检查命令跑的测试就在帮工的分支上，它把断言改松、把用例删掉，检查就过了。
- **没抓住问题的测试**：测试写在修复之后、由同一个帮工写，修复前跑它多半也是绿的。它只说明代码和测试一致，说明不了问题被修了。
- **越补越歪**：没过就在同一个上下文里接着补。前几次走错的路都留在上下文里，第三次往往比第一次还差。
- **修好的东西下次又坏**：上次怎么坏的只留在那个帮工的会话和主人的记忆里，下一个帮工不知道。
- **同一件事每次都花一轮模型**：定时任务和巡查发现的固定套路，每次都叫醒管家想一遍，每次想得还不完全一样。

有一套做法正好对着这些：**规划和运行分开**。规划时，智能体按需求和 MCP 工具的定义写一段 JS 工作流，再严格按工具定义造 mock 数据，用 mock 跑工作流来验收。验收过了，工作流才进运行时；运行时不调模型，照着跑。运行中出了故障，就退回智能体：把故障当新样本，重新采样、测试、修复，再上线。

本文要做的是把这套做法背后的想法用到 VibeValley 上，主要用在帮工修代码上，其次用在农场自己的自动化上。

## 背后的想法

这套做法表面上是「先写 JS 再运行」，真正起作用的是下面七条。VibeValley 拿来用的是这七条，不是 JS 本身。

1. **模型的一次输出是一次采样，不是结论。** 同样的输入再问一次，答案可能不一样。一份产出可信，不是因为模型说得笃定，而是因为它过了一个验证者。
2. **验收先于产出，由另一只手写，产出的一方改不动。** 规划和运行分开，本质是权限分开：规划时想写什么都行，但碰不到真东西；运行时碰得到真东西，但改不了规则。拿到修代码上，就是测试在修复之前写好、写好就冻结，修的一方只能改代码。
3. **契约是两边唯一共享的东西。** 工具的定义（MCP 的 schema），在代码里就是接口、protocol 的形状、测试。mock 从契约造出来，验收就便宜、离线、能重放。VibeValley 已经是这样：形状只在 protocol 定义一次，规则的黄金数据是几千条带种子的随机输入，服务端测试用 `oartest` 扮演帮工、用 `FauxProvider` 当模型。
4. **先红了，才算抓住。** 修复之前就通过的验收，什么也证明不了。验收必须先失败，失败在问题本身上，修完再通过。
5. **故障是样本，不是事故。** 每次故障留下一个复现，样本只增不减，像棘轮一样只往一个方向走。经验存在样本里，不存在模型的上下文或记性里。修代码时，样本库就是仓库里的测试：验收步骤写的测试随计划合进主分支，以后每次跑测试都在重放这次故障。
6. **修不好就重新采样，别在脏的上下文里打补丁。** 带着前面的失败样本开一个干净的会话，比在同一个会话里补第三次好。
7. **能编译成程序的，就别让模型留在热路径上。** 运行时不带智能，便宜、确定、能重放；模型只在规划时和出故障时出场。

对照起来：

| 那套做法 | 帮工修代码 | 农场自己的自动化 |
|---|---|---|
| 需求和 MCP 工具定义 | 要修的问题、项目的接口和测试 | 主人说的「每天……」、`/mcp` 上的农场工具 |
| 写 JS 工作流 | 帮工写修复 | 管家写一段农活脚本 |
| 按工具定义造 mock | 验收步骤写现在会失败的测试 | 按工具的 schema 造输入，用轨迹里录下的真实调用当返回 |
| 用 mock 跑来验收 | 农场跑冻结的验收，帮工改不动 | 农场用 mock 跑脚本，加上以前的样本 |
| 投入运行时 | 收获进主分支 | 脚本挂到定时上，在 moejs 里跑，不调模型 |
| 故障退回、重新采样 | 故障变成新的验收步骤，开新的帮工去修 | 失败的调用序列存成样本，退回管家改脚本 |

## Proposal

分四步，每一步单独可用、单独提交。

### 1. 验收先行（已做，2026-10-14）

种植计划的一步可以是**验收步骤**（计划的步骤现在是子工单，标在 `IssueTask.acceptance`；规则读的 `Task` 由它拼出来，[种植计划是带子工单的父工单](docs/subsystems/task.md)）。现在的行为见 [种植计划](docs/subsystems/task.md)的「验收」。要点和理由：

- **规划时写，排在最前面**：规划的帮工（`session/rules.go` 的 `SplitBrief`）在修 bug、或要做的事能用测试说清楚的时候，把第一步拆成验收，别的步骤都等它。它只写现在会失败的测试，检查命令只跑这些测试。这是想法 2：验收和修复由不同的帮工、在不同的时候写。
- **农场判红**：验收步骤做完，检查要**不通过**才合；通过了就退回去，说它没抓住问题。这是想法 4。
- **合进去就冻结**：农场记下验收步骤改了哪些文件（`frozen`，从计划分支分出来以后改的，提交没提交的、新加的都算），后面的步骤改了这些文件就退回去，让它恢复原样、从代码上修。选择退回而不是悄悄恢复：悄悄恢复会掩盖帮工的意图，帮工也学不到「验收不能动」。
- **最后一步判绿**：没有步骤等着的步骤做完，要跑它前面每个验收的检查。中间的步骤不跑：长活里前半段（比如只改了数据层）本来就过不了验收。
- **判断由农场做，规则是纯函数**：`IsAcceptance`、`AcceptancesOf`、`AcceptanceChecks`、`FrozenTouched` 是 Go 的 protocol 包里的纯函数，黄金数据覆盖它们；服务端 `tickets` 包的 `Tasks.verified` 只负责跑命令和退回。验收的状态（`acceptance`、`frozen`）在核心状态里，计划板上能看到。

### 2. 故障回流成样本，重新采样（待做）

- **故障从哪来**：收获进主分支以后，项目的测试挂了，或者主人说「坏了」；计划的一步重试用完了；一张工单一轮没做成。
- **修从样本开始**：修的时候开一张修复计划，第一步就是验收，要复现的正是这次故障。规划的帮工拿到的是故障的证据，不是一句「修一下」：失败的命令和输出、轨迹里出错的那几次工具调用、引入问题的提交。验收必须失败在这个证据上，失败的输出要对得上，而不只是「失败了」。
- **重新采样**：一步被退回时，第一次照旧在原来的会话里改，这样便宜。再退回时，农场改派一个新的帮工，在从计划分支新开的 worktree 里做。它拿到的是工单，加上前面每次失败的样本：做了什么、为什么被退回、命令输出的结尾。它不接前一个帮工的对话。这一条要量一下：比较「同一会话重试两次」和「第二次换新会话」做成的比例和花的钱，数据从计划的经过（`task_event`）里来。
- **样本库就是仓库里的测试**：验收步骤的测试随计划收获进主分支，不另建一张样本表。以后的每个计划，最后一步跑整体测试时，都在重放以前的故障。

### 3. 农活脚本：管家写、农场验、moejs 跑（待做）

给反复做的农场自动化用：定时任务、巡查发现以后的固定处理、「测试红了就派帮工」这类套路。修代码不用这一步。

- **规划**：主人说「每天早上……」，管家（或一个帮工）写一段 JS。脚本只能调用农场工具：`/mcp` 上的那些，加上项目的几样（跑命令、开分支、收获）。工具的定义从注册时的 schema 导出，交给写脚本的一方。
- **mock 和样本**：每个工具调用的输入按 schema 生成，空的、超长的、不合法的也要有。返回优先用轨迹（`session/trajectories.go`）里录下的真实调用，农场工具大多返回文本，没有 `outputSchema`，只按 schema 造的返回验不出语义。时间、随机数由宿主注入，所以每次跑的结果一样。
- **验收**：农场用 mock 跑脚本，脚本自己的断言要过，以前的样本也要全过，这样才能挂到定时上。验收是农场跑的，写脚本的一方只能看结果。
- **运行时**：脚本在 [moejs](https://github.com/Calcium-Ion/moejs) 里跑，它是纯 Go 的 JS 运行时，`CGO_ENABLED=0`，不影响 macOS 打包。宿主函数就是农场工具在进程里的实现，不走 HTTP。`MemoryLimit` 和打断管住死循环，脚本碰不到宿主没装进去的东西。这和「帮工没有权限确认、只在工作目录里开工」是一个思路。运行时不调模型。
- **故障**：脚本抛错、超时，或者工具返回了样本里没见过的东西，这次的调用序列和出错的返回就存成新样本。这一次照旧交给管家处理（现在的行为），并请它改脚本；改好的脚本要过全部样本才能换上。
- **核心状态**：脚本和它的每次运行都是事实，形状加在 protocol 里，经 `Site.Apply` 折进核心状态，Flutter 照常读。服务端不另存一份脚本的状态。

待定：脚本的语言面要多大（只给工具调用和简单的控制流，还是给整个 JS 标准库）；样本存多少、怎么淘汰（重放不能越来越慢）；moejs 包在一个接口后面，换引擎时脚本不变。

### 4. 技能：帮工起草，主人批（待做）

给还得靠模型、但每次都差不多的做法用：「这个项目发版要先改 CHANGELOG、再打 tag」「改了 protocol 要跑 shapegen」。它对应 [Hermes](https://github.com/NousResearch/hermes-agent) 的第三类记忆（程序性记忆：复杂的活做完后 agent 自己写技能），也是[记忆都存在 SQLite](.agents/notes/proposed/architecture/2026-10-18-memory-in-sqlite.md)第 1 节的第三类。和第 3 步的分别：脚本不调模型，技能是写给模型看的步骤。

- **起草**：帮工经 `/mcp` 的 `skill_draft` 交一份 Agent Skills 形状的技能（名字、`description` 写「什么时候用」、正文是步骤），附上为什么（来自哪张工单、哪个 Session）。改一份已有的技能也是交草稿，带上它的 id。规矩（`session/rules.go`）告诉帮工：一件活走了很多步、而且以后还会遇到，才起草；`memory_add` 记的是事实，技能记的是做法。
- **验收是主人**：草稿不生效。技能书（`/skills`）上多一栏「待批」，看得到全文和改了什么（改已有的技能时是前后对比），点同意才写进技能书（`agent.Service.SaveSkill`，照旧存在 `config.json`），点拒绝留下理由。这一关是第「背后的想法」第 2 条：写技能的一方批不了自己的技能。也对应 Grok Bot 的「新的定时要你点头」：技能会影响以后每一次派活。
- **用了以后回来**：档案勾上的技能随派活交给帮工；收工时农场记下这一轮带了哪些技能、做没做成。技能书上每个技能显示用过几次、做成几次；做不成的多了标出来，请主人看要不要改或删。这是第 5 条的「故障是样本」，样本是那几次失败的 Session。
- **存在哪**：草稿和用过的记录进 `vibevalley.db`，模块是拥有技能的 `internal/agent`：`agent_skill_draft`（草稿、出处、待批、批了、拒了和理由）和 `agent_skill_use`（哪个技能、哪个 Session、结局）。批了的技能本身照旧在技能书里；技能书整个搬进 SQLite（连同档案）是另一件事，不在这一步。
- **不另调模型**：起草是帮工在干活的那一轮里顺手做的，和「记住：」一样不多花一次钱。

待定：一个档案最多攒几份待批的草稿（太多主人批不过来）；技能被拒的理由要不要回给起草的帮工下次参考。

## Alternatives considered

**照旧让帮工自己写测试、自己过检查。** 写测试和判卷是同一只手，过了也只说明代码和测试一致。这是本文要改的现状。

**验收由主人写。** 信号最好，但每个计划都要主人写测试，太贵。折中：验收步骤在草稿里，主人看过、能改才开工。

**冻结整个测试目录。** 太宽：正当的步骤也要加测试、改测试工具。所以只冻结验收步骤自己改的文件，规划的规矩也要求验收尽量写在新文件里。

**改了冻结的文件就悄悄恢复。** 帮工不知道自己犯了什么规矩，恢复后还可能编不过。退回去说清楚原因更好。

**每一步做完都跑全部验收。** 长活的中间步骤本来就过不了验收（数据层改完、接口还没改）。所以只让最后的步骤跑；规划的规矩要求最后放一步整体验证，通常只有一个最后的步骤。

**用模型当评审（LLM judge）。** 评审本身也是一次采样，当不了验证者。它适合放在验收之后挑毛病（种植计划 Deferred 里的审查步骤），不适合当门槛。

**农活脚本用别的运行时。** Node 子进程没有沙箱，还要在 macOS 应用里带上 Node；Starlark 确定、安全，但模型写 JS 比写 Starlark 熟练得多，MCP 的生态也是 JS 的；cgo 的 QuickJS 和 V8 破坏纯 Go 的交叉编译；Sobek、modernc 的 QuickJS 是纯 Go，但起一个运行时更慢、更占内存。moejs 每个运行时约 1.4µs、80KiB，带内存上限和打断，能直接跑 TypeScript（`CompileTS`）。代价是它很年轻，所以包在接口后面。

**用 moejs 在 Go 里跑 TypeScript 的 `reduce`，省掉 Go 的移植。** 考虑过，否决了：protocol 依赖 Effect，模块初始化很重；`Site.Apply` 每折一个事实都要把整个状态在 Go 和 JS 之间来回转一遍；服务端也和「服务端是 Go」的决定相反（[Go 服务端](docs/subsystems/foundation.md)）。

**帮工写的技能直接生效（Hermes 的做法）。** 省掉主人一步，可写技能和用技能是同一只手，错的做法会随每次派活扩散，而且主人不知道多了什么；批这一步就是验收。

**技能也存成 SQLite 里的记忆，不进技能书。** 那就和档案勾选技能、派活时交给帮工的那条路分开了，同一份做法有两处；技能书本来就是技能的家。

**定时和巡查保持每次叫醒管家。** 简单，但每次都花一轮、每次结果都不一样，故障也没有样本留下。这只适合不重复的事。

## Acceptance criteria

- 第 1 步（已做）：
  - `server/internal/task/task_test.go` 的 `TestTaskAcceptanceFirst`：验收步骤顺手把问题修了，检查通过，被退回；重写成会失败的测试后合进去，记下冻结的文件。修复的步骤改松了冻结的测试，被退回、被告知哪些文件冻结了；从代码上修好后，最后一步跑验收通过，计划熟了。
  - `TestCrewChangedFilesSinceTheBase` 用真的 git 仓库，测改了哪些文件：提交的、没提交的、改名的（两个名字都算）、新加的都算，分出来以后别的步骤合进计划分支的不算。
  - 黄金数据（`internal/protocol/testdata/play.jsonl.gz`）覆盖 `AcceptanceChecks`、`FrozenTouched`、带验收的 `ParseTask`、`NodeTask` 和两段说法。
  - 规划的帮工看到的示例本身就是一张农场能收的计划，第一步是验收。
- 第 2 步：主分支上一个被收获进来的改动让测试挂了，修复计划的第一步复现的正是那条失败的输出；退回第二次时，接手的是新的帮工、新的 worktree，工单里带着前面的失败样本，不带前一个会话；修好收获以后，那条测试留在主分支上。
- 第 3 步：主人说「每天九点跑一遍测试，红了就派帮工修」，管家写出脚本，农场用 mock 跑过才挂上定时；到点在 moejs 里跑，不调模型；把一个工具的返回改成样本里没有的样子，这次运行失败，样本多一条，管家被叫来改脚本，改好的脚本过了全部样本才换上。测试里不连网，时间用注入的时钟。
- 第 4 步：帮工做完一件多步的活后经 `skill_draft` 交了一份草稿，技能书「待批」里看得到全文和出处；批之前派活不带它，批了以后勾上它的档案派活时带上；收工后技能书上它的「用过几次、做成几次」加一。改已有技能的草稿显示前后对比。

## Risks

- **验收本身错了**：测试因为写错、编不过而失败，也能过「判红」这一关；冻结一个写错的测试，会逼着后面的步骤去迁就它。目前只靠规划的规矩（失败要因为问题本身）、主人看草稿，以及步骤没做成时主人可以改工单或跳过。第 2 步要求失败的输出对得上证据，能挡住一部分。
- **冻结误伤**：修复确实需要改验收碰过的某个测试工具文件。这时主人改计划或跳过；规划的规矩要求验收写在新文件里。
- **多个最后的步骤**：每个都要过全部验收，单独一个可能过不了。靠「最后放一步整体验证」的规矩，让计划只有一个收尾。
- **多花一步的钱**：每个修复计划多一个帮工。值不值，看第 2 步量出来的数据。
- **检查命令是任意的 shell**：本来就是，验收没有让它更危险；判红只是多跑一次。
- **技能草稿太多**：每件活都起草，主人批不过来。靠规矩（多步、以后还会遇到才起草）和每个档案的待批上限。
