# Agent Note: 状态先提交，副作用由 worker 在提交之后做

Status: proposed

## Problem

一件事在服务端现在是这样走的：服务改库（工单、田头、执行各自的表），再把事实施加到核心状态（`Core.apply`），再在同一个调用里做外面的事：开 oar 会话、跑 git、发消息、调声网。三步之间没有共同的提交点：

- **崩在中间，各处不一致。** 库改了、事实没施加：页面看不到，要等下次开机从库重放。事实施加了、外面的事没做：工单在「在做」，帮工没派出去。开 oar 会话成功了、`session` 表没写上：重启后这个会话谁也不认。
- **开机和顺序靠组装撑着。** 十模块的第 1 步把「先建好、再按模块顺序开机」立了起来，第 6 步把模块之间的事件改成带类型的流；但「接回帮工以后才整理计划」「帮工接回以后才给它开工单串、送等着的话」这类规矩，仍然是开机函数的先后，不是数据上能看出来的状态。
- **重试各写各的。** 投递有 `channel_delivery`（送了没有、回执），连接器有 `connector_outbox`（先落盘、再发、至少一次），排队有 `issue_queue`。三处各自实现了「先记下要做的事、提交、再由一个循环去做」，别的地方（派活、收获、通知管家）没有，失败就只记一条日志。
- **核心状态有两个家。** 帮工的阶段在 `state.json`（防抖 500 毫秒写一次），工单、田头、定时在库里，重启时两边各读各的再拼。

参考的 [T3 Code](https://github.com/pingdotgg/t3code) 的编排是事件溯源的：编排器只决定事件，事件、投影和待做的副作用在一个事务里提交，副作用由 worker 在提交之后执行（`docs/internals/overview.md`）。

## Proposal

不做全量的事件溯源，只把「要做的外面的事」变成和状态一起提交的数据。

1. **一张待做的表**（`core_job`，Platform）：`id`、`kind`（封闭的联合，每个模块登记自己的几种）、`payload`、`not_before`、`attempts`、`last_error`、`done_at`。模块在改自己的表的**同一个事务**里写一行，不在事务里做外面的事。
2. **一个 worker**（Platform 的开机函数起它）：按 `not_before` 取没做完的，交给登记这个 `kind` 的模块的处理函数；成功写 `done_at`，失败按种类退避重试，到上限把原因写成通知。处理函数必须可重做：用 `id` 去重（oar 会话的名字、PR 的分支、消息的 `send_key`），已经做过就只补记结果。
3. **先挪最疼的三处**：派活（工单挪到在做 → 开 Session）、收获（合并、提 PR、结束 PR）、通知管家（`forOrchestrator`、巡查、定时到点）。投递、连接器的发件、排队已经是这个样子，挪到同一张表和同一个 worker 上，删掉各自的循环。
4. **事实跟着提交**：模块提交以后再施加事实（现在有的地方是先施加、再写库）。核心状态仍是读模型：开机时从各模块的表重放，`state.json` 只留帮工的阶段这一份不在库里的，等执行的状态也进库以后删掉。
5. **开机就是 worker 接着做**：重启时没做完的行还在表里，worker 照常取；第 1 步里靠开机顺序撑着的规矩，改成待做的行之间的 `not_before` 或依赖（比如「整理计划」等「接回帮工」那一行做完）。

## Alternatives considered

**全量事件溯源**（T3 Code 那样，一切状态都由事件日志折出来）。最彻底，但要把工单、田头、文档、账本的表都改成投影，旧的查询和测试几乎全部重写；我们的库本来就是工单和田头的唯一来源，缺的只是「外面的事」和状态一起提交。先做这一半，事件日志等有了回放、审计的需要再说。

**Effect 的 durable workflow（`@effect/workflow`、cluster）**。现成的重试和持久化，但它要自己的存储和运行时，和 PGlite、单进程的服务端是两套东西；我们要的只是一张表和一个循环。

**每个模块各留各的 outbox**。现在就是这样（投递、连接器、排队），三份实现、三种重试，开机时谁先谁后又回到组装的顺序上。

**维持现状，只补重试**。补得了「失败了再来一次」，补不了「崩在两步之间」：那需要状态和要做的事在一个事务里。

## Acceptance criteria

- `core_job` 和 worker 存在；派活、收获、通知管家、投递、连接器发件、排队都经它，各自原来的循环删掉。
- 每个处理函数在测试里被执行两次（模拟提交后、做完前崩溃），结果和执行一次一样。
- 一个流程测试在「状态已提交、外面的事没做」时重启服务端，帮工照样派出去、PR 照样提上。
- 开机函数里不再有「必须排在谁后面」的注释；顺序写在待做的行上。
- `state.json` 的删除另记：执行的状态进库以后再做。

## Risks

- **改动面大**：派活和收获是最常走的路，每挪一处都要有对应的流程测试先在旧路上跑通。按处理函数一个个挪，每个单独合。
- **重做不安全的外部调用**：`gh pr create`、oar 会话的启动不是天然幂等的；处理函数要先查有没有做过（已有开着的 PR、同名会话），查不了的种类不挪。
- **延迟**：worker 取活有间隔，派活要比现在晚一点才动。提交后立刻唤醒 worker，间隔只是兜底。
- **PGlite 的写并发**：worker 和请求处理在同一个进程里写同一个库；事务要短，外面的事一律在事务外做。
