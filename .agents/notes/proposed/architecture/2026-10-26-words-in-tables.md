# Agent Note: 对主人说的话收进词表，再谈英文

Status: proposed

## Problem

主人看得到的话散在两百多个文件里：页面约 2000 行、126 个文件；服务端约 1800 行、90 个文件；protocol、桌面壳、手机壳、灵动岛还有一些。同一个意思常有几种写法，一个词改了要到处找：比如两个时长的说法、几处各写一份的结局标签、页面和服务端各一份的 `mentionOf`。用语表（[docs/README.md](docs/README.md#用语)）只能靠人照着写，代码不查。

主人想支持英文。在这种状态下直接翻译，等于把散乱复制成两份，而且漏翻没有任何东西能发现。

另一个难处在服务端。照「结论写进帧」的规矩，帮工在干什么（`phaseText`）、工单在等什么（`attentionLabel`）、通知怎么说（`InboxWords`）、拒绝的理由、群聊里的系统消息，都由服务端写成话，页面只显示。所以语言不只是页面的事。

## Proposal

先收敛「字放在哪」，再做英文。每一步都是独立的 PR，用户看到的画面不变，到最后一步才多出英文。

### 话分两种

- **对主人的话**：界面上的字、写进帧的说法、通知、拒绝的理由、群聊里的系统消息、命令行的输出。这些进词表，将来按主人的语言写。
- **对模型的话**：管家的系统提示、工具说明、派给帮工的活怎么写（`jobBreak`、`conflictBrief` 这类）。这些不进词表，也不翻译，各模块收进自己的 `prompts.ts`；要英文时只在提示里加一句「用主人的语言回答」（LobeHub 也是这样做的）。

两种都沾的照「谁先读」归类。拒绝的理由主人和管家都会读到，算对主人的话；管家读英文没有问题。

### 词表的形状

- **放在哪**：两边都说的放 `packages/protocol/src/words/`，只有服务端说的放 `apps/server/src/<模块>/words.ts`，页面的放 `apps/web/src/words/`。桌面壳的菜单栏和灵动岛的话，由主进程从词表取好，再交给它们。
- **怎么写**：每张表是一个普通的 TS 对象，按概念分组，key 用实际的概念（`attention.reviewing`），不用中文原句。要填值的条目写成函数（`working: (n: number) => \`${n} 在干\``），不用 `{{var}}` 字符串插值，参数由类型检查。
- **类型怎么来**：中文是源头，`export type Words = Widen<typeof zh>`；将来的英文写成 `export const en: Words = { … }`，少一条或参数对不上就编不过。不用 i18next：我们是 Solid、两种语言、本机只有一个主人，按需加载、自动识别语言这些它擅长的事都用不上。
- **怎么取**：纯规则多收一个 `w: Words` 参数（`phaseText(h, now, w)`）。服务端的服务从设置里拿当前的词表；页面用 `useWords()`。在英文那一步之前，取到的永远是中文。

### 用 lint 卡住，名单只减不增

在 `scripts/oxlint-plugin.ts` 加一条 `vibevalley/no-cjk-literal`：字符串和模板字面量里出现中日韩文字，只在这些地方允许：

- 词表文件（`words/`、`words.ts`）；
- `prompts.ts`；
- 测试和黄金数据；
- 一份豁免名单 `scripts/cjk-exempt.json`，第一次列出现在所有还带中文的文件。

名单里的文件不能再有新的写法进来，靠评审；但一个文件迁完、不再带中文却还在名单上时，规则报错，逼着把它从名单删掉。名单的长度就是收敛的进度。新文件从第一天起就写不进散落的中文。

注释不查：代码注释本来就是英文（[docs/style/code.md](docs/style/code.md)）。

### 步骤

1. **机制**：lint 规则、豁免名单、`Words` 的类型和取法；把 protocol 已有的说法（`attentionLabel`、`stuckLabel`、`outcomeLabel`、`phaseWords`、状态和动作的词表）搬进 `protocol/src/words`。画面不变，黄金数据不变。
2. **服务端写进帧和对主人说的话**：通知（`notice`）、工单和计划的说法、群聊的系统消息、拒绝的理由、命令行，逐个模块搬，每搬完一个模块从名单删掉它。同时把对模型的话收进各模块的 `prompts.ts`。
3. **页面**：按地方逐个搬（`pages/<地方>`、`farm`）；种地的词另起一组 `farm`，只在农场的皮里用。
4. **英文**：
   - 用语表的两张表各加一列英文，先由主人定农场的词（田头、帮工、管家……），官网英文版的用词作起点；
   - 写 `en` 的各张表；设置里加「语言」（`zh`、`en`，默认跟系统），服务端、页面、桌面的菜单栏和灵动岛都跟它；
   - 管家和帮工的提示里加「用主人的语言回答」；
   - 已经存进库的历史不回头翻：切语言以后新写的话是英文，旧的群聊和时间线保持原样。

## Alternatives considered

- **直接上 i18next 的那一套**（LobeHub：i18next 加 react-i18next，英文是源头，18 种语言，gpt-4o 按术语表增量翻译，每天由机器人开 PR）。放弃：我们要的只是两种语言加一个设置；它最有用的两件事（带类型的源头、提交进仓库的翻译）用普通 TS 对象就有，不必多一个运行库和一套生成流程。
- **先翻页面，服务端的话以后再说**。放弃：页面里大半要紧的字是服务端写进帧的，只翻页面会是中英混着的界面。
- **翻译提示词**。放弃：管家的行为和付费评测绑在中文提示上，提示的写法是调出来的；模型读中文提示、用英文回答，没有问题。
- **服务端只发结构、让页面拼话**。放弃：这和「结论写进帧」的规矩相反，菜单栏、灵动岛、通知、命令行也都要那句话，会变成到处各拼一遍。

## Acceptance criteria

- 第 1 步后：`vp check` 拒绝词表、`prompts.ts`、测试、豁免名单以外的中文字面量；名单上的文件不再带中文时也报错；protocol 的说法只从 `words` 来；所有测试和黄金数据不改就过。
- 第 2、3 步每个 PR：名单变短；画面和测试不变。
- 第 4 步后：设置换成 English，页面、帧里的说法、通知、菜单栏、灵动岛都是英文，管家用英文回答；`en` 的表少一条就编不过；Playwright 另有一组英文的冒烟测试。

## Risks

- **搬家改签名**：纯规则多一个参数，调用处多；靠一个模块一个 PR 摊开。
- **键起得不好**：按概念起名，评审时对照用语表；键错了改名代价小，类型会带着所有调用处一起改。
- **分不清该进词表还是 `prompts.ts`**：照「谁先读」，拿不准的进词表；多翻一条只是多一点工作，漏翻会让英文界面混着中文。
- **英文那一步的用词**：农场的词要主人定，在这之前不写 `en`。
