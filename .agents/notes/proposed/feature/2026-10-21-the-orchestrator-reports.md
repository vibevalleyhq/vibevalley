# Agent Note: 管家给主人报告：早报、项目健康度、工单之间的关系和分拣建议

Status: proposed

## Problem

主人想要的管家像一个熟练用 Linear 的人：问「这个项目怎么样了」给个准话，每天早上说说昨天收了什么、卡在哪、今天等主人拍板的。管家现在能列出在等主人的工单（`issue_list` 的 `wantsOwner`，按等了多久排），但说不清一个项目怎么样了：没有健康度，没有固定的早报格式，标不了「这张和 #38 是一回事」，新记下的工单也不会建议优先级和谁来做。

## Proposal

### 项目的健康度

对应 Linear 的 Project update（On track / At risk / Off track）。由规则算，不让模型判。放在 `packages/protocol/src/rules`（页面也要画），输入是这个项目的工单和今天的花费：

| 健康度 | 条件（初版，可调） |
|---|---|
| 顺利 | 没有卡住的，等主人的都不超过一天 |
| 有风险 | 有卡住的，或有等主人超过一天的，或今天的花费过了每日预算的八成 |
| 卡住了 | 卡住的超过开着的一半，或有等主人超过三天的 |

健康度带着「为什么」（哪几张、等了多久），管家照着说，不另编理由。

### 早报

对应 Linear 的 Pulse。主人定一个每天的定时，管家照固定的三段说：昨天收了什么；现在卡在哪；今天等你拍板的。格式写进管家的提示，数据全来自 `issue_list` 和健康度。

### 工单之间的关系

`issue_link`：标「重复」「相关」，只标记、不调度。`Issue.relations`（`{ kind: "duplicate" | "related"; issue: string }[]`），存在 `issue` 表的一列 JSON。记一件事之前查重已经有了（`issue_list` 的 `text`）；查到相像的，管家问主人是不是同一件，主人说是就标重复。

### 分拣建议

对应 Linear 的分拣智能（Triage Intelligence）：管家给新记下的工单建议优先级、项目、谁来做，显示为建议，主人接受了才改。

### 要动的地方

- **`packages/protocol`**：`Issue.relations`；健康度的规则（`rules/health.ts`）和它的黄金数据。
- **`apps/server/src/issue`**：`relations` 的读写。
- **`apps/server/src/tool`**：`issue_link`；`issue_list` 加健康度。
- **`apps/server/src/orchestrator`**：早报的格式；样例进 `testdata/evals`。
- **页面**：项目页画健康度。

### 主人怎么说

| 主人说 | 管家做 |
|---|---|
| 「clock-in 怎么样了？」 | 健康度和最该注意的一件 |
| 「#41 和 #38 是一回事」 | 标重复 |
| 「每天早上给我说说」 | 定一个每天的早报 |

## Alternatives considered

**照搬 Linear 的周期（Cycle）和估点。** 周期是给人排两周节奏用的，帮工随派随做；真正的约束是同时干活的上限和花费。估点由「这张工单花了多少钱」（花费已经记在工单的 run 上）代替，不另让主人估。

**加标签。** 档案的「适合的活」（`Agent.tags`）已经够分派和筛选；多一套标签就多一套管家要维护、主人要看的状态。等有筛不出来的真实需要再加。

**加 SLA。** 「等主人多久了」已经在站位的 `since` 里，巡查和健康度用它就够；先不做独立的 SLA。

**让模型判项目健康度。** 每次说法不一样，主人没法信、也没法比；条件写成规则，阈值可调，管家只转述。

## Acceptance criteria

- 「clock-in 怎么样了」：说的健康度和项目页画的是同一个，理由是规则给的那几张工单。
- 「#41 和 #38 是一回事」：两张都带上关系，看板上看得到；调度不变。
- 早报照三段说，数据和 `issue_list`、健康度一致。
- 管家建议的优先级、项目、谁来做，主人接受以前工单不变。

## Risks

- **健康度的阈值拍脑袋**：初版照上表，跑一阵看主人觉得准不准再调；阈值在一个文件里，有黄金数据。
- **工具变多，管家挑错**：样例要覆盖「用哪个」的边界，描述里写清什么时候用、什么时候不用。
