# Agent Note: 工单详情的经过合成一条活动流

Status: proposed

## Problem

工单详情（`apps/web/src/features/issue/views/IssueDetail.tsx`）把一件事的经过拆在四块里，各有标题，各自取数：

| 块 | 取数 | 内容 |
|---|---|---|
| 讨论与交付记录（`IssueThread`） | 工单串的频道消息，`useFollowed`，往上翻页 | 用户的话、帮工的汇报、系统消息 |
| 怎么走到这一步（`Story`） | `issue.timeline.get`，服务端 `milestonesOf`（`apps/server/src/modules/issue/brief.ts`）由 runs 折出 | 开单、开工、交回、提问、打回、验收、关单 |
| 帮工的每一步（`WorkLog`） | `session.event.list`，只取当前帮工，展开才读 | 想、说、用工具、出错 |
| 每一轮（`Runs`） | `issue.run.list` | 每轮的起止、结果、摘要 |

结果是：同一件事出现两三次（一轮交回既是「交回」里程碑，又是一条汇报消息，又是「每一轮」里的一行；用户带的话既是消息，又是「told」里程碑）；时间顺序要在四块之间来回对；Story 新的在上、讨论旧的在上，方向相反；「每一步」只看得到最后一个帮工。Linear 的工单页只有一条活动流：评论和状态变化按时间排在一起，细节默认收起，这页现在读起来像四份报告。

## Proposal

详情页正文的下半部分换成一条**活动**（`issue-activity`），旧的在上、新的在下、输入框在最底下，和频道一样读。它由两种行组成：

1. **消息行**：工单串里的消息，照现在 `IssueThread` 的样子（名字、时间、Markdown）。用户在页面上说的话、带的话、回答都落在这里，所以不再有 `told` 里程碑。
2. **事件行**：一行小字、一个图标，说状态怎么变了：开单、开工（第几轮、谁）、交回、提问、失败、停下、打回（带意见）、验收、关单。一轮的事件行可以展开，展开时按 `session.event.list({ id, run })` 读这一轮的步骤，用现在 `WorkLog` 的画法画在它下面；读过的轮次不重读。

**服务端出事件，页面只摆。** 哪些里程碑和消息重复、一轮该怎么说，是服务端的规则（AGENTS.md「页面不折事实」），所以：

- `Milestone` 加 `run?: string`（开工、交回、提问、失败、停下这几种带它），页面凭它展开步骤；`IssueTimeline` 不再出 `told`（用户的话已经是消息）。
- 交回、失败、停下的里程碑不再把 `summary` 拼进 `text`，改放进新字段 `said?: string`：摘要已经是工单串里的汇报消息，页面的事件行只说「阿狐交回了第 2 轮」、不画 `said`；命令行的 `vibevalley issue timeline` 没有消息可看，照旧打印它。
- `milestonesOf` 改成旧的在前，和消息同向；页面按 `at` 把两列合成一列，同一毫秒事件在消息前。合并只是摆法，不做去重。
- `issue.run.list` 和「每一轮」那块在页面上退场：轮次的起止和用时进事件行（`开工 · 第 2 轮` …… `交回 · 用了 6 分钟`）。接口留给命令行和农场，不删。

**活动的顶上**是「较早的」按钮，照现在 `IssueThread` 的翻页；里程碑一次读完（一张工单几十条），消息按页来，所以较早的消息没翻出来时，只画比最早一条已读消息新的事件，避免事件挤在一段空白前面。

**不动的**：「现在怎样」那一行、「要你做的」那块、做到哪了、做出了什么、产出物，都留在活动上面。它们说的是此刻，不是经过。

## 共享约定

- 事件行的图标走 `ui/icons.ts` 的名字，一种 `MilestoneKind` 一个，写成 `Record<MilestoneKind, IconName>`，加新种类时编不过。
- 页面的 `data-testid`：活动 `issue-activity`，消息行沿用 `issue-message`，事件行沿用 `milestone`（`data-kind`、新加 `data-run`）。现有 Playwright 测试按这些找元素，改名就要一起改。

## Alternatives considered

**服务端出一个合好的 `issue.activity.list`**：把消息和里程碑合成一列再发。没选：消息是频道的，已经经 `useFollowed` 实时推、分页、有乐观的待发行；再在工单接口里复制一份，就是两份消息状态，带话的待发行也要另做一遍。服务端只决定「哪些里程碑出、怎么说」，合并留在页面。

**里程碑也做成频道里的系统消息**：把开工、交回写成工单串里的系统消息，活动就只剩消息。没选：频道里的系统消息会进农场的田头、未读数和通知，一轮一条会刷屏；而且步骤要按轮展开，消息上挂不住这层结构。

**保留四块，只调顺序和样式**：改动最小，但重复和来回对时间的问题都还在，不是 Linear 那样读的。

**把每一步平铺进活动**：一轮几百步，平铺就淹掉了对话。默认收起，按轮展开。

## Acceptance criteria

- 一张走过「开工 → 提问 → 回答 → 交回 → 打回 → 交回 → 验收 → 关单」的工单，详情页只有一条活动：每件事出现一次，从上到下按时间，回答和打回意见是消息行，其余是事件行。
- 事件行展开能看到那一轮的步骤，含之前帮工的轮次；不展开时不读 `session.event.list`。
- 服务端测试：`milestonesOf` 不出 `told`、摘要在 `said` 不在 `text`、带 `run`、旧的在前（`apps/server/src/modules/issue` 的规则测试）。命令行的 `issue timeline` 仍打出每轮的摘要（`apps/cli` 的 golden 测试）。
- 页面：合并两列的纯函数在 `features/issue/*.ts` 用 vitest 测（同一毫秒、只读到一部分消息时的截断）；`issue-page.spec.ts` 的真实一轮断言活动里的事件和消息都在、展开一轮能看到步骤。
- 截图验收（vv-acceptance 的页面分册）：1440 和 390 宽各一张。
- `docs/subsystems/issue.md` 写下活动由什么组成、去重归服务端。

## Risks

- **消息分页和事件的对齐**：只读了最近一页消息时，较早的事件要不要画？上面选了「只画比最早一条已读消息新的事件」，翻页后补出来；如果某张工单消息很少、事件很多，这个规则可能显得事件晚到。做时看真数据再定。
- **农场的工单视图**（`farm/issue/IssueView.tsx`）自己画里程碑和每一轮。这次只改工作台；`milestonesOf` 的变化（不出 `told`、摘要挪进 `said`）农场也会看到，它的里程碑行要改成读 `said`，否则交回那行就没了摘要。
- **`issue.timeline.get` 的形状变了**：加 `run`、`said`，去掉 `told`，`text` 不再带摘要。读它的有页面、农场和命令行的 `issue timeline`；照「内部不留兼容」直接改，三处一起改，跑命令行的 golden 测试。
- **页面测试**：`issue-page.spec.ts` 现在断言有 `told` 里程碑，要改成断言那句话是一条消息。
