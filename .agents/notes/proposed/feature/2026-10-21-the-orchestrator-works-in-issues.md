# Agent Note: 管家以工单为单位干活：像 Linear 的老用户一样记、找、改、问、报

Status: proposed

## Problem

管家应帮助主人管理一件事从提出到完成的全过程。创建工单、补充要求、指派帮工、开始执行、停止执行和接受成果，各自表达不同意图。

当前代码已有 `issue_create`、`issue_update`、`issue_status` 和按工单编号查询、带话、停止等工具；[管家提示词](apps/server/src/orchestrator/orchestrator.ts)仍把「主人要做一件事：用 dispatch 派活」作为首条行动规则。[dispatch](apps/server/src/tool/tool.ts)把工单说明、选人和立即派活组合在一次调用里。记录和执行已经有不同入口，但管家的默认行动仍围绕派活展开。

这会留下三个行为边界：讨论是否会触发开工，指定负责人是否意味着立即执行，停止当前执行是否会取消整张工单。仅修改 `dispatch` 的名字不能解决这些边界。本文保留已有的工单能力提案，补充按主人意图组织交互的目标行为；待定项不代表已经实施或获准实施。

## Proposal

**管家以工单为单位干活。** 所有工具都能用工单编号（`#41`、`41`）点名，帮工只是工单此刻由谁在做；照 Linear 老用户的日常补齐记、找、改、问、报五件事。规则不在管家里重写：每个工具都是转发给已有的服务方法（`Issues`、`attentionOf`、`issueStatusOf`），管家只决定什么时候调、怎么跟主人说。

### 交互边界：先识别意图，再选择动作

管家的主要对象应是工单。工单记载「要做什么」，执行承接「这一轮怎么做」。同一张工单可经历调查、实现、返工和换人；后续执行应保留原工单身份。需要独立交付和验收的工作，才另建工单并关联原工单。

下表是目标交互，不是现有能力清单。

| 主人说 | 意图 | 目标结果 |
|---|---|---|
| 「先设想一下，怎么做比较好」 | 讨论 | 围绕已有信息讨论，不自动建单或开工 |
| 「记一下，登录偶尔白屏」 | 记录 | 保留原话，建备选工单，不启动帮工 |
| 「新建一个导出功能的工单」 | 定义工作 | 写清标题、主要内容和已知要求；缺少的信息标为待定 |
| 「这张工单主要做什么」 | 解释范围 | 从工单说明和验收标准回答 |
| 「帮我把这个需求理一下」 | 澄清 | 整理目标、范围、验收标准，提出影响执行的缺口 |
| 「先看看代码，评估怎么做」 | 调查 | 启动有明确问题和交付物的调查，不自动进入实现 |
| 「加上 CSV 支持，优先级调高」 | 修改工单 | 更新要求和优先级；已开工时应说明新要求如何送达执行 |
| 「这张让 Codex 做，先别开始」 | 指派 | 保存负责人，不启动执行 |
| 「开始做这张」 | 开工 | 在原工单上启动执行；不能启动时说明原因和是否排队 |
| 「先停一下 #41」 | 停止执行 | 停止当前执行，保留工单和已有改动 |
| 「#41 先别开工」 | 暂缓 | 阻止待执行的工作自动启动 |
| 「#41 不做了」 | 取消 | 取消工单并停止相关执行，不合并改动 |
| 「#41 接着做」 | 继续 | 在原工单继续，带上已有进展、停止原因和新增要求 |
| 「#41 换个人接手」 | 交接 | 停止原执行，交代已有改动和未完成事项，再由新人接手 |
| 「做到哪了，哪些等我处理」 | 查询 | 返回真实进度、阻塞点和需要主人决定的事 |
| 「告诉他先别动数据库」 | 带话 | 将要求送到当前执行；持续有效的范围变化应同步进工单 |
| 「没做对，再修一下」 | 返工 | 将反馈留在原工单，再干一轮 |
| 「检查一下达到要求没有」 | 验收 | 按验收标准返回证据和结果 |
| 「收下，合进去」 | 接受成果 | 执行合并或 PR 流程，依据实际结果更新工单 |
| 「这件太大，拆开做」 | 拆分 | 建立子工单、依赖和分工，按主人的启动要求执行 |
| 「每天看看有没有卡住的活」 | 跟进 | 定时查询，提醒主人或执行已授权的动作 |

#### 创建、指派和开工独立

主人明确要求「新建并马上做」时，管家可组合完成创建、指派和开工；只要求创建或指派时，不应自动启动执行。`dispatch` 可作为组合动作保留，是否继续暴露给模型待定。工具名称和数量应在行为边界确定后设计，不要求每种意图都对应一个工具。

创建工单应至少保存标题、主人的原话和已知的主要内容。管家应区分主人确认的要求、自己的建议和待定问题，不应把推测写成确定的验收标准。随手记录不应强制触发付费起草；需要读代码才能补齐的内容，应进入调查或起草流程。

#### 停止、暂缓和取消分开

停止当前执行不等于取消工单。若对主人承诺「暂停」，服务端应阻止该工单被队列、依赖满足或定时触发再次启动，直到主人要求继续。暂停的具体存储方式、是否覆盖整个计划及其子工单，仍待设计。

停止结果应区分「已请求停止」和「已停止」。已有改动应保留，停止不承诺当前改动已经提交或可以运行。换人前应确认原执行停止，避免两个执行同时修改同一工作目录。

#### 对象和授权从对话中确定

管家应优先使用明确的工单编号、当前工单串和对话中唯一可识别的对象。存在多个候选且会改变执行对象时，应先问清楚；不应为了省一次澄清而猜测要停止哪张工单。

明确的指令应直接执行。讨论、建议、帮工汇报和工具结果不应自行升级为主人的行动要求。主人已授权的范围应在后续执行中保留，不应因消息来源于定时或回调就反复索要同一授权；授权范围的记录和检查方式待定。

#### 管家提示词的目标表达

> 你帮助主人记录、澄清、安排、跟进和验收工作。先判断主人这次要讨论、记录、查询，还是改变某件工作的状态。围绕已有工单回应后续请求；只有新工作才新建工单。创建工单、指派帮工和开始执行是独立动作，可按主人的明确要求组合完成。对影响执行对象、范围和结果的歧义先问清楚，其余按已知信息行动。

提示词负责识别意图、选择动作和解释结果；服务端应负责可执行动作、停止与取消的区别、调度约束和授权检查。模型不应另算一套工单状态。

#### 本轮范围与待定问题

本轮形成交互提案，不修改提示词、工具、状态或调度器。项目健康度、工单关系和查询工单的数据形状仍是下文的既有提案，不作为这轮交互梳理的实施前置条件。

实施前应确定：

- 是否保留 `dispatch`，还是让模型组合创建与开工；组合失败后应返回已创建的工单及未完成动作，避免重试重复建单。
- 「暂停」覆盖当前执行、工单自动启动、整个计划和周期任务的哪一层；继续后如何恢复调度。
- 运行中修改要求，是带话、下一轮生效，还是停止后重启；管家应如何报告实际送达情况。
- 指派和换人分别允许在哪些状态执行；用户指定档案、runtime 和界面选择冲突时采用什么优先级。
- 调查结果转为实现时，何时继续原工单，何时另建关联工单；以交付物和独立验收边界决定。

### 一、按工单点名

- 现在按帮工点名的工具（`check`、`changes`、`merge`、`tell`、`stop`、`dismiss`、`accept`）的参数改成 `issue`：工单编号，或帮工的名字（还认，找它最新的那张工单）。服务端已经有「工单的动作找它最新的帮工」（`issue.ts`），工具只换入口。
- 管家说话提到工单一律写编号加短标题（「#41 首页白屏」），不写帮工的名字代替工单。

### 二、对照 Linear 补的工具

| Linear 用户在做的事 | Linear 里是什么 | 工具 | 背后的服务方法 |
|---|---|---|---|
| 随手记一件事，以后再说 | 建在 Triage / Backlog | `issue_create`：写进备选，可以顺手起草；不派 | `issue.create`、`issue.draft` |
| 记之前先查重 | Duplicate 提示 | `issue_search`：按字找，开着的和最近关的都找 | `issue.list` + 文字匹配 |
| 按条件看一批 | 自定义视图、筛选 | `issues`：按状态、站位（等你回答 / 等你验收 / 卡住了…）、项目、优先级、谁在做、多久没动筛，按等了多久排 | `issue.list`、`attentionOf` |
| 看一张的来龙去脉 | 工单详情、活动记录 | `issue_get`：各栏、站位、验收标准逐条、时间线 | `issue.get`、`issue.timeline` |
| 改属性 | 改优先级、项目、负责人 | `issue_update`：优先级、项目、验收方式、验收标准、先后 | `issue.update`、`issue.move` |
| 挪状态 | 拖看板 | `issue_status`：照 `moves` 挪，挪不了就照拒绝的话说 | `issue.status` |
| 工单之间的关系 | related、duplicate | `issue_link`：标「重复」「相关」，只标记、不调度 | 新：`issue.relations`（见「要动的地方」） |

`dispatch` 留着，就是「`issue_create` + 挪到待办」，主人说「去做」时一步到位。

### 三、主人的 Inbox 和项目的健康度

**「哪些在等我」**：站位里已经有答案（`attentionWantsOwner`：等你回答、等你验收、卡住了）。`issues` 带 `wantsOwner: true` 就是主人的 Inbox，按等了多久排；管家一句话一条：编号、短标题、要主人做什么、等了多久。

**项目的健康度**（Linear 的 Project update，On track / At risk / Off track）：由规则算，不让模型判。放在 `packages/protocol/src/rules`（页面也要画），输入是这个项目的工单和今天的花费：

| 健康度 | 条件（初版，可调） |
|---|---|
| 顺利 | 没有卡住的，等主人的都不超过一天 |
| 有风险 | 有卡住的，或有等主人超过一天的，或今天的花费过了每日预算的八成 |
| 卡住了 | 卡住的超过开着的一半，或有等主人超过三天的 |

健康度带着「为什么」（哪几张、等了多久），管家照着说，不另编理由。

**早报**（Linear 的 Pulse）：主人定一个每天的定时，管家照固定的三段说：昨天收了什么；现在卡在哪；今天等你拍板的。格式写进管家的提示，数据全来自 `issues` 和健康度。

### 四、查询：管家懂主人在问什么，帮工去查

主人常问的不是「去改这个」，而是「查一下」：为什么这个测试偶尔挂、某个功能在哪实现的、两个库哪个合适、昨天那张工单为什么没做成。

**分工：管家负责懂主人，帮工负责查。** 查询是工单的一种（`Issue.kind`：`change` | `question`），走同一套派活、工单串、验收，交回来是一份有依据的答案，不收获、不合并。

**管家**把一句话变成一张查询单，写进提示：

1. **认出这是查询**：应结合上下文区分讨论、农场数据查询和需要帮工调查的问题，不应仅凭「为什么」「怎么」「看看」等词自动派活。明确要求读代码或收集外部证据的，才进入调查流程。
2. **补全**，用记性（主人的偏好、项目背景、以前问过的）和农场现状：要知道什么；为什么问（主人要拿答案做什么决定，不知道就不写、不编）；答案要什么样（一句结论、对比表、步骤）；在哪查（项目；要上网就写明）。
3. **只在执行对象或必要范围不明确时回问一句**，否则直接派。农场自己的事（现状、花费、工单历史）管家用上面的工具直接答，不派帮工。

**帮工**照起草的路子跑：在工单自己的 worktree 里，只读，交回来就重置（`project.Reset`）。交给它的活是 `questionBrief`（`issue/rules.ts`）：

- 能做：读代码、`git log`/`blame`/`diff`、跑只读的命令和测试、上网查文档、用 `vibevalley` 命令行读农场自己的数据。
- 不做：改文件、提交、装依赖、推送；改了也会被重置。
- 交回：最后一个 json 代码块，服务端读（`parseAnswer`，和 `parseRefinement` 一样）：

```json
{
  "conclusion": "一两句话，先回答问的那件事",
  "evidence": ["apps/server/src/issue/issue.ts:877 管家一轮 completed 就关单", "跑 bun test x 三次，挂了一次，输出 ……"],
  "unsure": "哪一块是猜的、缺什么才能确定；都确定就空",
  "next": "建议的下一步，比如派一张改代码的工单：标题……"
}
```

- 拿不准要问主人的，照旧写「要问主人：」，走缺肥。

**答上了没有，由格式和主人判，不由一轮的结局判。** 读不出 `conclusion`，或 `evidence` 是空的：这一轮算没做成，站位「卡住了」，不能挪到已完成。读出来了：工单「等你看」，页面摆出结论、依据、没查清的、下一步；主人点「知道了」关成已完成（`answered`），点「照这个改」用 `next` 起一张改代码的工单，`parent` 指向这张查询。管家被叫醒，一两句话转告结论和工单编号，不复述依据。

### 五、管家写东西的分寸

照 Linear 分拣智能（Triage Intelligence）的做法：**建议显示为建议，主人接受了才生效。**

| 档 | 做什么 | 规矩 |
|---|---|---|
| 读 | `issues`、`issue_search`、`issue_get`、看改动、健康度 | 随便读 |
| 写下来 | `issue_create`、起草、标「可能重复」、给帮工带话 | 直接做：能撤回，不花大钱；做完说一句 |
| 定主意 | 改优先级、改项目、挪状态、派活、取消 | 主人这句话里说了就做；管家自己看出来的，先问一句（「#12 挡着 #15，要提到高优先级吗？」） |
| 落地 | 合并、收获、关成已完成、计划开工 | 应有主人对该动作的明确授权；现有合并工具检查本轮主人来源，跨轮授权方式待定 |

工具应检查动作是否在主人的授权范围内；`Caller.Owner` 可用于识别直接指令的来源，但来源本身不能证明授权范围，也不能替代定时任务等已授权动作的记录。具体授权模型待定，分寸应写进代码。

### 六、主人怎么跟管家说

一句话就行，管家补全。管家的提示和输入框的占位文字照这张表写：

| 主人说 | 管家做 |
|---|---|
| 「记一下：首页偶尔白屏」 | 查重并建备选，不自动启动付费起草，回工单编号 |
| 「#41 开工」 | 在原工单启动执行；「派给老周」只指派，是否同时开工按上下文判断 |
| 「哪些在等我？」 | 主人的 Inbox，按等的时间排 |
| 「clock-in 怎么样了？」 | 健康度和最该注意的一件 |
| 「#41 提到高优先级」「和 #38 是一回事」 | 改优先级；标重复 |
| 「为什么 X」「查一下 Y」 | 查询工单 |
| 「#41 怎么回事？」 | 站位、最后一轮怎么结束的、在等谁 |
| 「收了 #41」 | 收获，要主人原话 |
| 「每天早上给我说说」 | 定一个每天的早报 |

### 七、要动的地方

- **`packages/protocol`**：`Issue.kind`、`Issue.answer`；`Issue.relations`（`{ kind: "duplicate" | "related"; issue: string }[]`，存在 `issue` 表的一列 JSON）；健康度的规则（`rules/health.ts`）和它的黄金数据；`IssueAct` 加 `acknowledge`、`spinoff`。和工单页共用站位（`packages/protocol/src/rules/attention.ts`），那边先落地。
- **`apps/server/src/tool`**：按工单点名；新的七个工具；授权检查覆盖「定主意」和「落地」两档；`testdata/tool_schemas.json` 跟着改。
- **`apps/server/src/issue`**：查询的派活（和起草共用「只读 worktree + 交回就重置」，抽成一个函数）、`questionBrief`、`parseAnswer`、查询的 `statusMove`、`relations` 的读写。
- **`apps/server/src/orchestrator`**：提示改成以工单为单位，加记、找、改、问、报的说法和分寸；「农场现状」里的帮工带上它的工单编号；样例进 `testdata/evals`。
- **页面**：工单页上查询的「做出了什么」是答案；看板上查询有自己的标记；项目页画健康度。

按这个顺序做，每一步单独能上线：

1. 按工单点名，`issues`（`issue_get` 并进了它：填编号就是一张）、`issue_create`、`issue_update`、`issue_status`。已经做了，现状在[管家](docs/subsystems/orchestrator.md)「管家以工单为单位」；还差 `verify-orchestrator-evals` 的样例。
2. 主人的 Inbox 和早报：规则已经有，只差管家能问和固定格式。
3. 查询工单。
4. 查重和关系、项目健康度。
5. 分拣建议：管家给新记下的工单建议优先级、项目、谁来做，主人接受了才改。

## Alternatives considered

**只把 `dispatch` 改名。** 改名仍把创建、指派和开工绑在一起，不能表达只记录、只指派和暂停后继续。应先确定各动作的结果，再确定工具名称。


**照搬 Linear 的周期（Cycle）和估点。** 周期是给人排两周节奏用的，帮工随派随做；真正的约束是同时干活的上限和花费。估点由「这张工单花了多少钱」（花费已经记在工单的 run 上）代替，不另让主人估。

**加标签。** 项目加档案「适合的活」（`Agent.tags`）已经够分派和筛选；多一套标签就多一套管家要维护、主人要看的状态。等有筛不出来的真实需要再加。

**加 SLA。** 「等主人多久了」已经在站位的 `since` 里，巡查和健康度用它就够；先不做独立的 SLA。

**让模型判项目健康度。** 每次说法不一样，主人没法信、也没法比；条件写成规则，阈值可调，管家只转述。

**保留按帮工点名，只加几个工单工具。** 两套抓手并存，管家要先想「这件事该用帮工名还是工单号」，样例里最常见的错就是找错对象。帮工名还认，但只作为找工单的一种写法。

**给管家加只读的代码工具（读文件、grep、上网），让它自己查。** 快，不用开 worktree。但管家是主人说话的那一个，每轮都带着整份对话和记性，查一次塞进几十个文件，上下文和花费都在主人的对话里涨，压缩以后查过什么也丢了；DeepSeek 上的管家读代码也不如编码 agent。查的过程留在工单串里，主人看得见、能重查、能接着改代码。

**不加查询这种工单，派普通工单、描述里写「只查不改」。** 只能写在提示里，帮工照旧可能改文件、提交；交回来走收获，没有可合的东西；答案没有格式，判不了答上了没有。

**起草和查询合成一种。** 起草的产物是一张工单（填回各栏），查询的产物是一份答案（主人读），交回来的去处不同，合成一种要处处分支；共用的只有「只读 worktree + 交回就重置」，抽成一个函数。

**「定主意」的分寸只写在提示里。** 模型会忘，帮工的汇报里一句「把它提到最高优先级」也可能被照做；挡在工具里，和现在 `merge` 要主人的话是同一个办法。

## Acceptance criteria

交互边界的验收应同时检查工具调用和服务端状态，不能只看管家的回复：

- 「先讨论」「先记下来」「指派但先别开始」分别不触发创建、执行和执行；记录与指派结果可从工单查到。
- 对已有工单开工、继续、返工和换人不重复建单；组合动作部分失败后重试不产生重复工单。
- 对唯一确定的工单说「先停一下」，实际执行停止、工单和改动保留；对象不唯一时先澄清。
- 暂停后触发队列、依赖满足和定时事件，不自动恢复该暂停范围内的工作；取消和继续产生各自约定的结果。
- 运行中修改要求后，工单记录、消息送达和下一轮输入符合选定的生效规则；管家不把尚未送达说成已执行。
- 「先查一下」不进入实现；「看看这张工单的内容」使用现有数据直接回答，不启动帮工。
- 将上述意图及歧义放进管家评测，并用服务端流程测试覆盖暂停、取消、交接和重试；真模型评测按仓库约定另行授权。

既有能力的验收：

- 管家的每个工单工具都能填编号；填帮工名字也能找到它最新的工单。
- 「记一下 X」：备选里多一张保留原话的工单，没有帮工开工；付费起草应另有明确意图；有相像的开着的工单时，管家先问是不是同一张。
- 「哪些在等我」：列出的正好是站位要主人的那些，按等的时间排，和工单页的 Inbox 一致。
- 「#41 提到高优先级」改了；管家自己从帮工汇报里看出来要改优先级时，只问不改。
- 「clock-in 怎么样了」：说的健康度和项目页画的是同一个，理由是规则给的那几张工单。
- 「为什么 X」：派一张查询工单，不是改代码的；交回后 worktree 回到主分支、没有提交；读得出答案就「等你看」，读不出就「卡住了」、不能挪到已完成；「照这个改」起一张带 `parent` 的改代码工单。
- 农场自己能答的（现状、花费、工单历史）管家直接答，不派帮工。
- `verify-orchestrator-evals` 里每一节至少一条样例：记一下、哪些在等我、按编号问、改优先级要不要问、查询、早报。

## Risks

- **工具变多，管家挑错。** 24 个加 7 个；样例要覆盖「用哪个」的边界，描述里写清什么时候用、什么时候不用。可以合并：`issue_get` 并进 `issues`（给编号就是一张）。
- **查询比管家自己答贵**：每次开一个编码 agent。管家能直接答的要答。
- **「要有依据」挡不住编出来的依据**：页面把 `文件:行` 做成能点的，主人顺手就能核对。
- **健康度的阈值拍脑袋**：初版照上表，跑一阵看主人觉得准不准再调；阈值在一个文件里，有黄金数据。
- **和工单页并行改**：站位、`IssueAct` 两边都动，工单页先落地，这边在它之上做。
- 待定：查询是 `dispatch` 加 `kind`，还是单独的工具；`issue_get` 要不要并进 `issues`。
