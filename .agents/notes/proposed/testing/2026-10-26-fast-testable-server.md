# Agent Note: 服务端测试快一个台阶，模块按好测来设计

Status: proposed

## Problem

服务端 632 个测试，不并行地顺序跑要 210 秒。CPU profile 拆开看（跑测试的 worker 合计）：

| 去向 | 占比 |
|---|---|
| PGlite（JS 和 wasm） | 36% |
| node 内部：加载编译模块、起子进程、读写文件 | 30% |
| 空闲：等计时器、等 git 子进程 | 19% |
| GC | 4% |
| Effect 本身和业务代码 | 6% |

几件实测的事：

- 344 个测试各自不到 50 ms，合计 1.3 s；时间压在约 150 个要搭整个农场（真库、真 git、全部服务）的测试上。
- 把产品代码里写死的几个延时（通知合并 3 s、登录等 1.5 s、语音 2 s）改成几十 ms，总时间几乎不变：测试主要在干活，不在等。
- 每个农场从快照建一个 PGlite 要 111 ms；清空它的 28 张表只要 13 ms。
- 一个项目测试文件起 684 次 git，花在 git 上的约占这个文件的八成；每次 git 约 17 ms。
- vitest 默认每个测试文件重新加载一遍模块；关掉隔离（`isolate: false`）以后顺序跑是 150 s，632 个全过。

虚拟时钟（Effect 的 `TestClock`）只能跳过「等」，跳不过「干活」，所以靠它提速有限；它真正的价值是确定性，以及能测到长的时间窗口（4 小时后再提醒、60 秒冷却、暂停 1 小时）。可服务端还有 68 处 `Date.now()` / `new Date()` 和 18 处 `setTimeout` 绕开了 Effect 的 `Clock`，集中在 Promise 一侧（自己的大脑、连接器、轨迹、语音）。这些地方虚拟时钟管不到，用了反而会卡死，所以 29 个测试文件只能用 `it.live`。这正是「不好测的设计」：测试慢、不确定，根子在模块怎么拿时间、怎么建库、怎么调 git。

## Proposal

两条线，每一步一个 PR，做完量一次顺序运行的总时间。

**提速：让模块的接口本身便宜**

1. **测试库复用：`Database` 自己管内存库的池。** 内存模式下（`db: "memory"`，只有测试用），`Database` 从进程里的池取一个 PGlite；用完把全部表 `TRUNCATE … RESTART IDENTITY CASCADE` 清空后放回池里。同时开着的两个农场各拿一个，不共享。这件事归数据库模块，测试工具不另写一套。
2. **测试仓库从模板复制。** `testing/git.ts` 的 `repo()` 按参数（几个提交、什么文件）在每个进程里建一次模板，之后每个测试 `cp` 一份，不再每次 `git init` 加提交。
3. **产品代码少起 git。** 量出一次合并、一次派活各起几次 git；能合成一次的合成一次（读多个 ref 用一次 `git for-each-ref` 或 `rev-parse` 带多个参数，状态和差异用一次 `status --porcelain=v2`）。这既快了测试，也快了主人的机器。
4. **服务端测试不再逐文件隔离（`isolate: false`）。** 模块只加载一次。前提是没有测试靠模块级的可变状态互相影响：先跑多遍、换顺序跑，确认稳定再留。
5. **测试金字塔压低。** 搭整个农场的测试里，能在纯规则上断言的部分挪成规则测试，农场级的只留真要跨模块的那一条主线。

**可测性：时间只从 `Clock` 来**

6. **lint 规则**：`apps/server/src` 里不许 `Date.now`、`new Date()`（不带参数）、`setTimeout`、`setInterval`，只给 `base/` 里一个把 `Clock` 交给 Promise 一侧的适配处开例外。新写的代码从此只能经 `Clock`。
7. **Promise 一侧的类注入时间。** 大脑（`agent/brain`）、连接器、轨迹（`session/journal.ts`）、语音、宿主（`session/host.ts`）构造时接一个由 `Clock` 给的 `now()` 和 `sleep(ms)`，不再自己读墙钟、开计时器。
8. **依赖时间窗口的测试改用虚拟时钟。** 冷却、再提醒、错过补跑、暂停这类，用 `TestClock` 拨过去断言，不靠真睡、不靠改常量。

## Alternatives considered

**前后端共用一个时钟。** 页面和服务端是两个进程，要用 Playwright 的 `page.clock` 接管浏览器时间，再给服务端开测试专用的拨钟接口。页面的 96 个测试基本不依赖时间，投入换不来收益，不做。

**只把延时常量在测试里调小。** 实测几乎不省时间，而且测的不再是上线的数值；虚拟时钟拨过去才测得到真实的窗口。

**每个测试一个 Postgres schema，而不是清表。** 每个 schema 要重新跑一遍建表，比清表贵，也要改所有查询的 `search_path`。

**测试里把 git 换成假的。** AGENTS.md 定了用真的 git 仓库：合并、冲突、工作区这些最容易错的地方，假的测不到。所以只让它便宜（模板、少调），不换掉。

**加并行。** 不在这次的范围：先把每个测试本身的成本降下来，并行的收益会跟着放大。

## Acceptance criteria

- 服务端测试顺序跑的总时间从 210 s 明显下降，每一步的前后数字写在各自的 PR 里。
- `apps/server/src` 里 `Date.now`、无参数的 `new Date()`、`setTimeout`、`setInterval` 由 lint 拦下，只剩一处开了例外的适配。
- 冷却、再提醒、补跑、暂停这类时间窗口的测试用虚拟时钟，不真睡。
- `server:check`、CI 全绿；`isolate: false` 换顺序跑多遍也稳定。

## Risks

- 清表漏了状态（序列、非表的设置）会让测试互相影响：清完要和新库一样，用一个测试比对。
- `isolate: false` 下，模块级的缓存（`memoryBase`、各处的单例）会跨文件存活，测试顺序一变可能出错；不稳定就退回。
- Promise 一侧注入时间要改大脑、连接器这些类的构造，牵动面大；按模块一个个来，每个都有测试兜着。
- 少调 git 改的是合并、派活这类核心路径，必须由现有的流程测试覆盖住再动。
