# Agent Note: 把模块层往下压：项目检查成端口，重启留在内存，项目的决定成规则

Status: proposed

## Problem

[测试金字塔](docs/subsystems/foundation.md)立起来以后，服务端的形状是：规则 205 个测试 3.3 秒，模块 398 个 48 秒，流程 44 个 18.6 秒（顺序跑）。模块层占了七成，钱花在三个地方：

- **项目检查是真进程。** 项目模块的测试 19.6 秒（`project.test.ts` 14.8、`github.test.ts` 4.8），占模块层四成。最慢的三个都在真跑 `.vibevalley/check`：「检查在项目的轮次外跑」3.9 秒、「合并跑检查：没有、通过、失败」3.5 秒、「检查跑太久被停掉」2.2 秒。每个用例新写一个脚本再执行，macOS 第一次执行新文件要扫一遍（0.4–1 秒）。测合并的规矩（检查期间分支变了要拒、检查失败不合）不需要真进程，只需要「检查说了什么、什么时候说」。
- **重启要建磁盘上的库。** 15 处测试用 `db: ""` 在临时家目录里建磁盘库，重启时再打开，为了证明「重启以后还在」。从拷贝建一个约 350 毫秒，开一次约 70 毫秒；连接器里最慢的三个、提及、田头的重启测试都是这样。它们要证明的是我们的服务从库里读回来，不是 PGlite 能落盘。
- **项目的决定和 git 写在一起。** 释放工作区时留不留分支、合并走快进还是合并提交还是拒绝，都写在 `project.ts` 里一串 git 调用中间，只能搭真仓库测，一张决定表要搭好几个仓库。

## Proposal

**1. 项目检查成端口。** 项目自己的检查是外面的程序，归到 `ProjectHooks.check`（和 `gh`、`push`、`fetch` 一样）：

- 真的适配器 `project/check.ts`：现在 `projectCheck` 的那段挪过去（找 `.vibevalley/check`、在工作区里跑、超时连子进程一起停、留最后的输出）。
- 测试里换成进程里的检查：照测试说的通过、失败（带输出），或停在门口等测试放行（「检查期间」的测试不再 `touch` 文件再轮询）。
- 真适配器只在自己的测试里跑真脚本：没有、通过、失败带输出、不能执行、太久被停，一种一个用例。

**2. 重启留在内存。** 测试的库可以有名字：`testConfig({ db: keptDatabase() })` 给一个名字，`Database` 遇到有名字的内存库，农场关的时候不清空、不还池，留给下一座同名的农场。测试结束时由测试放掉（`Effect.ensuring`，和现在删临时家目录一样）。重启测试只换这一行；只有测磁盘本身的（`base/db.test.ts` 的挪开旧库、`.schema` 记号、从拷贝建盘上的库）留在磁盘上。

**3. 项目的决定成规则。** `project/rules.ts`：把「看到了什么 → 做什么」写成纯函数，项目模块先看（一组 git 的读），再问规则，再照做：

- 释放工作区：工作区删得掉吗、分支在不在、领先几个提交 → 删 / 留（带理由）。
- 合并：分支是不是检查时的那个、主分支有没有变、有没有冲突、能不能快进 → 快进 / 合并提交 / 拒绝（带理由）。

决定表在规则层测（每种情况一行），模块测试每条路只留一个接线用例。

每步一个 PR，写上金字塔小结的前后（模块层的测试数和秒数，规则层多了多少）。

## Alternatives considered

- **只缩短检查的超时、复用一个脚本**：省一点时间，但合并的规矩还是要真进程才测得到，「检查期间」还是靠轮询文件。
- **项目测试换成假 git**：AGENTS.md 定了真的 git；合并、冲突、工作区正是最容易错的地方。端口只放在检查这个真正的外面。
- **重启测试不重启，只重建服务**：同一个连接测不到「关掉以后再开」时我们自己的开机路径（读回、退回交出去的投递）；同名内存库照样走一遍开机。
- **把项目模块拆成「决定」和「执行」两个服务**：多一个服务、多一层组装；纯函数放在 `rules.ts`，照现在每个模块的样子就够。

## Acceptance criteria

- 合并、PR、释放工作区的模块测试不再起检查进程；真检查只在 `check.ts` 的测试里跑。
- 重启测试（除了测磁盘的）不再建磁盘库。
- `project/rules.ts` 有释放和合并两张决定表，在规则层测；`project.ts` 照决定做。
- 模块层的秒数明显下降，规则层的测试数上升；数字在各自的 PR 里。

## Risks

- 假检查和真脚本的语义要一致（退出码、输出、超时的说法）：真适配器的测试覆盖每一种，假的只产出同样形状的结果。
- 有名字的内存库忘了放掉会留在进程里：只在 `Effect.ensuring` 里放，测试结束时还有没放掉的就报。
- 抽决定时改了行为：先在规则层把现在的行为写成表（照现有测试的期望），再换调用处。
