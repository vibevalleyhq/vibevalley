# VibeValley 概念与命名架构审计（基于 `d376c1b9` 及最新边界收拢实现）

## 一、对上一答五处推断的复核与修正

在进入新的概念与命名设计前，先对照 [地基](docs/subsystems/foundation.md)、[核心状态](docs/subsystems/core.md)、[帮工](docs/subsystems/session.md)、[计划](docs/subsystems/task.md)、[频道](docs/subsystems/channel.md) 的「为什么这样」及 [2026-11-01-argon-execution.md](.agents/reviews/2026-11-01-argon-execution.md)，逐项纠正上一答中的不实推断：

1. **关于 `X` 与 `XView`（`SessionView`、`CronView`、`DoingView`、`WorkspaceView`）**：
   - **修正**：这不是多余类型树，而是「**给人看的话只在出帧时填，不进 `reduce`、不落盘 `state.json`**」的静态类型边界（[core.md](docs/subsystems/core.md#为什么这样)）。话随时会改、随语言变，一旦写进 `WorkspaceState` 就会落入 `state.json` 带来旧文案兼容负担，并污染 `Transition` 持有的前后状态快照。
   - **真正的矛盾点**：不是 `View` 不该存在，而是 **`Task` / `TaskGraph` 和 `Issue` 破坏了这条边界**——`Task` 把出帧才填的 `stateText`、`actions`、`actionText`、`canEdit`、`canRemove` 直接混在了领域类型 `T.Task` / `T.TaskGraph` 上，迫使服务端到处调用塞空字符串的假构造函数 `graphView()` / `taskView()`（`apps/server/src/task/graph.ts:7-23`）。
2. **关于 `Task` 事件（`task_event`）与工单运行时间线（`IssueTimeline`）**：
   - **修正**：两者不可替代。`IssueTimeline`（`apps/server/src/issue/timeline.ts`）是从工单状态和 `session_run` 现算的**执行里程碑**；而 `task_event`（`apps/server/src/task/changes.ts`）记录的是**含人工/管家编辑历史的审计账**（谁把哪一步的 `check` / `needs` / `brief` 从什么改成了什么、谁点了暂停/继续/跳过）。删除 `task_event` 会丢失步骤字段修改的前后对比（`TaskFieldChange`）和操作者归属（`ActorKind`）。
3. **关于进程内 `InProcessRun`（管家）与外部 `Session` 轮次（帮工）**：
   - **修正**：两者语义边界不同，不能合并成同一个状态机（[session.md](docs/subsystems/session.md#为什么这样)）。帮工的一个 `Run` 对应一次 `oar` turn，一对一绑定单张工单；而管家的 `InProcessRun` 对应一次进程内 `Brain` loop（`agent_start` 到 `agent_end`），**单次 loop 可连续消费多条排队输入、关联多张工单（`session_run_issue`）**，且消息回执（`inputsConsumed`）必须在 loop 真正消费该输入（`message_start`）时才提交，终结写库失败时还需保持 `ending` 状态阻塞新输入直至重试成功。两者的共享层已经在 `apps/server/src/session/recording.ts` 抽齐，上层状态机必须分离。
4. **关于 PGlite 与 `channel` 内存状态（`ChatModel` / `Audience` / `Deliveries`）**：
   - **修正**：PGlite 是单连接 WASM Postgres，每次查询都有 SQL 解析、WASM 边界编解码和异步 `Effect` 调度成本，不是零成本的 JS `Map`。`channel` 在高频消息流中查询频道关系、@ 提及冷却、跳数限制（`hopLimit`）和待投递队列时，读内存镜像是合理的设计（[channel.md](docs/subsystems/channel.md#模型和不变量)）。真正该审视的是概念职责与切分，而非把高频同步查找退回每次查 WASM SQL。
5. **关于行数统计与口径**：
   - **修正**：上答将生产代码与测试代码混算，且正文估算与汇总表数字自相矛盾；本次审计不再以凑删行数为目标，严格围绕**消除多余概念、消除跨层职责泄漏、统一领域命名**展开。

## 三、逐项详解：可以消除的概念（E1–E5）

### E1. 消除 `Task` 模块的平行执行与 Git 端口（`TaskWork` / `TaskGit` / `TaskOptions.usable`）

- **现有概念及路径**：
  - `apps/server/src/task/task.ts`：第 130–154 行 `export interface TaskWork`、`export interface TaskGit`、`export interface TaskOptions`，第 169–176、188–189 行默认实现分支，第 161 行 `export const make`。
  - `apps/server/src/task/task.test.ts`：第 58–200 行 `class FakeWork implements TaskWork`、`class FakeGit implements TaskGit`（手搓 `core.apply({ type: "hired" | "run" | "report" | "left" })` 伪造帮工生命周期）。
- **造成的矛盾 / 重复**：
  1. **与 `da5c59dc`（移除 `Channel` 的 `Helpers` 测试端口）违背同一原则**：此前 `Channel` 为了单测定义了一套 `Helpers` 接口代替 `Session`，已在 `#225` 中作为冗余抽象彻底删除；但 `Task` 仍保留着一模一样的 `TaskWork`（包装 `Issue.hire` 和 `Session.deliver`/`dismiss`/`lastTextOf`/`handOver`）和 `TaskGit`（包装 `Project` 的 6 个方法）。
  2. **破坏 `Issue` / `Assignment` / `Session` 不变量**：`FakeWork.hire` 直接向 `Core.apply` 注入假的 `hired` 事实，既不写 `issue_assignment_execution`，也不经过 `Executor` 占槽和 `Project` worktree 分配。正因如此，上一轮审计在收拢 `Issue.ran` 时，不得不把 `task.test.ts` 里两项验证父子工单和拆单关系的测试迁去 `apps/server/src/flows/task.test.ts`（见 [2026-11-01-argon-execution.md](.agents/reviews/2026-11-01-argon-execution.md) 第 19 行）。
  3. **多维护一套假状态机**：`FakeWork` 自己维护 `last`、`attempts`、`written`、`started`、`touched`、`told`，与 `scriptedRuntime` 的能力完全重复。
- **保留的唯一语义**：
  - `Task` 服务直接依赖 `Issue`、`Session`、`Project`、`Runtime` 四个正式 `Context.Service`；测试一律在 `scriptedRuntime` 和真实/模板 Git 仓库（`testing/git.ts`）或 `Project` 服务层接缝上运行。
- **删除 / 合并 / 重命名后的边界**：
  - 从 `apps/server/src/task/task.ts` 删除 `TaskWork`、`TaskGit`、`TaskOptions`，`Task.layer` 改为无参静态成员 `static readonly layer = Layer.effect(Task, Effect.suspend(() => make))`（与 `Channel.layer`、`Artifact.layer` 完全一致），并取消 `make` 的导出。
  - 删除 `apps/server/src/task/task.test.ts` 中的 `FakeWork` 和 `FakeGit`，改用 `scriptedRuntime` 驱动真实 `Session`（对纯规则断言保留在 `graph.ts` / `splitting.ts` / `editing.ts` 的纯函数测试中）。
- **外部行为如何保持**：
  - 生产环境中 `options` 本来就为空（`services.ts` 调用 `Task.layer()`），生产代码路径零变化。
- **反例（如果不消除会怎样）**：
  - 任何对 `Session.handOver`、`Session.deliver` 或 `Issue.hire` 签名的演进都要同步改一遍 `TaskWork` 和 `FakeWork`；且 `task.test.ts` 在假端口上通过的测试无法证明真实 `Assignment` 和 `Session` 锁顺序没有死锁。
- **验收**：
  - `vp run server:check && vp run deadcode`
  - `vp test apps/server/src/task/ apps/server/src/flows/task.test.ts`

### E2. 消除 `Runtime` 服务实例上的 `Object.assign` 内部状态后门

- **现有概念及路径**：
  - `apps/server/src/runtime/runtime.ts`：第 584–590 行：
    ```ts
    return Object.assign(shape, {
      refreshUsage,
      cached: held,
      spent: () => spent,
      setSpent: (s: Spent) => (spent = s),
    });
    ```
  - `apps/server/src/runtime/runtime.test.ts`：通过类型转换或直接调用 `make()` 访问 `refreshUsage`、`cached`、`spent`、`setSpent`。
- **造成的矛盾 / 重复**：
  1. **与上一轮已清除的 `SessionsInside` 完全同构**：[session.md](docs/subsystems/session.md#模型和不变量) 已明确立下规矩：「服务只返回声明的接口，不附带内部对象」。但 `runtime.ts` 仍在 `Runtime.of({...})` 返回值上用 `Object.assign` 偷挂了 4 个不在 `Context.Service` 声明里的私有方法，且 `export const make` 暴露了内部构造器。
  2. **`setSpent` 绕过持久化与日期切换主线**：生产中花费通过 `Runtime.spend(id, cny)` 累加并写入 `spend.json`，跨日通过 `Clock`（`dayOf(clock.currentTimeMillisUnsafe())`）自动清零；测试用 `setSpent` 直接篡改内存变量，跳过了真实的 `spend.json` 落盘与 `TestClock` 跨日推进。
- **保留的唯一语义**：
  - `Runtime` 服务只暴露 `Context.Service` 声明的公开方法；跨日花费清零通过 `TestClock.adjust` 验证，初始存盘恢复通过在 `home` 目录写入 `spend.json` 或调用 `runtime.spend` 验证，用量刷新通过 `runtime.usageSoon` + `TestClock` 验证。
- **删除 / 合并 / 重命名后的边界**：
  - 删除 `apps/server/src/runtime/runtime.ts:584-590` 的 `Object.assign`，直接 `return shape;`，取消 `make` 的导出。
  - `apps/server/src/runtime/runtime.test.ts` 全部通过 `yield* Runtime` 公开接口 + `TestClock` 测试。
- **外部行为如何保持**：
  - 生产代码无任何调用方使用这 4 个后门属性，对外 API 与行为完全不变。
- **反例**：
  - 保留 `Object.assign(shape, ...)` 会让其他 Agent 照抄这种绕过 `Context.Service` 契约的后门模式（正如之前 `Session` 的 `SessionsInside`）。
- **验收**：
  - `vp test apps/server/src/runtime/runtime.test.ts`
  - `vp run server:check && vp run deadcode`

### E3. 消除 `Task` / `TaskGraph` 上的空壳视图填充器 `graphView()` / `taskView()`（对齐 `*View` 出帧边界）

- **造成的矛盾 / 重复**：

- **保留的唯一语义**：
  - 服务端领域层持有纯粹的 `Task` 与 `TaskGraph`（只含持久化和调度所需的领域字段）；出帧计算的派生展示字段（`stateTag`、`stateText`、`actions`、`actionText`、`canEdit`、`canRemove`、`layers`、`blockedBy`、`asksForYou`、`settled`）归入 `TaskView` 与 `TaskGraphView`（由 `frameOf` 和 `graph.list` / `graph.get` 统一经一个 `graphViewOf(graph)` 纯函数稿子）。
- **删除 / 合并 / 重命名后的边界**：
  - 删除 `apps/server/src/task/graph.ts:7-23` 的空壳填充函数 `taskView()` 和 `graphView()`，以及全仓 8 处 `...graphView()` / `...taskView()` 展开。

- **外部行为如何保持**：
  - 线上 JSON 结构（`StateFrame.graphs`、`graph.list`、`graph.get`）的每一个字段名与取值 100% 保持不变。
- **反例**：
  - 若保留现状，服务端任何地方读 `graphOf(core.state(), id)` 拿到的 `graph.actions` 都是 `[]`、`graph.stateTag` 都是 `""`（因为只有在 `frame.ts` 里才填），极易引发服务端误读空数组。
- **验收**：
  - `vp check && vp run server:check && vp run web:check`

### E4. 消除 `Issue.start` 公开服务方法与 `Dispatched`，统一收拢至 `Issue.setStatus`

- **现有概念及路径**：
  - `apps/server/src/issue/issue.ts`：第 73 行 `readonly start: (id: string, channel: string) => Effect.Effect<Dispatched, ApiError>;`、第 114–118 行 `export interface Dispatched`、第 468–484 行 `start` 实现、第 979–981 行服务挂载。
  - 外部唯一生产调用方：`apps/server/src/tool/issue.ts`（管家的 `issue_create` 在 `start: true` 时调用 `issues.start(made.id, where)`）。
- **造成的矛盾 / 重复**：
  1. **上一轮收拢 `Issue` 写入口后的最后一处漏网分支**：在 `2026-11-01-argon-execution.md` 的建议 1 中，我们已经从 `Issue` 公开接口删除了 `queue`、`merge`、`cancel`、`ran`，确立了「完成、取消和排队经 `setStatus` 的状态机执行」（[issue.md](docs/subsystems/issue.md#模型和不变量)）。
  2. 但 `Issue.start` 仍然暴露在公开接口上，导致「把一张备选工单派出去」有两个公开入口：`issues.start(id, channel)` 和 `issues.setStatus(id, "todo", "", channel, by)`。

## 五、必须保留的边界（绝不回退或错误合并的 6 条架构支柱）

为避免后续简化误伤系统根基，明确列出经本次复核确认**必须原样保留**的边界：

1. **B1. `Assignment`（责任）→ `Session`（持续上下文）→ `Executor`（底层 oar 资源）三层分离**：
   - `Assignment` 在未派工时即可存在、跨多次重开保留责任，只在换人/取消指派时结束；`Session` 管领域生命周期、轮次和轨迹；`Executor` 管底层 `oar` 实例与关闭失败时的目录占槽保护（上一轮刚完成 `ExecutionOwner` 快照隔离与 `Hand.sess` 移除，边界已非常干净）。
2. **B2. `IssueStatus`（存储/流程状态）与 `IssueStage`（服务端现算的给主人看的状态与动作集 `acts`）**：
   - 页面不自己判断工单卡在哪、有哪些按钮可点，一切以服务端算出的 `IssueStage` 为准；写入口统一走 `issue.status.update` 与 `issue.comment.create`。
3. **B3. 核心状态（`WorkspaceState`）与出帧视图（`*View` / `StateFrame`）的分离**：
   - `reduce` 只折纯粹的事实并落盘 `state.json`；随语言和时钟变化的展示文案（`actionText`、`phaseText`、`whenText`、`nextText`）只在 `projection/frame.ts` 出帧时填入 `*View` 副本（因此 E3 的方向是让 `TaskGraph` 也补齐这层边界，而不是删掉 `SessionView`/`CronView`）。
4. **B4. 进程内 `InProcessRun` 与外部 `Session` 轮次的上层状态机分离**：
   - 共享底层 `session/recording.ts` 的 SQL 持久化即可；上层保留 `InProcessRun` 对单 loop 多工单关联（`session_run_issue`）、消费时点回执（`inputsConsumed`）和终结失败重试阻塞（`ending`）的专门控制。
5. **B5. `Task` 作为父子 `Issue` 存储、按整图纯函数计算、以 `graphChanges` 记录含人工编辑的 `task_event`**：
   - [task.md](docs/subsystems/task.md#为什么这样) 已明确说明：「规则仍按整张计划算，读写时拆拼」「经过由比较得出，回答这一件怎么走到这里的、工单被谁改过」。保留 `graphsOf` / `graphIssues` 的纯函数拆拼和 `task_event` 审计表，只消除 E1（假测试端口）和 E3（`graphView()` 空壳填充）。
6. **B6. `packages/protocol` 的 `shapes.ts` 与 `schema.ts` 分离（以及生成 `client.ts`）**：
   - [foundation.md](docs/subsystems/foundation.md#模型和不变量) 明确规定：生成 `client.ts` 且让页面只 import `shapes.ts` 类型，是为了**让工作台前端（除 WebSocket 房间订阅外）不必在运行时加载整套接口与状态的 Effect Schema**，从而控制前端包体积并利用 `Codec<T.X>` + `schema.test.ts` 实现双向编译期与键集合锁死。这条边界有明确的工程收益，予以保留。
