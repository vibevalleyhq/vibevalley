### 2. 归属证据辨析：哪些证明 DAG 属于 Agent 能力，哪些只是工单载体/投影，哪些是真实耦合

#### （1）支持「DAG 本质是 Agent 能力（规划、分派子任务、自检推进）」的代码与历史证据
1. **核心抽象源于 Agent package**：DAG 的拓扑定义与分层算法 `packages/agent/src/dag.ts` 位于 `@vibevalley/agent` 包内；其文件头注释（`dag.ts:1`）和早期提交 `74b10145`（`Tasks are DAGs: the farm's task graph, the agent's own task graph, one module`）明确记录：最初设计就是把「Agent 把一件活拆成有依赖关系的几步、按依赖并发派发执行并回收结果」作为统一的能力（当时统一叫 `Task`，表名叫 `task_graph` / `agent_task`）。
2. **`issue_split` 与 `graph.split` 的发起与决策主体都是 Agent**：
   - 在 `graph.split` 中，拆图不是人填表建子工单，而是派一个作为「规划师」的 Agent 读仓库代码产出 DAG（`task/prompts.ts:159`）；
   - 在 `issue_split`（`task/task.ts:522`）中，更是正在干活的 Agent 自己发现任务太大，主动调用工具将当前任务裂变为一张并发执行的 DAG，且**无需主人审批直接进入 `running` 自动调度**。
3. **两套状态机与推进语义高度同构**：
   - 对比 `packages/agent/src/todo.ts` 与 `apps/server/src/task/graph.ts`：节点状态同为 `waiting | working | done(merged) | failed | skipped`；推进条件同为上游全部 `done(merged) | skipped`；都有并发槽位控制（`maxSubagents = 3` vs `defaultParallel = 3`）、失败自动打回重试（`retries = 1` vs `autoRetries = 2`）、中断/重启退回或暂停恢复。
4. **演进过程中的命名漂移痕迹**：
   - 在提交 `f527d936`（#204，用语表批量对齐）中，为了满足「一个词只指一样东西」，机械地将 `packages/agent` 里的 `agentTask.ts` 改名为 `todo.ts`、表 `agent_task`（最初叫 `task_graph`）改名为 `runtime_todo`，并把 `apps/server/src/agent/taskStore.ts` 挪到了 `runtime/todoStore.ts`；但 `todo_add` 的模型参数至今仍叫 `tasks`（`todoTools.ts:30`），提示词仍写「把一件要分几步、有先后的活写成任务」（`prompts.ts:132`）。这说明它从一开始就不是普通的勾选项 Todo，而是给 Agent 配的 DAG 任务分解与子代理调度能力。
   - 同时，未完成的架构提案 `.agents/notes/proposed/architecture/2026-10-28-toolsets-and-skills.md`（第 53–66 行）明确写道：**工具能力应作为 `Agent.toolsets` 配置在 Agent 档案上**（「给一个帮工加上 `issue`/`graph`，它就是能拆子工单的领班」），而不是像现在这样按 `role` 硬编码给所有工单帮工。

#### （2）哪些只是「工单作为任务载体或看板投影视图」
- 在 `apps/server/src/task/issues.ts` 中，`graphIssues(graph, before, now)` 将 `GraphSpec` 映射为父子 `Issue` 行，`graphFrom(parent, issues)` 再从 `WorkspaceState.issues` 拼回 `T.TaskGraph`。
- 历史 Note（`2026-10-15-tasks-are-parent-issues.md`）写得很清楚：早先 `Task`（当时叫 `Playbook`）是独立存在 `state.json` 的 `tasks` 字段里的，后来为了**避免看板上同一件事既有计划卡又有散落工单、且能复用核心状态同步与看板展示**，才把 `TaskGraph` 的持久化压进了 `issue` 表的 `graph` / `task` JSON 列。
- 换言之：**子工单（`p1.api`）在看板上不可手动挪状态（`moves: []`）、不可单独完成、不可单独重开（`issue/status.ts`、`issue/moves.ts`），它根本没有独立的 `Issue` 生命周期**；它只是把 `issue` 表借来当作 DAG 节点的持久化行与 UI 钻取视图（点开看某个节点的帮工轨迹）。

#### （3）当前代码里「把 `Task` 焊死在 `Issue` 上」的真实耦合点
当前 `apps/server/src/task/task.ts` 并非纯粹借用 `Issue` 做存储，而是在以下 4 处形成了对 `Issue` 服务的深度反向耦合：
1. **写路径耦合（`Task.put` → `Issue.putTask`）**：`Task` 自己没有表读写（除 `task_event` 外），每次状态变化都必须构造整棵 `GraphSpec` 调 `issues.putTask(graph)`，触发 `issue`、`issue_assignment` 全家重写。
2. **执行派发耦合（`Task.cron` / `Task.split` → `Issue.hire`）**：`Task` 派规划师和派每个 DAG 节点帮工时，调的不是 `Session.send`，而是 `issues.hire(agent, brief, project, { issue: taskIssueID(graph.id, task.id), taskGraph: tag, ... })`（`task.ts:251, 504`）。这迫使每个 DAG 节点都必须先是一张拥有 `Issue` 编号、`issue_assignment` 和 `issue_assignment_execution` 记录的工单。
3. **拆单入口耦合（`issue.split` 挂在 `issue` 命名空间下）**：协议接口叫 `issue.split`（`api.ts:137`），帮工工具叫 `issue_split`，且 `splittable`（`task/prompts.ts:114`）强制要求调用方必须绑定在一张 open `Issue` 上（频道私聊 Session 或无工单的 Agent 根本无法使用 DAG 拆解能力）。
4. **`Issue` 状态机被迫到处给 `graph` / `task` 写特判逃生口**：
   - `issue.ts` 中 `unsent`（L228）、`reopen`（L519）、`onSessionNews`（L791）、`place`（L887）、`review`（L1081）全部要写 `if (issue.graph || issue.task) return refused(...)`；
   - `issue/status.ts` 和 `issue/moves.ts` 被迫内置一套平行的「当 `issue.graph` 或 `issue.task` 存在时，如何从 DAG 状态反推伪造一个 `IssueStatus` 并清空 `moves`」的规则。

### 4. 保持用户行为的目标模型（职责、边界与命名，不新增框架）

要在不破坏现有页面（`TaskBoard.tsx`、`TaskDetail.tsx`、`StateFrame.graphs`）和用户可感知行为的前提下，把 DAG 归还给 **Agent 能力**，同时解开与 `Issue` 的错位耦合，目标模型应当只用现有模块，按以下职责收口：

| 概念 / 模块 | 职责归属（管什么） | 明确不管什么（交给谁） | 关键命名与边界修正 |
|---|---|---|---|
| **`Agent`（AgentProfile，档案）** | **能力的配置主体**：<br>决定该档案是否开启 DAG 能力、允许哪种执行模式（进程内子代理 vs 跨 worktree 派帮工）、默认并发度与工具集（与 `2026-10-28-toolsets-and-skills.md` 的 `toolsets` 对齐）。 | 不管运行期某次具体的图状态；不管工单流转。 | 在 `Agent` 配置上显式表达能力（如 `toolsets` 中的 `graph` / `task`，或档案的 DAG 配置项），而不是在 `tool.ts` 按 `role` 一刀切给所有 session 塞 `issue_split`、或在 `runtime/vibevalley.ts` 暗自塞 `todos`。 |
| **`TaskGraph` / `Task`（Agent 的 DAG 定义与运行实例）** | **Agent 执行复杂任务的 DAG 编排器**：<br>1. 承接 Agent 发起的拆解（规划师拆图，或执行中的 Agent 自拆当前任务）与主人的启停/合并控制；<br>2. 维护 DAG 节点拓扑（共用 `@vibevalley/agent/dag`）、节点状态（`waiting / working / done|merged / failed / skipped`）、并发度、重试计数、验收步冻结文件与计划分支合并；<br>3. `completeGraph(spec: GraphSpec): T.TaskGraph` 纯函数在 `task/graph.ts` 一次性算齐分层、阻塞、花费与可执行动作。 | **不再把每个节点伪装成完整生命周期的 `Issue`**：节点执行直接调 `Session`（开分支 worktree 会话、带话、交接合并），不再绕道 `Issue.hire` 造假工单。 | • 模块仍叫 `Task`（`apps/server/src/task`），协议形状仍叫 `T.TaskGraph` / `T.Task`（保持 `StateFrame.graphs` 和 `graph.*` API 契约稳定）；<br>• 调度函数 `cron` 改名为 `advance`（消除与定时任务 `Cron` 的同名异义）；<br>• 帮工自拆工具从 `issue.split` 收归 `graph` / `task` 语义（对外 v1 HTTP 路由可保留别名转发）。 |
| **`Issue`（工单）** | **主人与工作台的任务单 / 需求契约**：<br>管一张工单从 `backlog → todo → in_progress → in_review → done / canceled` 的状态机、起草（`refine`）、问题（`questions`）、验收标准（`criteria`）、责任指派（`Assignment`）及最终交付（`merged / pull_request / kept / none`）。 | **不管 DAG 内部节点的调度、不给每个 DAG 步骤维护一套残废的 `Issue` 状态机**。 | 当一张 `Issue` 交给配置了 DAG 能力的 Agent 执行（或帮工在执行该 `Issue` 时触发 DAG 拆解）时，**整张 `Issue` 只关联这一个 `TaskGraph`（1:1 关联或作为该 Issue 的执行图）**，而不是在 `issue` 表里裂变出 12 张 `moves: []` 的假子工单。`Issue` 自身的 `statusMove`、`unsent`、`reopen` 彻底删掉针对子工单 `issue.task` 的特判分支。 |
| **`Session`（帮工会话）** | **Agent 档案的一次持续执行上下文**：<br>持有工作目录/worktree（`Workplace`）、轨迹日志（`Journal`）、Run 记录（`session_run`）、记忆召回与通道对话。既可为一张 `Issue` 服务，也可为 `TaskGraph` 的一个节点（`task`）服务，或为频道私聊服务。 | 不管工单的业务验收；不管 DAG 的拓扑排序。 | `Session.send` 是派发帮工会话的唯一正式入口：`Issue` 开工调 `Session.send`，`Task` 调度节点也直接调 `Session.send`（经 `Session.makeRoom` 共享工作区/项目/农机并发上限），不再让 `Task` 倒过来调 `Issue.hire`。 |
| **`Executor`（执行器）** | **底层 oar 会话进程/纤程的资源生命周期**：<br>管 `Runtime.resolve`、oar 会话 `spawn`/`send`/`interrupt`/`dispose`、卡死检测（`watchStalls`）与未释放资源占槽。 | 不认识 `Issue`、不认识 `TaskGraph`。 | 保持上一轮已收敛的窄快照边界不变。 |
