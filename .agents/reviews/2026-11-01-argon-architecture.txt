### 优化三：收窄 `Executor` 与 `Session` 边界，消除 `Executor` 持有的完整 `T.Session` 副本、`Hand.sess` 双轨引用及启动失败的重复清理

#### 1. 路径
- `apps/server/src/executor/executor.ts`（第 18–33 行 `Execution` / `StartExecution`、第 50–61 行 `Allocation`、第 186–242 行 `start`、第 287–288 行 `find` / `all`）
- `apps/server/src/session/session.ts`（第 89–108 行 `Hand`、第 310–319 行 `handRow`、第 424–428 行 `watch`、第 514–567 行 `attach` / `failedOpening` / `open`、第 582–611 行 `rest` / `capacity`、第 653–667 行 `deliver`、第 842–865 行 `makeRoom` / `send`、第 914–970 行启动登记与清理、第 973–984 行 `stop`、第 1032–1037 行 `clearWorkplace`）

#### 2. 问题机制
1. **`Executor` 持有了完整的 `T.Session` 领域状态对象**：[docs/subsystems/session.md](docs/subsystems/session.md) 明确规定：「`Executor` 拥有执行资源，不保存第二份工单或 Session 状态… **执行器拥有资源，Session 拥有领域状态**」。但 `apps/server/src/executor/executor.ts:19, 28` 在 `Execution` 和 `StartExecution` 中要求传入并保存完整的 `readonly owner: T.Session;`（包含 `phase`、`runs`、`brief`、`lastRun`、`conflict`、`play` 等随事实演进的领域状态快照）。实际上 `executor.ts` 仅读取 `owner.id`（第 133、187 行），而 `session.ts` 也仅在 `capacity` / `send` / `clearWorkplace` 中读取未挂接或未释放分配的窄归属元数据（`id`、`agent`、`runtime`、`project`、`issue`、`channel`）。
2. **`Session` 与 `Executor` 双轨持有可变 `Allocation` 引用导致状态不一致**：
   - `executor.ts:239` 在 `start` 返回时直接把内部可变对象 `allocation: Allocation` 作为 `Execution` 暴露给调用方，`session.ts:517` 将其存入 `h.sess = s`。
   - `Session` 内部因此出现两套不一致的查询路径：`handRow`（第 311 行）、`deliver`（第 653、660 行）、`rest`（第 586 行）、`stop`（第 974 行）读 `h.sess`，而 `capacity`（第 601 行）、`makeRoom`（第 843 行）、`send`（第 956 行）读 `executor.find(id)`。
   - 当 `wake`（第 628–643 行）先 `rest(h)` 清空 `h.sess = undefined`，再调 `open` 启动新会话失败且底层关闭也失败（`retained: true`）时，`Executor` 的 `allocations` 中仍留着处于 `closing: true, failure: ...` 的实例，但 `h.sess` 却是 `undefined`。此时若再次调 `deliver`（第 653 行），`if (h.sess?.closing === true)` 会漏检，导致继续进入 `wake` 再次触发关闭。
3. **`Session.send` 启动登记失败时的双重清理与重复报错**：
   - 在 `session.ts:914-924` 中，`Effect.result(...)` 已经捕获 `NotRecorded` 并在第 922 行调用 `failedOpening(id, ...)`（内部调 `executor.failed(id, why)`，若 `retained: true` 则发 `core.notice("error", failure.refused)`）。
   - 但第 920 行又挂了 `.pipe(Effect.onError((cause) => failedOpening(...)))`，且外层 `starting.pipe(Effect.onExit(...))`（第 951–970 行）在非成功退出且 `!committed && !released` 时会再次检查 `executor.find(id)`、再次调用 `executor.close(id)` 并在失败时再发一条 `core.notice("error", ...)`。当 `opt.hiring` 发生中断或 defect 且农机关闭失败时，会执行两次关闭等待并向主人发送两条重复的错误通知。

#### 3. 具体修改
1. **收窄 `Executor` 的归属类型并隔离内部可变 `Allocation`**（`apps/server/src/executor/executor.ts`）：
   - 将 `Execution` 与 `StartExecution` 中的 `owner: T.Session` 收窄为只含占位与归属标识的窄接口 `ExecutionOwner`：
     ```ts
     export interface ExecutionOwner {
       readonly id: T.SessionId;
       readonly agent: string;
       readonly runtime: string;
       readonly project?: string;
       readonly issue?: T.IssueId;
       readonly channel?: string;
     }
     ```
   - `find(id)` 与 `all()` 返回只读视图 `{ owner, sessionId, attached, closing, failure }`（或由 `Allocation` 映射），不向外部暴露内部可变 `Allocation` 实例。
2. **移除 `Hand.sess` 双轨引用，以 `executor.find(h.id)` 作为执行状态的唯一来源**（`apps/server/src/session/session.ts`）：
   - 从 `Hand` 接口（第 95 行）中移除 `sess: Execution | undefined;`。
   - 在 `attach`（第 516–530 行）中记录 `if (s.sessionId) h.oarSessionId = s.sessionId;`，`watch`（第 427 行）通过 `launch`（`const atLaunch = h.launch; ... if (h.launch === atLaunch && event.agentPath.length === 0)`）判断当前启动代次。
   - 在 `deliver`（第 653、660 行）和 `stop`（第 974 行）中统一通过 `const exec = executor.find(id);` 检查 `exec?.closing === true` 与 `!exec?.attached || !h.launch`。
   - 在 `rest`（第 585–594 行）中通过 `const exec = executor.find(h.id);` 保存 `exec?.sessionId` 并调用 `yield* closeExecution(h)`、清理 `closedLaunch(h)`。
   - 在 `capacity()`（第 596–611 行）中将未发布的 `executor.all()` 项按 `ExecutionOwner` 转为占槽所需的最小对象（或直接让 `hiring.ts` 的 `noRoom` / `sessionName` 接收 `Pick<T.Session, "id" | "agent" | "runtime" | "project" | "phase">`）。
3. **合并 `Session.send` 的失败回滚出口**（`apps/server/src/session/session.ts:914-970`）：
   - 移除第 920 行冗余的 `.pipe(Effect.onError(... => failedOpening(...)))`（`NotRecorded` 已由 `Effect.result` 在第 921–924 行走 `failedOpening` + `refuseStart` 完整处理并置 `released = true`，而 `retained` 分支也置 `released = true` 避免外层 `onExit` 重复执行 `executor.close(id)` 和重复发送 `core.notice`）。
