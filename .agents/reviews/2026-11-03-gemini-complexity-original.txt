## 一、核心结论与最重要前 5 项（Top 5）

### 核心结论

四层网关收口（Task 1～Task 5）确实消除了 `issue_dispatch` 与 `cron_occurrence` 两张自轮询中转表，删除了 `attachIngress` / `attachDelivery` / `attachInputRegistrar` / `attachExternalChange` 四个反向钩子，将协议 `Fact` 收敛为 15 项并剥离了 `Session.play`。

## 二、专项核查：最近收口是否只是搬走 / 改名 / 隐藏复杂度？

针对提示词要求重点核实的 5 个收口区域，逐项结论如下：

1. **`posting.ts` 与 `Transfer`（部分真收口，部分搬移复杂度）**
   - **真简化**：删除了旧 `Mailbox.routeChannel` / `hearChannel` 的平行跳数计算与写表分支，频道候选与工单放行确实统一走 `posting.forward` 过 `brakes`、写 `mailbox_delivery` 并写 `markRouted`。
   - **搬移/隐藏复杂度**：为了把 `mailbox.ts` 精确压到 520 行（匹配验收脚本 `test "$(wc -l < apps/server/src/mailbox/mailbox.ts)" -le 520`），抽出了未提交的新文件 `apps/server/src/mailbox/posting.ts`（216 行），并在 `work.ts` 定义了含 12 个字段（9 个可选）的 `Transfer` 结构，把 `prepare?: Effect.Effect<boolean>` 和 `commit: Effect.Effect<void>` 数据库钩子塞进路由传输对象里（见 **G05**）。
2. **双层 `Mailbox`（Tier 1 与 Tier 2 边界成立，但内部接线有半拉子残留）**
   - **应保留边界**：Tier 1（`mailbox_issue`：工单归属、人类门禁 `waitsForHuman`、Bot 轮次预算、handback/letGo 退回管家）与 Tier 2（`mailbox_delivery`：面向 `Session` 的 `pending -> handed -> consumed/dropped` 及三道刹车）生命周期确实不同，应当保留。
   - **隐藏问题**：`work.ts:242-274` 写了完整的 `initial = Effect.fn("Mailbox.initialInputs")` 来合并工单排队输入与显式输入，但 `mailbox.ts` 根本没调用它！相反，`Issue.start` 和 `Issue.refreshQueue` 在 `issue.ts` 里各自手搓了一套讀取和转发 `mailbox_issue` 的逻辑（见 **G04**）；此外在 `pump.ts:39-55` 的 `readyInputs` 里又对 Tier 2 的 `mailbox_delivery` 重复做了一次 `waitsForHuman(issue)` 过滤，使得 Tier 1 和 Tier 2 都持有 `board: Map<string, T.Issue>`。
3. **`Trigger` 与 `replay`（消除了自轮询表，但重放与写入分裂为 3 套）**
   - **真简化**：砍掉了 `issue_dispatch` 和 `cron_occurrence` 两张表。
   - **隐藏复杂度**：由于 `Ingress` 在第 8 层，而 `Channel`（第 6 层）、`Issue/Cron`（第 7 层）、`Mailbox`（第 5 层）都在 `Ingress` 之下，下层无法调用 `Ingress.record`。结果代码里出现了 **3 套写 `ingress_trigger` 表的实现**（`Ingress.record`、`issue/trigger.ts:recordTrigger`、`channel/chat.ts:settle`），以及 **3 套重放循环**（`Mailbox.replay` 每 3 秒轮询非 cron/非 channel_message 的未路由 trigger；`Channel.start` 重放 `unroutedChannelMessages`；`Cron.tick` 每次先跑 `Cron.replay` 重放 `unroutedCronTriggers`）（见 **G03、G08**）。
4. **`Issue.refreshQueue`（方向理顺，但与 `Issue.start` 存在双轨分叉）**
   - **真简化**：排队推进回到了 `Issue` 自身（监听 `core.subscribe` 的 `issue` / `sessionGone` / `session` 事实 + 定时兜底），不再由 `Ingress` 反向调用。
   - **残留问题**：`Issue.refreshQueue`（`issue.ts:782-816`）与 `Issue.start`（`issue.ts:563-620`）对排队输入的消费方式不一致：`refreshQueue` 通过 `mailbox.queuedInputs`（每个工单只取 1 条 `DISTINCT ON (m.issue_id)`）调 `mailbox.registerInitialInputs`，而 `Issue.start` 直接查 `qi.issueInputs` 并调 `qi.forwardIssueInput`（不写 `mailbox_delivery`）（见 **G04**）。
5. **Core 快照读取与缓存（用 `core.transitions` 规避静态检查，复制了状态源）**
   - `modules.test.ts` 检查 `readsOf(file, text, "core", "state")`，禁止非 `Issues` 模块读取 `core.state().issues`。
   - `Mailbox`（第 5 层）为了在不触发 `modules.test.ts` 报错的情况下拿到 `T.Issue`，在 `mailbox.ts:204-208` 写了 `const [snapshot] = yield* Effect.scoped(core.transitions)`，并在 `Mailbox` 内部维护了 `const board = new Map<string, T.Issue>()`，每次 `receive`、`subscribe`、`flushIssue`、`onFact` 都重新创建 `PubSub` 订阅、取快照、清空并重建 `board`（见 **G01**）。

### G14【待确认假设 · 并发与事务边界】`Channel.startTalk` 在 `registerTalk` 中逐条跑 `Mailbox.insert`（含独立事务）+ `Mailbox.hand`

- **文件路径与行号**：
  - `apps/server/src/mailbox/posting.ts:169-208`（`registerTalk`）
  - `apps/server/src/channel/chat.ts:680-747`（`registerTalk` 与 `startTalk`）
- **生产调用方**：`apps/server/src/channel/chat.ts:690`（当主人在帮工档案私聊里发第一句话启动 `talk` Session 时）。
- **代码片段**：
  ```ts
  // apps/server/src/mailbox/posting.ts:169-208
  const registerTalk = Effect.fn("Mailbox.registerTalk")(function* (session: string, launch: string, at: number, rows: readonly TalkRow[]) {
    yield* Effect.forEach(
      rows,
      (talk) =>
        Effect.gen(function* () {
          const recorded = yield* db.one(qr.triggerById({ id: talk.row.envelope_id }));
          if (!recorded) return yield* Effect.die(new Error("Private message trigger is missing"));
          ...
          yield* Effect.andThen(
            insert({ session, row: { ..., state: "pending", launch: null, ... } }),
            hand(session, talk.row.envelope_id, launch, at),
          );
        }),
      { discard: true },
    ).pipe(Effect.orDie);
  });
  ```
- **为什么值得注意（待确认假设）**：
  1. `registerTalk` 是在 `Session.send` 的 `hiring` 回调里被调用的，而 `Session.send`（`session.ts:1141`）**本身已经处在一个外层 `db.inTx(...)` 事务中**！
  2. 在 `registerTalk` 里，对最近 12 条消息逐条调用 `insert`（内部开嵌套 `db.attemptTx` -> savepoint，并获取 `writtenLocked` 锁）紧接着又调 `hand`（再次获取 `writtenLocked` 锁执行 `UPDATE mailbox_delivery SET state = 'handed'`），而且如果外层事务随后因其他原因回滚，`insert` 和 `hand` 已经同步修改了内存中的 `open`（`Deliveries`）和 `reach`（`Reach`）缓存（不像 `ChatModel` 有 `Effect.onError(() => reload)`）！
  3. 对比同文件的 `registerInitialInputs`（`posting.ts:146-162`）：它是在单个事务块里跑完所有数据库写入，**等事务提交成功后**才在最后统一更新内存 `received` 和 `stored`。`registerTalk` 却在循环内部边写库边改内存，且最后 `.pipe(Effect.orDie)` 把所有 `SqlError` 变成了不可恢复的 Defect（而 `Session.send` 的 `hiring` 约定是返回 `NotRecorded` 走优雅拒绝路径）。
- **最小修改方案**：
  - 将 `registerTalk` 改为与 `registerInitialInputs` 相同的结构：在一次 `writtenLocked(db.attemptTx(...))` 中完成全部行的写入与 `markHanded`，事务提交后再更新 `open` 与 `reach`，并将错误映射为 `NotRecorded` 而非 `Effect.orDie`。
- **验证方式**：`(cd apps/server && vp test run src/flows/talk.test.ts src/channel/chat.test.ts)`。
- **风险与置信度**：风险低，置信度 **中高（代码路径已核实，故障窗口在嵌套事务回滚时触发）**。

## 四、已核实应保留的复杂度（不要误删的合理边界）

审查中重点核查了以下看似复杂、实则承担关键领域不变量的设计，**明确建议保留，不要合并或删除**：

1. **`Assignment`（责任关系）与 `Session`（持续执行上下文）与 `Executor`（运行时资源）三层分离**
   - `Assignment`（`issue_assignment` + `issue_assignment_execution`）表达「工单归哪个档案负责」，可在尚未开工、休眠或换 Session 重开时持续存在；`Session`（`session` + `session_run`）跨多轮 `Run` 与进程重启保留上下文身份（并支持无工单的档案私聊 `direct`）；`Executor` 独立管理 `oar` 子进程与 `Subagents` 的异步关闭确认（防止关闭失败时把仍被占用的 worktree 交给下一个会话）。三者职责正交，不可合并。
2. **双层信箱（Tier 1 `mailbox_issue` + Tier 2 `mailbox_delivery`）的生命周期分离**
   - Tier 1 解决「工单まだ没有在场 Session、或正在等人类拍板（`asking/stuck/reviewing`）、或 Bot 评审超预算时，输入归谁蓄水、何时放行、何时退回管家（`handback` / 关单 `letGo`）」；Tier 2 解决「具体某个 `Session`（帮工或管家）的唤醒、忙时攒批 Steer、真实入模 `Consumed` 回执与三道刹车」。两层状态机不能合并为一张表。
3. **主人追问与 Agent 间 `@` / 汇报的分流规则（`work.ts:183`）**
   - `const threads = audience && trigger.actor.kind !== "owner" ? [] : trigger.threads;`：当消息来自频道（有 `audience`）且发言者不是 `owner`（即帮工或管家在工单串里说话、`@` 别人或发汇报）时，清空 `threads` 跳过 Tier 1 工单拦截，直接按频道受众走 `forward`。这保证了帮工汇报与 Agent 间协作不会被工单自己的 Tier 1 蓄水池吞掉，是经过验证的核心不变量。
4. **协议层核心形状（`Session`、`Cron`、`Doing`、`WorkspaceState`）与视图形状（`SessionView`、`CronView`、`DoingView`、`WorkspaceView`）的分离**
   - `shapes.ts` 与 `projection/frame.ts` 将纯事实（供 `reduce` 与持久化使用，不带语言文案）与带 i18n 文案的 `View` 形状（仅在出帧 `frameOf` 时填充 `phaseText`、`actionText`、`whenText`、`nextText`）分开，符合「页面不折事实、持久记录不存界面文案」的架构原则，不应合并。
5. **两阶段准入锁（`Session.send` 的 `admission` 锁 + 每会话 `hand.access` 锁）**
   - `Session.send` 在容量检查、目录准备和 `Executor.start` 占位期间持有全局 `admission` 锁，一旦占位成功立即释放 `admission` 锁，再去执行 `hiring` 回调（可能获取 `Channel` 锁），从而避免与「持有 `Channel` 锁并调用 `Session.deliver` 等待 `admission` 锁」形成死锁；同时合并/检查只拿单会话 `hand.access` 锁，不阻塞其他会话派活。这套锁序不可简化。
